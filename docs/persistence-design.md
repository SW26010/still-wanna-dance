# 持久化数据职责与边界

2026-10-26 确认的设计。本文是持久化分类和职责的统一依据；实现范围和验证状态见[迁移计划](persistence-migration-plan.md)，实际落盘行为见[存储契约](storage.md)、[运行文件生命周期](runtime-lifecycle.md)和[配置生命周期](settings-lifecycle.md)。规则改变时同步更新这些文档。

## 目标与取舍原则

以“简洁、优雅、必要性、维护性、用户理解和管理的便利性”为依据，按用途、恢复价值、数据规模、访问方式和生命周期决定数据归属。文件数量少不是独立目标；固定目录中几个职责清楚的小文件，可以比混合职责的大文件更容易维护。

- **配置表达运行设置。** 配置承载程序基本运行所需的设置及用户选择，比较重要，但通常可以重新配置。配置项通常较小、更新不频繁；程序生成的身份、观测结果、任务结果和确认记录不因体积小就成为配置。
- **数据库保存适合统一管理的业务数据。** 包括长期积累、几乎不可重建的重要数据，也包括重要性较低、可以重建，但需要在大量记录中检索、筛选、关联、局部更新或统计，天然适合数据库操作的数据，以及围绕歌曲和视频资源库积累的大量结构化资料。入库依据是业务职责与存储方式的适配性，不要求每条记录都重要或不可重建。数据库因包含不可重建的个人积累，整体仍按最高备份优先级保护；不能仅为了省文件，将临时数据和零散运行状态并入核心库，也不因一份独立资料重要就将其塞入数据库。
- **完整视频独立管理。** 正式视频可以跨运行保留，重新下载有成本；它们与个人数据库的备份价值、容量和生命周期不同。
- **辅助资料集中放置。** 有跨会话保留价值、但不属于配置或核心库的内容，使用约定目录或独立文件。不同失效语义不强行合成同一个文档。
- **程序承担内部管理。** 缓存、日志和工作文件有固定位置、边界和清理责任；不要求用户日常删锁、清块、判断原子写文件或挑选 SQLite 恢复文件。
- **保留必要关联。** “可以重新获取”不等于“应该拆出数据库”；支撑收藏、历史和统计解释的歌曲、资源关系仍属于业务模型。拆分必须降低总维护成本，不能把一个事务变成散落的重复状态。
- **调整须有可核查的收益。** 合并、拆分或改变存储归属前，核对实际查询和更新方式、事务依赖、数据增长与清理、备份体积和恢复步骤、故障影响及用户管理操作，说明具体收益与新增成本。不能只凭“放一起简单”或“拆开干净”下结论；不需要另建评分体系，没有明确收益就保留现有合理实现。
- **错误按影响范围处理。** 可重建状态失效不能被当作核心数据丢失；核心数据无法可靠读写也不能被当作普通缓存缺失忽略。

## 基本划分

| 类别 | 内容与边界 | 重要性与重建成本 | 位置和用户管理 |
| --- | --- | --- | --- |
| 配置 | 程序基本运行所需的设置及用户选择，如数据库和视频路径、下载策略、代理连接设置、界面偏好 | 比较重要，但通常可重新配置 | 固定默认位置，EXE 自动读取；升级保留，备份便于恢复设置 |
| 核心数据库 | 收藏、屏蔽、个人历史、累计统计，大量歌曲与视频资源资料及其关系，以及重要性较低但适合数据库检索、关联和更新的结构化业务数据 | 各类记录的重要性与重建成本不同；因包含几乎不可重建的个人积累，整个数据库仍优先保护 | 数据库文件位置可指定；优先备份，不能随视频清理、缓存失效或配置丢失而重建 |
| 持久化完整视频 | 通过校验并正式发布的视频文件 | 没有核心数据库那么重要，但重新下载比较费劲 | 目录可指定；按视频保留策略管理，按需备份，不能被描述为永不淘汰的归档 |
| 值得保留的辅助状态或资料 | 不属于配置或核心库、确有独立保管价值的资料；按实际内容判断，当前不为填满分类新增文件 | 比较重要，但通常低于数据库；逐项说明丢失影响和恢复方式 | 有实际内容时可集中在一个目录，便于定位、备份或迁移，不要求用户逐个查找 |
| 可重建的跨会话状态 | 无需纳入业务库、为跨会话运行提供便利的辅助状态，如通道身份、测速样本和冷却、条款确认记录、上次扫描与任务结果、可重建的依赖工作数据、有界日志等 | 不承担重要业务资料保存；丢失不妨碍重新运行，但不承诺重现过去的观测或失败列表 | 约定位置，由程序按用途保留、失效或清理，不增加普通用户的逐项管理任务 |
| 仅运行期工作文件 | 单次运行中的视频块、发布与导入暂存、原子写工作文件、锁、会话发现与权限探测文件 | 不承载需长期保存的数据，不承诺跨重启业务恢复 | 由所属运行实例管理，异常残留安全清理；不要求用户备份 |

归属判断先识别配置、完整视频等明确职责；对其余数据，先按业务职责和访问方式判断是否适合纳入业务数据库，再将无需入库的资料和辅助状态按保留价值、跨会话需求或单次运行生命周期归入第四至第六类。不能因为数据可重建，就跳过业务判断直接放入第五类。

能否重建、重要程度与适合何种存储分别判断：配置可重建但重要，完整视频可重下但有成本；重要性较低的数据也可能因规模、查询和更新方式适合留在数据库。跨会话保留本身不是入库理由，可重建或具有时效性也不是拆出数据库的充分理由，应比较整体维护成本。SQLite 恢复所需伴随文件随数据库管理，不能因其存在时间短而当作可清理工作文件。

这是职责分类，不要求每类单独设置一个路径选项，也不要求每类恰好一个文件。第四类与第五类可以共享固定父目录，但值得保留的资料与可清理状态应明确分组，便于用户整体保管资料；缓存和工作文件不能因此获得与核心数据相同的保留承诺。

### 配置与辅助资料

配置中的数据库位置和视频位置可以独立设置。EXE 先读取固定配置，再打开指定资源；普通目录设置不依赖“切换整套应用数据根”或生成带参数快捷方式。

代理地址、用户名及与其配套的受保护密码属于连接配置，保持同一更新语义。当前导入的代理节点集合也是服务器、协议和凭据等运行配置；导入只是输入方式，本轮继续保存在配置中，保留预览不落盘、一次保存原子提交、失败保留原值、重启生效的行为。不为拆文件增加第二次保存或跨文件事务机制。唯一一份凭据仍按实际恢复价值保管，沿用现有密文保护，不增加明文副本。

`channel.key` 是稳定通道身份材料，不是解密代理凭据的密钥。损失它会失去原身份与旧观测的关联，不会丢失代理凭据、收藏、个人历史或完整视频。它属于第五类可重建的跨会话状态，继续由程序独立保存，不并入配置或数据库，也不要求用户专门备份。身份材料在发布网络对象前准备好，网络构造、诊断和节点查询使用本实例一致的值，不通过这些读取入口重入持久化写入。

`terms.json` 保存主动确认记录，不是用户偏好。按[存储契约](storage.md#json凭据与二进制身份)在单文件内有界保留多个环境或条款版本的凭据；没有可用记录时重新确认，沿用独立保护和成功保存后才授予同意的规则，不并入配置或核心库。

### 核心数据库与可重建状态

长期业务事实及其必要关系，以及按上述规模和访问方式判断适合数据库管理的业务数据，留在核心库。对可重建数据的保留期和失效规则按业务用途确定，不因与重要数据同库就承诺永久保存。当前数据库中各表的目标归属见[迁移清单](persistence-migration-plan.md#当前内容与目标归属)。

`song_urls` 本轮保留在核心数据库，不拆成 JSON、内存状态或第二个数据库。它保存每个歌曲、API、节点的最新地址观察，参与播放候选、失败回退、元数据补齐覆盖判断及更新顺序校验；其写入与资源属性、缺失歌曲关联共用事务。超过播放复用时限的记录仍可作为元数据覆盖证据。是否可重新获取或地址是否会过期，不能单独决定整条业务记录的存储归属；拆分未证明能降低总维护成本，因此不列入本轮实施范围。

`catalog_checks` 的检查提示本身不是重要积累，但它是现有清单业务的配套状态：当前只更新 `songs` 一份记录，成功检查与清单接纳共用事务，重启和离线界面会读取。代码复核未发现拆出它能降低总维护成本，本轮保留表和现有行为，不因“诊断可重建”而删表、另存或升版。这不授权将其他零散诊断并入数据库。测速样本继续留在已有独立状态文件中。

当前请求明细承担用户可见的“历史”和统计解释，记录真实 HTTP 视频请求，并非普通排障日志。2026-10-27 首发前收口后，预加载和批量下载仅保留已有诊断日志，不再写入请求历史；历史的用户可见范围和保留期不变。核心数据库具有长期积累价值，不意味着每条历史记录都必须永久保留；若未来改变历史范围或保留策略，应作为明确的功能变更讨论。

测速冷却虽然可以重建，但有避免重启反复大流量测试的作用，继续保留必要的跨会话状态。它不进入核心库；自动测试仍需先成功保存本次尝试，失败时不启动自动大流量测试。手动测试的现有边界保持。

上次扫描、最近成功批次和最近结束尝试继续作为低价值状态保留，每种只保存最近一份，不累积任务历史。复用现有快照和原子写机制，不增加数据库表、历史管理系统或用户选项；不迁移旧快照格式，缺失、损坏、不支持格式或数据库与视频位置不匹配时忽略。恢复的内容只用于查看带时间的过去结果，不代表当前库存，不恢复运行任务、选择或删除授权，也不作为是否允许建库的证据。保存失败保留本次内存结果并提示未能保存，不影响已完成业务；用户无须备份、搬迁或管理这些文件。

### 完整视频与工作文件

视频块只是运行期可复用内容，不是完整视频，也不是断点恢复资料。块文件与完整视频目录分开，沿用现有引用保护和回收规则，不能因为目录整理而删除仍在读取的块。

正式发布前的合并文件，以及导入暂存，需要按发布方式放在目标视频卷。这是保证发布行为的必要工作产物，由程序清理，不增加用户路径选项，不要求用户搬迁或备份，也不承诺视频目录运行时永远只有 MP4。

现有硬链接导入行为及其文件系统限制不在本轮重写。视频仍按原有保留策略处理；临时工作区固定在 EXE 旁 `work/` 下，不提供普通或高级路径设置，也不随配置文件、数据库或视频位置的变化换盘。工作区可能占用较多空间，需要换盘时正常退出并移动程序目录；原位置残留按所有权安全处理，不搬入完整视频目录。程序按实例隔离工作文件并持有对应所有权，不因固定父目录而混用其他实例的块。相关位置说明实际占用所在盘，不扩建配额系统，也不静默切换到系统临时目录或其他磁盘。

## 默认目录与状态命名

2026-10-26 独立复审及用户确认的目录方案如下，替代此前 `data/config.json`、`data/storage/`、`data/work/` 和辅助文件散置于实例根的路径约定；上述六类职责、文件格式和业务行为不变。目录按需产生，不交付空用户目录。

```text
SWD/
  SWD.exe
  licenses/                         # 发行文件，升级替换
  config.json                       # 配置，建议保留
  data/
    database/storage.sqlite         # 核心数据库，必要伴随文件留在同目录
    state/                          # 可重建跨会话状态，通常无需备份
      terms.json
      channel.key
      throughput.json
      inventory.json
      batch-last-success.json       # 最近成功的完整批量任务结果
      batch-last-attempt.json       # 最近结束的任务，包括失败或中止
      mihomo/                       # 现有依赖 Home，按实际需要产生
  videos/                           # 完整视频，按需备份
    {md5}.mp4
    .swd-tmp/                       # 同卷发布、导入暂存
  logs/                             # 有界排障日志
  work/<实例>/                      # 固定跟随 EXE 的临时块工作区
```

根目录单个配置文件使相对路径与实例归属保持直观，不为一个文件新增 `config/` 及兄弟目录解析分支。`data/database/` 提供 SQLite 文件组的保管边界；它只是默认位置，数据库文件与视频目录仍可分别指定。锁和原子写入工作文件随所属资源放置，不能为目录外观移入 work 或撤销必要的互斥。

`state/` 保持扁平：六个已知文件各保留当前一份，Mihomo 保留组件自己的目录。不合并独立状态、不新增网络／任务子目录、不保存多轮任务历史；两个 batch 文件仅改名，读写、失败保留和重启展示语义不变。当前没有第四类辅助资料，不创建空 `materials/`；将来确有独立保管价值的内容再放入 `data/materials/`，不得混入可清理状态。Mihomo 只调整现有 Home，不根据未经验证的文件名增加清理规则。

默认布局下，退出后备份 `config.json` 与 `data/` 即可保管配置和核心资料，精简备份可排除 `data/state/`，完整视频按需保留。外置数据库和视频按实际位置保管，任意外置父目录不属于程序所有，不要求一律复制或清理整个父目录。升级只替换发行文件，用户目录原样保留；无需备份不等于升级时应清空，不增加用户例行清理或新的备份系统。

## 定位 创建与打开

默认配置为 `EXE/config.json`。数据库文件位置和完整视频目录由配置分别保存；辅助目录保持可预测，普通设置不暴露每个内部文件的位置。沿用自定义配置的实例归属规则：名为 `config.json` 时使用其父目录，其他名称使用 `<配置文件全名>.d/`；这属于现行多配置隔离能力，不是旧格式兼容层。实例根内的 `data/state/`、`logs/` 和默认资源互相隔离，工作区仍归 EXE。桌面首次打开自动准备实例下的 `data/database/storage.sqlite` 与 `videos`，配置保存相对位置，基于配置文件父目录；正常使用无需手动选择或创建。自定义位置是可选操作，具体初始化与异常边界以[配置生命周期](settings-lifecycle.md)为准。CLI 显式提供 `-database` 与 `-video-dir`，`-create-database` 只明确建库后退出。路径由统一入口解析，不在各业务调用处推导。

仅在即将自动初始化未配置实例时检查当前默认数据库、必要伴随文件和视频目录；发现资料或无法可靠检查时保留原状，提示明确选择资源。不探测旧安装标记或历史布局，不解析迁移旧配置，不递归寻找任意外置库，也不清理未知文件。

程序目录内仅使用当前实例的默认数据库和视频位置；自定义位置应在程序目录外。已有资料和新建位置共用路径规则，不为历史布局保留特殊接入例外。数据库格式、目录类型、资源锁与视频保留策略检查仍然适用。

配置与数据库不是必须同存同亡的一对文件。配置缺失可以恢复或重新设置；不知道原数据库位置时，提示选择已有数据库或明确创建新数据库，不能推断成“可以创建空库”。配置重建不得覆盖、清空或重置原数据库。

数据库的创建与打开是不同操作。普通打开要求已有合法数据库，不隐式建库、不用业务快照推断初始化历史、不补齐损坏核心数据。应用的首次默认初始化负责调用明确的创建操作；这不要求新用户额外点击建库。已配置数据库的打开失败不能转为创建；自定义位置的新建仍是单独操作。当前结构以[存储契约](storage.md)为准；位置和连接所有权变化本身不构成格式升级理由。今后确需结构变化时，受支持来源只在受控入口升级；不支持或未来格式保留原文件并诊断。不让用户手改版本号或删库代替升级。

不建立旧测试配置兼容层，不等于允许放弃现有核心数据库。调整当前数据库结构前，须明确现有数据的保留、升级与回退方式；只支持实际需要承接的来源版本，不为未知历史格式建立通用迁移链。正式发布后的格式演进继续遵循同一打开契约。

数据库由应用持有，视频引擎使用既有业务存储。曲库、收藏、历史、元数据观察与无关设置保存不依赖视频盘可用，也不因访问数据库启动下载或淘汰视频。视频目录失联时仍可修改位置；“不保留视频”模式也不禁用位置编辑。路径变化继续保存后重启生效，不自动搬运用户数据。

配置重建后接入已有视频，或更换数据库而复用已有视频目录时，在启用可能删除视频的管理行为前明确当前数据库与视频保留策略。不能让新配置默认的“不保留”悄然清理原视频，也不能暗示旧数据库的收藏保护会自动跟随视频。该确认在选择已有位置或首次配置时完成，使用现有保存和重启流程，不新增永久绑定标记或每次启动的例行确认；确认后仍按现有保留算法管理。

数据库和视频分别排他保护；不同配置指向同一个数据库也不能并发写入，不能只锁配置目录。配置及工作文件按其所有者保护，复用既有 OS 锁机制；不为定位和清理增加永久 UUID、目录登记库或绑定文件。独立资源使锁的数量由实际写入职责决定，不以“只能两把锁”作为约束。

数据库仅支持可确认的单一硬链接名称及实际完整路径；不能保证独占和伴随文件归属的别名明确拒绝，不静默改写资源身份。限制只作用于数据库，不改变完整视频的硬链接导入能力。外部程序不得在使用期间移动、替换或改名数据库及其伴随文件。

个人数据操作验证当前数据库归属；涉及视频及当前数据策略的操作验证数据库与视频位置的组合，并保留提交时的文件身份、状态和保护检查。作用域由规范路径及既有会话校验确定，不成为永久目录身份。旧任务的执行状态、选择和导入回执不跨重启恢复；可恢复的上次结果仅供查看。

## 故障 清理与备份

核心数据库的故障反馈不依赖视频引擎是否存在。用户操作提交失败不能显示成功；后台持续写入失败不能只有日志。无效样本、业务校验失败、正常取消与核心 I/O 故障分别处理；状态反馈放在内存和现有日志中，不新增错误状态文件。

清理只处理已证明归属的工作产物，必须持有对应所有权且尚无写入者。不能把成功写日志、恢复数据库或视频盘在线作为清理块残留的前提；同时不得以缺少配置或数据库为理由宽泛扫描、递归清空未知目录。SQLite 的 WAL、SHM、journal 等伴随文件属于数据库机制，不是本程序可随意清理的缓存。

| 用户任务 | 目标操作 |
| --- | --- |
| 升级 | 正常退出后替换发行文件，保留配置、数据库、完整视频及所需辅助资料 |
| 重点备份 | 正常关闭数据库后备份核心数据；恢复仍需 SQLite 伴随文件时一并保留，由程序说明或操作入口处理，不要求用户猜测哪些可删 |
| 恢复使用习惯 | 按需保留配置，避免重新填写位置和设置；唯一一份凭据或导入资料按其实际恢复价值保管 |
| 搬视频 | 搬完整视频并修改视频位置；数据库、配置和块缓存不随之搬迁 |
| 搬数据库 | 正常退出后迁移数据库及必要伴随文件，再修改数据库位置；不要求连带搬视频或运行缓存 |
| 日常维护 | 程序管理缓存、日志和临时文件，不把删锁、清块或处理原子工作文件列为用户例行操作 |

同用户文件移动不等于跨 Windows 用户或机器可以解密凭据；不能承诺复制密文即可完整恢复。具体限制沿用现有保护契约。

hosts 及其备份属于本机系统接入与恢复材料，保留其特殊位置；会话发现记录是本机运行信息。VRChat 日志、VRCX 数据库和导入源视频属于外部输入。Mihomo 的实际落盘集合需要运行跟踪，但其职责仍应落在上述分类中。内存中的任务、队列和导入回执不因此增加持久化文件。

## 不采用的整理方式

- 为减少文件数，将测速、任务快照和其他独立运行诊断新增到核心数据库；也不反向按“诊断”名称清除已有业务配套状态，现有 `catalog_checks` 按上文的实际依赖保留。
- 将条款记录、生成的通道密钥等并入配置，以凑成“两个核心文件”。
- 因配置丢失就重建数据库，或要求配置与数据库必须位于同一根目录。
- 让普通用户通过切换整个数据根和维护快捷方式来改变数据库或视频位置。
- 只移动路径，保留数据库依赖视频引擎、所有设置保存依赖视频盘的耦合。
- 为本轮整理引入通用状态框架、重复存储、永久目录登记、运行任务恢复或旧测试配置兼容链。

这些边界替代此前讨论中相冲突的合并与整根定位设想；此前设计评审不等于这些已撤回设想的实施依据。
