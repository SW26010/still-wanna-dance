# Issue #21：VRChatUrlLogger v1427 行为与 CF 优选验证

**v1427 确实会把视频连接转发到指定 CF IP，但它的通用测速排名不能直接代表真实视频的速度，也没有覆盖播放链路的自动回退。** 本轮 HTTP 视频前 8 MiB 的三轮中位吞吐，从普通 DNS 的 1.725 MiB/s 提升至所选地址的 12.930 MiB/s；程序原默认地址同时达到 12.979 MiB/s。随后同视频 HTTPS 对照中，所选地址的直连与程序透传均两次超过 20 秒，DNS 对照两次完成。不能把 HTTP 收益外推到 HTTPS，或认为这次重新测速优于默认地址。

本轮完成 [#21](https://github.com/SW26010/still-wanna-dance/issues/21) 的 v1427 前置调查和隔离验证，**暂不按它的算法接入产品**。未修改 SWD 生产代码、配置、现行架构或既有跨时段实验；未启动 VRChat，未 commit / push / 更新 GitHub issue。完整观测见[统计与逐请求证据](../evidence/vrchaturllogger-20261021/summary.json)、[脱敏日志](../evidence/vrchaturllogger-20261021/logs.json)、[清单](../evidence/vrchaturllogger-20261021/manifest.json)。这不是 VRC 播放体验验收，不新增游戏台账项。

## 对象与证据层次

- 用户已打开的 Windows 程序，文件版本 `1427.0.0.0`，166,040,582 字节；SHA256 `a41475c46bcf01a398fd836d7f3739ad8e2e327f1abf8b6b58829597247a291f`。
- 从该 .NET 单文件包提取原始 `VRChatUrlLogger.dll`，SHA256 `13b610e14769a80d0aa0196e6810e2eddd753fadbf21d30f30114abad16ae4e7`；用 ILSpy 11.1.0.9782 阅读反编译结果。**以下代码结论来自这份二进制，不冒充作者公开源码，也不代表其他版本。** 原程序、反编译内容及工具留在私有忽略目录和本地备份，不入库。
- 在用户指定的 Windows 11 测试虚拟机运行其原界面，以系统 PktMon 采集网卡上的 TCP 80/443；本机用 dpkt 1.9.8 分析。测速抓包 153,786 包、实际转发抓包 17,600 包，PktMon 均报告无事件丢失。快照分别限制每包 512/1024 字节；不声称保存完整 HTTPS 正文。
- 原始 DLL 的定向调用在本机 .NET 10.0.12 执行，用于核实地址更新机制；公网测速与转发在测试机执行。这两类证据分别标注。
- 测速与视频对照串行进行；关闭显式 HTTP 代理，保留原 Host，HTTPS 保留原 SNI 和正常证书校验。虚拟机的网关行为、其他设备流量和公网调度未隔离，不能将结果描述为无任何中间设备的网络。

## 它怎样选 IP

| 环节 | v1427 的二进制逻辑 | 本轮实际证据 |
| --- | --- | --- |
| 候选来源 | `CfIpProbe.CandidateIps` 固定 104 个 IPv4；不读取当前资源 DNS、不在线拉取网段，也不包含 IPv6 | 抓包观察到全部 104 个候选 |
| 测量对象 | 固定 `https://speed.cloudflare.com/__down?bytes=2097152`，目的端口 443，正常 TLS 验证 | 捕获 63 个 `speed.cloudflare.com` ClientHello；未把这些请求当视频请求 |
| 并发和时限 | 最多 8 路；建连 5 秒、每次请求连同正文 10 秒；下载最多 2 MiB | 一轮日志约 47 秒，63/104 成功；其余 41 个未进入成功排名，未依据日志缺失补写逐地址失败原因 |
| 成功和排序 | HTTP 成功状态且读到至少 256 KiB；按正文 MiB / 总耗时排序，总耗时含建连、TLS 和首字节 | 第一名 `172.64.144.1`，界面 4.0 MB/s；第二、三名 `104.17.160.1` / `104.17.96.1`，3.6 / 3.3 MB/s。代码实际单位为 MiB/s |
| 应用 | 用户确认后保存第一名为主节点、第二三名为缓存下载备选，另保存测速前 IP | 本轮确认后设置文件与界面均更新；监听当时关闭，日志正确提示下次启动生效 |
| 失败和刷新 | 全部测速失败或取消应用时保留原主地址；此版调用入口是手动按钮，候选和排名没有独立到期刷新机制 | 部分失败实际保留；全部失败与取消应用分支仅作代码检查，未重复制造一整轮故障 |

该轮对候选的抓包 IP 层长度合计 139,476,692 字节，约 **133.0 MiB**，包含握手、重传等；不是正文下载量或运营商计费总量。104 × 2 MiB 是全部成功时的正文规模，不能写成本轮实际下载 208 MiB。8 个并行测速会相互竞争带宽，单次通用文件排名也没有直接测量当前视频、当前端口或长时间稳定性。

所选与默认地址均落在 [Cloudflare 官方 IPv4 网段](https://www.cloudflare.com/ips-v4) 内；本次真实视频响应另有 `Server: cloudflare`、`CF-Ray` 与缓存状态。这些证据共同用于确认本次对象，不能因 API 参数 `node=cf` 就固定认定未来资源属于 CF。

## 它怎样影响实际视频连接

启动监听时，`MainWindow.StartRedirect` 将四个固定域名 `api.udon.dance`、`play.udon.dance`、`api.pypy.dance`、`cdn.pypy.dance` 同时映射到 `127.0.0.1` 和 `::1`，在两族回环地址监听 TCP 80/443。**不是修改系统 DNS 服务器，也不是 SOCKS5 节点或系统代理。** 这会影响测试机上使用这些系统域名解析结果的客户端，而不局限于 VRChat 进程。

HTTP 从 Host 识别目标，原始请求前缀和后续字节继续转发；HTTPS 默认不解密，从 ClientHello 读取 SNI 后透传。目标仍用客户端原端口，未把 80 自动升级为 443。Cloudflare 支持这两个端口，但[支持端口](https://developers.cloudflare.com/fundamentals/reference/network-ports/)不等于两个端口或资源的吞吐相同。

本轮启用后核对了四个 hosts 域名和四个回环监听，实际请求先连接 `[::1]:80/443`。抓包确认公网目标为 **`172.64.144.1:80/443`**；HTTP 保留 `Host: play.udon.dance` 与 `Range: bytes=0-8388607`，HTTPS ClientHello 保留该域名。HTTP 返回完整 206、8 MiB，内容哈希与所有成功直连样本相同。说明优选结果能进入实际视频连接，确实不只是展示测速数字。

缓存是另一条机制：HTTP 视频缓存未命中时，程序另起完整后台 GET，同时继续原播放请求；完成后可从本地文件响应 Range。默认不开 HTTPS 解密时无法取得 HTTPS 完整路径，不能把 HTTP 缓存能力直接推广到 HTTPS。**本轮缓存目录为空，没有实际执行缓存发布、缓存命中或后台慢速切换**；这些描述来自二进制检查。

可选 HTTPS 解密会安装本地根证书；该模式的上游 `SslStream` 验证回调在此二进制中无条件接受证书。本轮没有开启、没有安装证书，不能用默认透明转发的证书验证结果为此模式背书。

## 失败回退与运行中更新的边界

播放转发只遍历 `GetRealIps(host)` 返回的地址。指定主节点时，域名缓存被填成该主地址；播放路径不读取 `_backupIps`，没有因为吞吐过低就切换备用、重新测速或回到正常 DNS 的机制。

后台缓存下载才把主地址和备选合并：有下一个候选且最近至少 5 秒窗口低于 100 KiB/s、下载尚不足已知长度的 60% 时，丢弃临时文件并从头换地址；最多三轮，轮间等待 10 秒。检查发生在读取返回之后，不是独立的停滞看门狗；错误 HTTP 状态会直接返回，不能概括成“所有故障都会自动切备用”。这些是代码路径结论，未做全故障矩阵。

还发现一个可复现的问题：**运行中应用新测速结果的“转发已实时生效”文案不符合实际地址状态。** `OnSpeedTestClick` 仅调用 `SetForwardIp`，而该方法没有更新 `_realIpCache`，也没有更新运行中的备选列表。定向调用原始 DLL 的结果是：

1. 设置 `104.16.0.1`，再设置监听域名，实际地址为 `104.16.0.1`。
2. 调用同一个 `SetForwardIp("104.17.0.1")` 后，`GetCachedRealIps` 和实际选址方法 `GetRealIps` 仍返回旧地址。
3. 重新执行 `SetWatchDomains` 才得到新地址；界面的停止/启动会重建代理并执行此初始化。

该实验未修改原 DLL，不是重写实现后的模拟；只证明此方法链，没有把它说成已经抓到原界面二次测速后的每一条连接。本轮联网验证是在监听关闭时应用结果，再启动，因而没有受到这个问题影响。

## 同一真实视频的 HTTP 对照

测试机重新请求歌曲 1343 的播放 API，实际获得 `http://play.udon.dance/...`，资源长度 32,867,177 字节。URL 原样使用，签名仅保留在私有材料。普通 DNS、全部三个 DNS IPv4、v1427 选中地址和原默认地址共六组，各预热一次、正式三轮，每次新建连接池，下载同一个前 8 MiB；轮换组起点、请求间隔一秒，20 秒期限。此轮不是完整位置平衡设计，也没有把不同组的块数当独立样本。

共 24 个 HTTP 请求全部满足 206、精确 Content-Range / Content-Length、identity、相同 ETag 指纹与 SHA256；均为 HTTP/1.1、CDN HIT。程序选中的两个备用地址未加入本次视频速度对照。

| 路径 | 三轮中位吞吐 MiB/s | 中位首字节 ms | CF-Ray 后缀 |
| --- | ---: | ---: | --- |
| 普通 DNS，实际选中 IPv6 `2606:4700:20::681a:51c` | 1.725 | 446.5 | SEA |
| DNS IPv4 `104.26.4.28` | 1.720 | 444.1 | SEA |
| DNS IPv4 `104.26.5.28` | 1.755 | 392.5 | SEA |
| DNS IPv4 `172.67.69.58` | 1.130 | 464.0 | SEA |
| v1427 测速所选 `172.64.144.1` | 12.930 | 114.6 | HKG |
| v1427 原默认 `172.64.229.213` | 12.979 | 122.5 | HKG |

所选地址明显快于本轮普通 DNS 和三个 DNS IPv4，但**没有显示胜过原默认地址**。这是地址、路由与服务端处理路径组合的结果，CF-Ray 后缀不是固定机房或独立因果证明。最快样本不到一秒读完 8 MiB，这些数值是该区间的平均吞吐，不是完整视频、长时间持续吞吐、冷 CDN 首播或游戏首帧保证。另两个 DNS IPv6 未逐一固定测试，不能宣称胜过所有 DNS 候选。

## HTTPS 反例与补测

HTTP 真实转发通过后，将同一资源路径及查询仅改为 HTTPS 做独立协议控制；**这不是 API 另行返回的 URL，也不混入上述 HTTP 统计**。正常证书验证通过、返回 206/HIT，但首笔经程序转发在 20 秒只读到 6,114,990 字节，记为失败。

保留这笔失败，再追加预先限定的两轮三组对照：所选 IP 直接连接、同 IP 经程序透传、固定原普通 DNS 使用的 IPv6。每请求仍取 8 MiB、期限 20 秒，轮换起点，禁止凭结果延长时限或更换候选。

| 路径 | 第一轮 | 第二轮 |
| --- | --- | --- |
| `172.64.144.1:443` 直连 | 20 秒超时，2,075,779 字节 | 20 秒超时，8,375,073 字节，仍未完整 |
| 同地址，经 v1427 透传 | 20 秒超时，2,133,687 字节 | 20 秒超时，2,539,484 字节 |
| 固定 DNS IPv6 直连 | 完整 8 MiB，5.346 秒 | 完整 8 MiB，12.142 秒 |

四笔选中地址样本均失败，不能因为已收到 206 或第二轮接近完整就改记成功。直连也慢，排除了“只有程序透传才会出现该慢速”的解释，但本轮没有锁定网络限速、路径调度等更深原因，也不能断言代理完全没有额外开销。DNS 对照本身也有明显波动。

这组反例足以否定“同 IP 在通用 HTTPS 测速站快，就一定能加速该视频的 HTTPS”。选址必须以真实资源与实际协议/端口为依据；即使保持原 SNI 和 TLS 验证也不能省略这一检查。

## 对 SWD 的最小结论

额外 CF IP 值得作为**直连侧候选来源**继续评估；不复制四个固定 hosts 域名、全局主 IP、104 地址并发通用测速或播放无 DNS 回退的设计。

- 继续依照[动态资源来源](../resource-domains.md)，只在实际资源已确认使用 CF 时提供额外候选，保留普通 DNS 候选。
- 复用现有[通道与 Monitor](../upstream-channels.md)的 Transport、测量、推荐和失效处理；正常域名、Host、SNI、证书及资源内容验证必须保留。HTTP 与 HTTPS/端口之间不得直接复用未经验证的“最快”结论。
- 候选扫描负担、有效期、失败退出及 DNS 回退须有边界；本轮不为其新增配置、UI、周期或独立业务选路系统。采用哪个来源和最小扫描规模仍由后续产品方案确定。
- [既有完整分块及跨时段对照](cf-family-paths-20261021.md)继续按原协议收尾；本轮 HTTP 前缀观测与它的 HTTPS/完整分块结果不合并计算收益，不修改其预先条件。当前不足以宣布“对所有用户默认启用优选”或“稳定 5 MB/s”。

前置调查已可收尾；尚未交付产品集成，不将 issue 关闭或把它标为功能完成。若进入实现阶段，上述 HTTPS 反例和地址更新问题应作为选址/生命周期验收依据；不需要为了这项机制调查额外启动游戏。

## 失败保留、清理与归档

首次连接使用任务专用 known_hosts；最初桌面实例未提权，启动监听被程序拒绝。那两笔 HTTP/HTTPS 探测实际仍连公网 DNS，已单独保存为 `preElevationDirectObservations`，不混入转发成功证据。随后利用已有管理员 SSH，在同一交互会话以临时任务启动原程序，实际验证回环监听后才继续。原始普通实例与重复启动实例在没有监听、没有缓存目录时结束。

测试机自带 curl 8.8.0 在带 write-out 参数的探测中返回错误 43；无此参数的请求正常。失败材料保留，未把它当作上游不可达；正式测量改用 Go 标准库探测器。首次 dpkt 安装受沙箱临时目录权限限制，经仓库临时目录入口成功；首次抓包分析遇到网卡卸载产生的零 IPv4 长度，已显式计入未知长度包，不用截断后的捕获长度伪装原始线速字节。

结束时通过程序停止监听，hosts 已由程序恢复且与初始文件 SHA256 完全相同；设置文件也按原字节恢复。测试机重新打开原普通权限程序，转发 IP 回到默认显示、监听关闭；80/443 无遗留监听，临时任务已删除，PktMon 停止、过滤器为空，系统代理保持关闭。没有启动游戏、更改 DNS 或安装 HTTPS 解密证书。

原始材料下载后逐一比对测试机的 41 个文件哈希；原始 EXE、抓包、失败日志和工具均留在 `artifacts/vrchaturllogger-20261021/` 及本地备份。Git 仅收录精简 JSON、脱敏日志、方法和哈希，不公开完整签名 URL、私人路径、原程序或反编译全文。备份与测试机临时目录清理回执见证据清单；未经授权未发布 Release 附件。
