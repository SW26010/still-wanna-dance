# 存储格式与现有歌曲库兼容

这是第一版兼容目标。Go MVP 已实现直接复用及原布局发布，并以临时歌曲库自动化验证；原版回读及真实歌曲库验收仍待完成。实现策略和边界见 [MVP 手册](mvp.md)，原版格式的观测依据见[已知协议与行为](observed-behavior.md)。

## 直接复用现有目录

StepStash 必须允许将歌曲库根目录配置为已有目录，例如：

```text
<歌曲库父目录>\wannadance-song
```

该路径为脱敏占位示例，实际路径通过 `-songs-dir` 配置。对于完整、有效、与请求内容版本匹配的已有视频，直接读取并命中缓存；不要求导入、迁移、改名、复制整个库或重新下载。

## 对外存储格式

```text
<歌曲库根目录>/
  1344/
    video.mp4
    metadata.json
    download.txt       # 可选，已有 mirror 库可能包含
  <其他歌曲ID>/
    video.mp4
    metadata.json
```

- 歌曲 ID 对应目录名，最终视频仍命名为 `video.mp4`，元数据仍为 `metadata.json`。
- 同时兼容现有 mirror 库的完整元数据与原版代理下载生成的简化元数据；不能强制要求 `url`、`urlForQuest`、完整标题等只在某些样本中存在的字段。
- `download.txt` 不是播放的必要文件。存在时应保留，不因缺失而重新下载有效视频。
- 保留已有元数据的额外字段、曲目信息和其他附属文件；不能为了统一格式将完整元数据降级覆盖成简化版本。
- 根目录中的 `failed.txt` 等非歌曲条目应忽略或作为辅助信息处理，不能当作歌曲目录，也不能自动清除。

## 新增缓存与状态文件

新下载成功的视频继续发布到 `<id>/video.mp4`，并生成与原版可读取格式兼容的 `metadata.json`。具体必需字段和原版回读能力需要验收，不能仅凭文件名相同就宣布兼容。

下载中间文件应与正式歌曲文件区分；完成检查后再发布，不把残缺文件占用为正式 `video.mp4`。已有有效版本在新版本下载失败时应保留，不先删除再尝试回源。

下载状态和已下载的版本文件放在独立的 `-cache-dir`；它们可以重建，不能成为读取现有歌曲库的强制导入条件。MVP 对视频和元数据分别进行完整文件替换，不提供两文件原子事务；崩溃窗口及诊断规则见 MVP 手册。

## 校验与兼容边界

- “复用”适用于有效文件；仅有同名目录或文件不代表版本正确。
- 元数据缺失、JSON 损坏、大小或 checksum 不符时，应诊断并按后续明确的恢复策略处理，不能默默将未知或半成品作为有效缓存，也不能无条件清空已有库。
- 校验时机和索引策略待设计，不默认每次启动都对整个视频库进行全量 MD5 扫描。
- 读取已有缓存与新增写入的权限分别处理；只读检查不应修改视频或元数据。
- 当前目标是新旧程序可以轮流复用同一歌曲库；两个程序同时写入同一目录的兼容性尚未承诺，需额外验证协调机制。

## 必须通过的验收

- [ ] 直接配置一份已有 `wannadance-song` 库，正常歌曲命中本地并支持完整读取与 Range，无需迁移或重新下载。
- [ ] 分别使用 mirror 完整元数据、原版简化元数据、无 `download.txt` 的样本，均可复用有效缓存。
- [ ] 纯读取前后视频及已有元数据哈希不变，附属文件保持不变。
- [ ] 新下载继续采用 `<id>/video.mp4` 和 `metadata.json`；停止 StepStash 后，由原版读取验证兼容。
- [ ] 重启后无需原有 StepStash 索引也能重新识别库；损坏文件、版本变化和下载失败按明确策略处理。

以上验收框保留用于真实歌曲库和原版回读验收，自动化通过不等于实机验收已完成。
