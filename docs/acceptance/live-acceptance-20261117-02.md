# LIVE-20261117-02：owner 进度模型 A/B 与后半段缺块

## 结论与条件

同一首 4598、同一缺块条件下，开头缺块的 A 组没有错误或回零，按原时间线结束；B 组的进度模型提前返回一次 504，随后黑屏、重新加载并回零，再次遇到缺块，直到来源恢复。游戏日志中的起播至结束时长由 133 秒增加到 170 秒。这是一对条件下的观察记录，不是发生频率估计。

将缺块移到后半段后，B、A 都由正式下载截止路径返回 504，均重新加载并回零，起播至结束都是 288 秒。该对照中模型主动拒绝次数为零，不能把后半段回零归因于模型的提前拒绝；也不能据此认为缺块移至后半段就能避免 owner 回零。

证据见[逐请求与播放记录](../evidence/live-20261117-02/playback.json)、[构建身份](../evidence/live-20261117-02/provenance.json)和[清单](../evidence/live-20261117-02/manifest.json)。本轮是 issue #51 的隔离实验，没有启用正式产品策略。

- 环境为 Windows、VRChat 中的 WannaDance 正式播放器；多人房，本机为 owner。角色有起播日志中的 owner 分支及操作者确认支持。未独立采集本轮游戏／世界版本号，不外推到其他播放器版本。
- A 使用实验准备时当前 main `d7be45246d572567935a288e5a9ec34d60ec660a` 的正式请求与交接逻辑；受控来源和匹配歌曲元数据是共用夹具。不是对已发布桌面安装包的验收。
- B 使用同一基线，读取 VRC 日志建立线性进度模型，余量 0 秒。显式绕过角色门槛，owner 和缺少多人角色记录时也参与判断；仍保留同次已识别播放最多一次主动拒绝、错误恢复期间放行。
- 默认交接 2 秒；B 按模型为仍预计使用的范围选择 10 秒。下载延续保持原 30 秒；所有配对使用 2 个下载槽位、无限缓存。
- 使用同一媒体版本，35,169,662 字节、目录时长 133 秒。缺块先向 SWD 提供 128 KiB 后停住，其他块正常供数；故障定时从每笔第一个 NSPlayer GET 开始。源文件与数据库均隔离，未限速正常块。

## 实际结果

| 配对／顺序 | 缺块与恢复条件 | 主动模型 504 | 观察结果 | 游戏起播至结束 |
| --- | --- | ---: | --- | ---: |
| 开头 A | 2–3 MiB；第 66 秒来源恢复 | 0 | 人工约起播后 7 秒卡住、停顿约 51 秒后恢复；无黑屏或回零反馈，日志无错误／重载。来源恢复后请求跳到较后范围，按原时间线结束 | 133 秒 |
| 开头 B | 同上 | 1 | 首次接续被模型拒绝；人工黑屏、重新起播，日志同步回 0；再次卡住，来源恢复后继续 | 170 秒 |
| 后半段 B | 24–25 MiB；第 180 秒来源恢复 | 0 | 人工约起播后 91 秒卡住；正式截止返回 504，黑屏后两次加载尝试，最终同步回 0，再播放至结束 | 288 秒 |
| 后半段 A | 同上 | 0 | 人工约起播后 96 秒卡住；同样出现正式 504、黑屏、两次加载尝试及回零，再播放至结束 | 288 秒 |

开头 B 的人工首次卡顿只报告“很快”，没有精确秒数，不补造其总停顿时长。后半段 A 的卡顿时间是约数。按操作者约定，未报告的音画异常视为正常，但不补造缺失的事件时间。后半段两笔的自然结束由游戏日志确认；人工时间与日志时间保留秒级差异，时长比较统一采用游戏日志。

### 开头配对：增加的回零

A 的首次播放器请求在第 32.011 秒结束，接续请求收到回退的 8 KiB 后又等待；下一请求继续等同一缺块。第 66.001 秒来源恢复后，新请求转到 14,614,528 字节处。游戏没有发生错误和重新加载，不能把这次前跳称作“跳过仍不可读块”：此时来源已经恢复。

B 在第 35.051 秒的接续入口返回 504，对应模型使用时间约为第 12.747 秒。日志随后记录错误、重新加载，以及同步到 0 的 owner 起播。该拒绝没有建立新的 SWD 下载需求。此后的请求均按恢复阶段放行，没有模型连续拒绝；来源仍不可读，所以从头播放再次遇到缺口。第 66.001 秒来源恢复后才继续供数。

两笔起播至结束相差 37 秒。请求至实际起播的间隔不同，人工反馈也有秒级误差，因此不将所有细小时差归因于模型；额外的错误、重新加载和回零有 HTTP 与游戏日志的对应证据。

### 后半段配对：正式 504 也会回零

文件索引显示 24–25 MiB 块最早约在第 92.044 秒使用，线性模型估计为第 95.169 秒，确实位于全曲后半段。两笔都实际交付至 24 MiB，并在此停住，不是整段已缓存而绕过故障。

B 的两次预读接续记录为 `model-unavailable`，并未被模型判定为过时；后续已有请求在等待中到期，不触发新的入口判断。第 122.997 秒正式处理返回 504，重新加载后的同缺块请求也在约 30 秒后收到正式 504。A 对应首个 504 在第 119.689 秒；两笔终端错误均标记为 `download need-by window expired`。这证明该组是下载时间窗口到期后的响应，不能仅凭“等了约 30 秒”把它另称为独立读取超时。

两笔都先尝试从 24 MiB 接续，随后重新发起从零请求，游戏同步目标回到 0。B 从首次起播到再次起播为 155 秒，A 同样为 155 秒；再次起播后均约 133 秒自然结束。

该配对顺序为 B→A，使用同一个 v3 EXE。初始播放器 GET 在 B 为 `bytes=0-`／206，A 为无 Range／200；两者实际服务范围均从零至文件尾，故障边界和恢复定时一致。没有声称播放器内部缓存和逐请求时序完全相同，也没有据此估算日常发生概率。

## 构建与验证边界

| 构建 | 用途 | EXE SHA256 |
| --- | --- | --- |
| v1 | 开头 A | `9c004022ce23c84852d9f8743fda76049262ee00283e7ecd92648975f36b0c14` |
| v2 | 开头 B | `b7e29a9226d47527c60ef1c17425cfc0ea2aa40b11b1cb1e40a200fa8fa97f2a` |
| v3 | 后半段 B、A | `e021d7be2b659a0680ab67821f5ffcd1c78db06718a2cde24b55d35d2687aeb8` |

v1→v2 只调整开启实验时的角色门槛：缺少多人角色记录也不避让；关闭模型的 A 分支不变。v2→v3 只将夹具允许的缺块位置从最多 16 个前置块，改为文件内完整块的有效范围。首次设置 24 块被旧上限拒绝，进程在播放前退出；修正并校准后才开始后半段实机，没有把失败准备算成一笔播放。

模型单元测试通过，覆盖 0 秒边界、关闭／开启、默认角色门槛、实验角色无关路径，以及 owner 回零后不连续拒绝。三次隔离 HTTP 校准覆盖有角色日志、缺少角色日志和 24 MiB 前缀：A 为 206，B 为一次 504，拒绝未进入 SWD 需求；B 后续恢复请求为 206。它们不替代游戏观察。夹具补丁相对固定 main 的应用检查通过。

公开构建记录保留实际源码哈希、不同构建的模型快照、夹具及校准结果。两笔开头使用不同二进制，不能描述为完全相同 EXE 的开关对照；角色门槛差异只作用于开启模型，关闭路径另经受控 HTTP 校准。后半段为同二进制开关对照。

无限缓存和正常后段供数限制了交接成本解释；本轮没有证明 10 秒交接的净收益，也没有证明错误码是回零的充分必要条件。后半段 B 未产生模型主动 504，不能用它验证“模型在所有后半段请求中正常起效”。

## 证据与清理

公开证据以各笔首次播放器 GET 为相对零点，保留范围、字节数、状态、模型判定、游戏事件及人工观察；不含玩家／房间身份、原始 URL、私人路径或原始游戏日志。原始记录、实际 EXE、源码及准备失败保留在忽略目录。

两轮支持服务及四笔实际播放服务均已停止，80／443／19082／19083 无本轮监听，hosts 前后哈希一致。本轮没有修改 hosts，保留了原有映射；日常 SWD 没有由实验自动启动。实验视频、日志与源码作为证据保留，没有删除用户视频或数据库。
