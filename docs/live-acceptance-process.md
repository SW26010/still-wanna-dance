# 开发验证与 VRC 实机验收机制

目标是快速推进开发，只把**不得不在 VRChat 游戏里判断的剩余风险**攒到下一轮集中验证。台账不是每项改动的登记簿，也不是开发者把验证转交用户的出口。本文替代旧有“用户可见行为一律登记”“自动检查不能替代任何实机项”的要求；历史文档中的待验步骤按本文重新判断必要性，不自动恢复为当前要求。

## 开发者先完成验证

先确定本次变更可能破坏的行为，再选择能判断该行为的最小检查。已有证据足够且仍适用时直接引用；只补缺口，不机械增加测试或重跑全量矩阵。

| 要判断的行为 | 默认验证方式与责任 |
| --- | --- |
| 协议、配置、文件/数据库、调度时序与取消、故障注入 | 开发者执行针对性单元/集成测试、受控上游或隔离进程检查；用脚本编排精确时序，不要求用户在游戏里撞竞态 |
| 页面显示、交互、草稿、导航、错误提示 | 开发者用浏览器测试或直接操作浏览器检查；需要确认后端持久化/重启时使用隔离真实服务，不能以纯内存夹具外推 |
| 托盘、UAC、跨用户/机器、系统 DPI、辅助技术、会话结束或断电 | Windows 环境验证；能由 agent 完成的就完成，缺环境则在对应开发记录注明未验证范围及具体下一步，不进入 VRC 台账 |
| 实际 VRC 播放器的请求/重连、游戏日志交接、多人同步、音画和游戏内卡顿 | 先完成可替代部分，只有仍需游戏的部分进入[台账](live-acceptance-backlog.md) |

有用户可见变化、代码复杂、测试没写、agent 没有工具或环境、旧项尚未关闭，都不是必须 VRC 验收的理由。真实公网请求也不天然需要启动游戏。工具受限时先尝试可用的测试/API/隔离服务；剩余缺口如实说明，不能虚报通过或只丢一句“待实机”。

开发验证通常记在现有验证文档或变更说明，写执行范围、结果和有影响的限制即可，不要求每次建独立报告、截图集或新编号。[非 VRC 验证分流](validation-followups.md)只用于承接本次旧项整理，不建立另一套逐提交强制台账。

## VRC 台账准入与合并

入账必须能回答：**还缺什么事实，为什么只有游戏能给出，用户最少要做什么？** 每项保留代码/开发验证依据、不能替代的理由、最短操作、预期、必要证据和已有结果。仅剩普通开发验证时不入账；没有 VRC 剩余项时，完成说明直接给验证结果，不强行附 LA 编号。

先搜索现有场景：一次冷播、预览拖动或队列交接能验证多项改动，就更新同一场景并共用采集。只有真正不同的游戏条件才拆场景。合并的是操作和证据，不把几十个代码断言拼成一个永远无法通过的大项；程序内部边界留给开发测试。新编号从 `LA-048` 继续，旧编号不重用。

当前台账以场景为判定单位。某场景已覆盖就记录结论；同组其他场景未测不抹掉它的结果，也不强制下轮重测已覆盖场景。已通过结论只在实际构建和环境内成立；后续变更影响该结论时说明影响点并定向重开，不能仅因有新提交就全表重开。

允许合并、迁出和取消：注明原因、接收场景或开发记录，保留旧编号与历史证据。旧实现已删除、条件已由充分开发验证覆盖或本就与游戏无关，可以退出积攒；退出不是“实机通过”。仍适用的已知失败必须明确跟进，不能通过改分类抹去。

## 下一轮怎样少做、做准

默认等待用户安排游戏时机，不因功能开发完成启动游戏或改 hosts。等待期间开发者继续完成已有授权下的测试、问题定位、修复、构建和采集准备，不能用等待实机阻塞无关开发。

开始前由 agent 核对相关开发检查和已有证据，选最少的剩余游戏场景，准备隔离数据、构建及采集。向用户给简短的游戏操作顺序；构建、日志关联、哈希、脱敏、报告及清理由 agent 承担。只选择与变更或历史失败相关的回归，不默认每轮重复全部基础矩阵。同一操作能覆盖多个场景时一次执行；出现失败先定位并补可控回归，不让用户反复盲测。

实际开测时复制[报告模板](live-acceptance-report-template.md)，批次使用 `LIVE-YYYYMMDD-NN`。记录源码 SHA、工作区差异和实际运行 EXE 的 SHA256；有未提交代码则保留可还原补丁及哈希。只有实际测发行包时才记录包哈希。中途换构建分段记录，不混用结论。环境只写影响判断的游戏/Windows 版本、网络、存储、角色与条件；统一相对时间并注明关联误差。

## 必要证据与交付

| 交付物 | 最小内容 |
| --- | --- |
| `docs/acceptance/live-acceptance-YYYYMMDD-NN.md` | 构建、范围、操作与实际结果、证据引用、未解决问题、实际清理回执；共用步骤写一次 |
| `docs/evidence/live-YYYYMMDD-NN/` | 支持结论的脱敏日志片段、操作/音画反馈记录；只有确有必要时另附截图或录像，不为每条代码断言另造证据 |
| 证据目录内 `manifest.json` | 批次、源码/实际构建哈希、证据路径/字节数/SHA256/来源/脱敏说明；清单不含自身哈希 |
| 台账与证据索引 | 对应场景结果、报告链接和剩余动作；在 `docs/evidence/README.md` 增加入口 |

一份证据可支持多个结论，引用具体位置即可。播放体验需实际音画反馈与可关联的游戏/服务事件；HTTP 200 或测试通过不能证明游戏体验。证据缺口只限制相关结论，不因无关的全量 Debug、截图或退出标记缺失否定已能证明的场景。无法判断的部分明确未测或阻塞，不能补写通过。

证据哈希按提交后的 Git blob 字节核对，注明 `hashBasis: git-blob`；运行文件哈希按实际字节。大附件遵循[证据与大文件约定](evidence-storage.md)，报告引用持久链接、哈希和脱敏摘要。不得仅留下聊天里的结论。

原始资料放 `artifacts/acceptance-evidence/<批次>/` 等忽略路径。提交材料遵守[脱敏规则](evidence/README.md)，去除私人路径、身份/房间信息、完整签名 URL、凭据及代理密码等；清理临时环境前由 agent 提取和校验必要证据。只清理本轮实际创建或修改的进程、端口、挂载、hosts 和测试数据，并核对结果；未触及的写不适用，失败的明确跟进。

## 结果与收尾责任

执行状态为 **待验收 → 本轮验收中 → 通过 / 失败 / 阻塞 / 未测**；分类调整另记为“并入 / 转开发验证 / 不再适用”，不得当作通过。失败先由开发者分析、修复并完成适当检查，只有修复后的游戏专属复测仍积攒。阻塞/未测只保留仍符合准入条件的剩余场景，能转开发验证的及时转出。

已实际开测但中断，交付已有结果和未完成原因；尚未开测的普通开发轮次无需空的 LIVE 报告。报告、脱敏证据、manifest、台账和索引作为同一验收变更准备，历史报告及失败证据不覆盖重写。

最终说明已完成什么、还缺什么及谁负责下一步；有游戏剩余项才附台账编号，非游戏阻塞单独说明。不把“登记待验”写成验证完成。Git commit/push 遵循当前授权，未执行则明确未提交/未推送。
