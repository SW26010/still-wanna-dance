## LA-025：播放接入与恢复

- **依据与必要性**：[API 接入边界](resource-domains.md#仅接管-api-的假设与待验证边界)、`internal/cacheproxy/{playback,server,redirect}.go`。请求脚本能验证协议和选路，但不能证明 VRC 是否重新访问本地 API、复用旧资源地址或接受返回视频的方式。
- **最少操作**：在已准备好的隔离环境冷播一首，再热播/切线路恢复进度；如仍需覆盖中途接入，让一首先播放再启用接入，观察后续新的游戏动作，结束时恢复直连并触发一次新播放。所需接入操作由 agent 在本轮授权内执行。代理模式只有涉及游戏 HTTPS 透传的剩余风险时补一个代表场景，不按节点/协议做全组合。
- **预期与证据**：实际音画及进度符合操作，能区分本地 API 请求与旧解析资源读取；恢复后新动作可正常直连。共用游戏/服务相对时间线及简短音画反馈；仅本轮触及 hosts 时附前后差异和恢复回执。
- **已有覆盖**：[LIVE-20261015-01](acceptance/live-acceptance-20261015-01.md) 的 CF 冷热、完整缓存及直连恢复反馈正常；这部分无需因本次文档整理重测。旧构建结论不外推至受影响的新实现。升级、导入、缓存文件校验及代理候选穷举转开发验证，不再分别追加“游戏 HIT”。
- **2026-10-19 增量结果**：[本轮报告](acceptance/live-acceptance-20261019-01.md) 在当前产品源码下完成 10946 CF 冷播、同线刷新及 hosts 恢复/停止网关后的 3893 新播放，用户均未见异常。1 GiB 独立存储成功发布并复算正式 MD5 文件；热解析器 HIT 200 有正文、WMF 为 HIT 304，不误记完整热正文传输。仅已开播后接入未复测。

## 全局块调度与有限需求租约

### LA-040：慢网拖动、多播放器与后台竞争

- **依据与必要性**：`internal/blocksched/`、`internal/cacheproxy/{scheduled_download,scheduled_range,block_demands,stream}.go`；[开发验证](validation/block-scheduler-validation.md)、[调度规则](download-concurrency.md)。真实播放器的探测/重连、并发读者及用户观察到的卡顿不能仅由受控 HTTP 断言代表。
- **最少操作**：优先复测历史失败条件下的冷播放和前后拖动，再在同一会话加入同歌预览/正式双播放器及后台预取，取消一个读者或切歌，观察另一个是否继续。单连接限速与总带宽限速分清，不为每个修复分支另开游戏操作。agent 先分析历史证据、准备可控复现和所需采集；不能把未定位的问题反复交给用户重试。
- **预期与证据**：取消一个读者不打断仍有需求的播放；可用带宽恢复后不永久等待，进度与音画恢复；记录起播/Seek 等待及卡顿。低于媒体所需带宽不承诺无卡顿，保留实际瓶颈和恢复结果。当前有限任务在 need-by+30 秒截止后明确失败；同轮观察真实播放器能否重新请求并恢复，不把明确截止与永久等待混为一谈，也不重复验证精确秒数。共用请求/读者时序、针对问题的调度日志及音画反馈；判断游戏卡顿时由 agent 同步采集必要 CPU/帧时间，完成下载时核对文件哈希。
- **失败与已有覆盖**：[LIVE-20261014-02](acceptance/live-acceptance-20261014-02.md) 的 1 Mbps 交互未恢复、[LIVE-20261015-01](acceptance/live-acceptance-20261015-01.md) 的聚合慢网冷播卡顿/双播放器 Seek 长等待继续跟进；[LIVE-20261015-02](acceptance/live-acceptance-20261015-02.md) 日常播放及 38 文件校验正常，没有复测上述失败。本项汇总原 LA-008/020/037/038/039 的相关游戏行为，不因 A1–A8 或调度重构的自动检查通过就关闭失败。
- **2026-10-19 增量结果**：[本轮报告](acceptance/live-acceptance-20261019-01.md) 中，1343/1344 在聚合 1 Mbps、0 GiB 条件下实际返回截止 504，播放器随即重新 GET，恢复带宽后起播；1344 多个读者共享任务，关闭预览未报告正式播放异常。6254 尾部响应截止后自动 Range 续读；Seek 目标实际已缓存，不能替代独立慢网冷 Seek。下一次由 agent 先用日志确认目标尚无块、清除旧预览干扰，再只做一次该目标的拖动/恢复；不宣称所有历史慢网根因均已解决。
- **已分流**：16 路额度、250 ms 增路、固定 M/下载截止边界、租约精确时间、唯一使用容量 4096/2867 块、候选耗尽、错误 Range、MD5、竞态和文件清理由开发测试/隔离进程验证，不再要求游戏逐条证明。原 6/4 路、每视频固定 worker、1 秒宽限等旧策略不再适用；历史依据保留。

## LA-041：队列交接与真实游戏事件

- **依据与必要性**：`internal/vrclog/`、`internal/console/queue.go`、`internal/cacheproxy/{queue_timing,demand,block_demands}.go`；[队列机制](queue-prefetch.md)。真实游戏的队首消失、日志落地、播放器 GET 与开播间隔不能由人工构造快照证明。
- **最少操作**：复用 LA-040 的慢速下载，让队首自然切入正式播放；利用同轮热缓存场景作对照。对尚缺的来源退出覆盖，在游戏中重排/删歌或离房，核对没有旧队列复活；同一动作覆盖相关需求、续传与交接，不按旧编号重复。
- **预期与证据**：歌曲与 GET/开播关联正确，交接没有导致错误撤销/重复下载或永久等待；退出来源后不复活旧队列。agent 关联队列快照、应用发现时刻、正式 GET 与游戏开播/音画反馈，区分预览，注明轮询和日志缓冲误差；记录交接是否在接手前到期及其实际影响，不预设实际接手必然早于交接到期，不把未开播样本填成零。
- **已有覆盖**：[LIVE-20261015-01](acceptance/live-acceptance-20261015-01.md) 有三笔交接观测；[LIVE-20261015-02](acceptance/live-acceptance-20261015-02.md) 的 37 个正常网络样本中，消失→正式开播为 9–11 秒，消失→候选 GET 为 0.962–2.371 秒。保留这些结论，只补慢网/租约及未覆盖事件；不重新收集同类 37 个样本。LA-043 的设置与窗口计算转开发验证，实际提前准备效果在本场景观察。
- **2026-10-19 增量结果**：[本轮报告](acceptance/live-acceptance-20261019-01.md) 覆盖 6254 下载途中接手、3261 全临时块自然交接、8771 删除后取消且不复活。两次队首消失→候选 GET 约 1.366 / 1.110 秒，→video-start 均 10 秒，交接租约均 20 秒。8935 完成后无 GET 停留 130.420 秒，13 次滚动、21 块各下载一次，随后全量复用；没有提前回收或重复取块。剩余为离房真实事件，精确迟到解析竞态仍由开发测试负责。
- **2026-10-20 时间观测**：[本轮报告](acceptance/live-acceptance-20261020-01.md) 分别采集手动、自然结束及手动热缓存对照各 3 笔。队首日志首次可读→首个同视频 GET 约 0.8 秒，九笔采样边界合计 0.736–0.907 秒；SWD 每 3 秒轮询发现变化→GET 为 −1.534～+0.690 秒，6/9 笔 GET 已先到。手动/自然的播放器热缓存对照未显示超过采样误差的差异；不把文件可读时间等同于游戏事件生成时间；测量当时未修改租约，后续策略调整见下项。离房剩余场景及历史结果保留。
- **2026-10-20 策略调整**：经确认，队首交接改为与 GET 相同的 `E + 2 秒 / N + 2 秒`，见[现行规则](download-resource-design.md#常规播放交接与同块需求重新接入)；历史 20 秒租约下的实机结果继续保留。固定到期、原时钟平移、延迟通知、共享需求与保护由开发回归验证；最新九笔时序样本不覆盖冷回源、慢网或多人。下轮已有 LA-040 慢网操作中合并一次下载未完成的队首接手，由 agent 关联退出、GET 与取消/重取，判断缩短空档是否影响真实播放；无需重做正常网络九笔采样或另立台账项。离房场景保持待验。

## LA-011：多人中途加入

- **依据与必要性**：[历史未覆盖项](acceptance/live-acceptance-20261007.md)。多人同步、非 owner 的进度追赶与房间实际播放状态无法由单人或 HTTP 请求替代。
- **最少操作**：在合适实例中以非 owner 中途加入正在播放的歌曲，确认追上实际进度并持续播放；可复用本轮 LA-025 的接入环境，无需额外切全套线路。
- **预期与证据**：同步进度正确、音画持续，记录实际角色、同步/播放事件、服务请求及用户反馈。实例暂不可用时仅保留此场景，不阻塞其他开发；不在材料中保留玩家/房间身份。
- **状态**：2026-10-19 用户确认无现成多人实例，本轮未测；早期其他版本的通过记录不自动证明当前相关实现。

## 零容量缓存与独立不限选项

### LA-047：零预算下的实际播放保护

- **依据与必要性**：`internal/cacheproxy/{retention,local_protection,block_reclamation,local_blocks,cache}.go`；[容量验证](validation/cache-capacity-validation.md)、[块资源与截止验证](validation/block-scheduler-validation.md)。引用/保护逻辑可自动验证，剩余风险是实际播放器断开/重连和真实队列事件之间的空窗是否触发过早回收。
- **最少操作**：agent 提前在隔离配置应用零预算并验证生效；复用 LA-040 的冷播、拖动和 LA-041 的预取→正式播放，在保护有效时重播，随后退出相关需求并等待回收。
- **预期与证据**：实际播放/交接不因误删而中断，保护有效期间复用已有内容，最后保护释放后可回收；共用音画、请求/命中、引用释放与文件变化记录。无需在游戏里重复设置输入、CLI、重启、正数/不限矩阵或异常进程清理。
- **状态**：[LIVE-20261019-01](acceptance/live-acceptance-20261019-01.md) 的实际重连/前后拖动、共享与队列保护通过；两组临时块在原进程中分别于最后 GET 后约 62.162 / 62.622 秒采样到全部回收，符合 2 秒交接与 60 秒尾期。另以独立 1 GiB 冷播验证正式 MD5 文件发布，没有把零预算成功代替持久化成功。本组已覆盖操作无需重复；未缓存慢网 Seek 共用 LA-040。精确时间边界仍依赖[开发验证](validation/cache-capacity-validation.md#自动检查)。
