# 实机验收机制

项目将“开发完成”和“实机验收通过”分开管理。新功能完成自动检查后，登记到[待验收台账](live-acceptance-backlog.md)，积攒至用户安排的下一轮集中验收，不要求每个功能完成后立即打断开发进行实测。

## 开发完成时

1. 新增稳定编号 `LA-001` 等，不重用历史编号。相关修复可以更新原项，但保留原报告及失败记录；已通过项发生行为变化后重新置为待验收，注明新的代码依据。
2. 写明功能、提交/PR/实现文件、已有自动检查、实际操作步骤、可判断的预期结果、证据需求及环境条件。大功能拆成可独立判定的项目。
3. 在功能变更中一并交付台账更新；完成说明写“开发完成，待实机验收 LA-xxx”。自动化、本机无界面子进程和真实上游脚本结果不能替代 VRChat、托盘或跨用户操作的实际结果。
4. 纯文档、测试、开发工具修改不涉及产品行为时，说明不适用原因即可。修复、重构、性能或持久化变更只要影响实际使用，也要登记。

## 下一轮开始时

从台账选择本轮编号，复制[报告模板](live-acceptance-report-template.md)为 `docs/live-acceptance-YYYYMMDD-NN.md`，批次 ID 使用 `LIVE-YYYYMMDD-NN`。同一天多轮使用不同序号。

冻结本轮范围、源码完整 SHA、工作区差异、可执行文件及发行包 SHA256。若存在未提交代码，留存可还原的补丁及其哈希；中途换构建需分段记录版本和证据，不能混用结论。填写 Windows/游戏版本、网络与代理条件、隔离存储、操作者角色和场景前置条件。隐私时间采用场景相对时间并说明零点；需要跨日志关联时保留共同基准或偏移。

将选中项置为“本轮验收中”，其余保持积攒。至少检查接入、冷/热播放、切歌/跳转、队列、退出及 hosts 恢复等相关基础回归；本轮未覆盖的基础场景需明确列出。具体操作参考[复现手册](testing-runbook.md)和各功能验证文档，历史域名与旧版本步骤不能直接作为当前配置。

## 每轮必须交付

| 交付物 | 必需内容 |
| --- | --- |
| 报告 `docs/live-acceptance-YYYYMMDD-NN.md` | 批次、版本/哈希、环境、范围、逐项步骤/预期/实际、用户反馈、结果、限制、遗留问题、清理回执 |
| 证据目录 `docs/evidence/live-YYYYMMDD-NN/` | 精简脱敏日志、截图或录像链接、请求及文件校验；每份证据有 ID、来源和采集方式，报告引用具体文件/事件/位置 |
| 目录内 `manifest.json` | 批次、源码 SHA、被测 EXE/包 SHA256、每个证据文件的相对路径/字节数/SHA256/来源/脱敏说明；不包含清单自身哈希 |
| 台账与证据索引 | 每项结果、报告链接、失败/阻塞原因和下轮动作；在 `docs/evidence/README.md` 增加本轮入口 |

证据文件哈希按提交后的 Git blob 字节计算，避免 Windows CRLF 与 LF 差异；清单注明 `hashBasis: git-blob`，二进制构建哈希则按实际运行文件字节。也可将证据固定为 LF 后计算并核对 Git blob。大体积媒体可存入批准的持久附件位置，但仓库必须保存可访问链接、哈希和脱敏摘要，不接受仅在当前聊天或临时目录中的唯一证据。

每项至少包含实际操作与观测依据。播放体验结合用户音画反馈、游戏播放事件和服务请求/落盘结果；托盘、条款等 UI 场景保留截图或明确的人工操作记录；文件生命周期保存前后状态和校验。HTTP 200、单条成功日志或自动测试通过都不能单独证明实机通过。无法取得证据时记录阻塞或未测，不补写推测的通过结果。

原始资料放 `artifacts/acceptance-evidence/<批次>/` 等忽略路径，仅本地留档。提交材料遵守[证据脱敏规则](evidence/README.md)：去除用户名、房间标识、私人路径、完整签名 URL、代理密码、条款凭据等。必须在删除临时环境前完成证据提取和校验；报告记清 hosts 恢复、进程/监听退出、挂载解除、测试数据处置及保留材料。清理失败也要记录并跟进，不能写已完成。

## 结果与收尾

台账使用：**待验收 → 本轮验收中 → 通过 / 失败 / 阻塞 / 未测**。失败修复后回到待验收；阻塞解除或未测项排入下一轮。失败、阻塞、未测均属于未结项，始终留在积攒列表，不随批次结束消失。

一个项目只有全部验收条件实际满足且证据齐备才通过。部分通过应拆项或保持未结项，在报告说明已覆盖部分。取消或中断的一轮也提交部分报告，未执行的项标为未测并说明原因。报告中的逐项状态与台账必须一致。

报告、脱敏证据、manifest、台账和索引在同一验收变更中交付，缺少任一项不得宣布本轮材料完整。执行 Git 提交时一起提交；若当前未授权 commit/push，则准备好可审查的文件并明确“未提交/未推送”。不得只提交口头结论或只保留忽略目录中的日志。

每轮收尾说明本轮通过范围、失败/阻塞/未测项及下轮积攒项目。通过仅证明指定构建和场景，不自动等于全部发布验收完成。历史报告不覆盖重写，复测通过仍保留原失败报告。
