# 视频缓存优先级与上限

控制台也可通过[缓存明细管理](console.md#缓存明细管理)手动删除选中的文件。手动删除复用资源删除预留与容量记账，并保留全部歌曲资料和统计；文件身份或歌曲关联与确认快照不一致时拒绝。活动引用、完整队列、离队宽限及独立校验均受保护。若队列新增的资源已被预留删除，队列更新在锁外等待该资源删除结束后生效，等待可由队列取消信号中止；控制台以独立更新锁串行执行队列快照、保护、初始化与清空，等待时不持有控制台状态锁；无关资源的删除不阻塞队列更新。关闭 CDN 不等于解除下载与队列保护。

控制台「视频缓存上限（GiB）」支持两位小数，0（默认）表示不限；停止 CDN、队列和批量任务后保存，下次启动 CDN 或下载任务时生效。命令行使用 `-max-cache-bytes`，单位为字节，负数拒绝启动。旧配置缺少此字段时保持不限。

上限只计算统一存储 `videos/<64位资源指纹>.mp4` 的文件长度，每个版本只有一份正式视频。数据库、其他文件和符号链接不删除。此值是保留视频容量，非整个磁盘的硬配额；数据库和下载临时文件不计入。

## 排序规则

直接复用 SQLite 的 `resource_usage.demand_count` 和 `last_demand_at`：

`优先级 = ln(1 + 去重需求次数) / (1 + 距离上次需求的天数 / 7)`

- GET 按既有 30 秒窗口同一资源跨 Host 去重；统计代表观察到的请求需求，并非确认完成播放。HEAD、预缓存不增加热度。
- 七天衰减尺度抑制长期未使用的历史热门视频；对数频次避免累计次数长期支配排序。
- 无需求记录的视频得分为 0，优先淘汰。
- 同分时先淘汰曲库歌曲 ID 较小的缓存，ID 按数值比较；同一资源关联多个歌曲时取最大 ID，未知歌曲 ID 按 0 处理。ID 也相同时再按需求时间（无需求则文件修改时间）、路径稳定排序。
- 从文件名读取资源指纹并查询资源热度，不将视频编号当作曲目 ID；不同资源分别统计。

## 执行与并发

控制台的当前版本确认遵循回源线路设置：固定 CF 或 HKG 时，仅向该线路查询。Auto 以 HKG 为版本权威（与预缓存首选线路一致），不会按下载完成顺序、测速结果或哈希推断哪个版本更新。两路版本不一致时，只有 HKG 返回的版本可替换已有当前版本；HKG 确认失败时保持原映射，不回退到 CF 确认。尚无当前版本时，首个校验成功的版本建立映射。离线降级使用此映射；未获确认的其他版本可完成本次播放，但随后会按历史版本清理，即使容量不限。因此 Auto 在两路不同步时可能重复下载 CF 版本，需要长期保留 CF 版本时应固定 CF。

设置上限后，启动缓存引擎时扫描视频容量，之后在发布、删除视频时更新内存中的文件清单和总字节数。普通缓存命中及引用释放不再扫描目录。发布视频后若已知超限，会通知单个后台任务；歌曲版本映射提交及最后一次引用释放也会唤醒该任务，检查并清理被取代的历史版本，即使容量不限也如此。后台任务合并重复的清理请求。每五分钟重新扫描一次，校正外部新增、删除或修改的文件；扫描期间发生的内部发布、删除优先于扫描结果，避免容量记录被旧结果覆盖。

未超限（含恰好等于上限）不等待统计落盘、不读取热度数据库、不排序；历史版本清理仍需查询歌曲归属及当前版本引用。超限时先排空已接受的统计事件，再按低到高顺序清理到上限。目录扫描、数据库查询与事务、排序和文件 I/O 均不持有全局播放引用锁。删除前在锁内复查引用并预留该资源，随后在锁外检查文件和执行删除，最后加锁更新容量记录并解除预留。预留期间仅同一资源的新引用等待，其他资源的引用保护和释放不受该文件 I/O 阻塞。历史版本清理还会检查查询期间歌曲映射是否发生变化，若已变化则延后重查，避免使用过期的查询结果删除文件。

完整待播队列中的已有缓存独立于热度获得保护，包括前三首预下载范围以外的歌曲。预下载在持有资源引用、启动或加入共享下载之前登记内存中的歌曲资源关联；即使下载期间移到第四位导致等待任务取消，共享下载完成后仍受完整队列保护。此内存关联不会提前确认或持久化当前版本。容量不足时先清理未受保护的普通缓存；受保护缓存本身超限时允许暂时超过预算。歌曲离队、队列清空、换房或停止监听后解除队列保护，并通知后台回收。队列日志不提供可靠的播放结束信号；离队时仍在响应的资源由播放请求自身的引用继续保护。

正在响应、校验或下载的资源使用引用计数保护；普通低优先级文件仍被占用时延后删除，不会因此改删更高优先级的视频。最后一个使用者结束后通知后台重试；关闭引擎时等待所有使用者结束，解除队列保护，并完成最后一轮清理。

单个视频大于上限仍可播放或供队列预缓存，所有保护解除后不再长期保留。下载补齐单独执行容量准入：已有视频及并发下载预留共同计入预算，剩余预算不足以容纳下一首完整视频时停止，并提示前往设置调大预算后重试；不会为补齐主动淘汰旧视频腾出空间，也不会循环使用本轮被淘汰视频释放的预算。0 表示不限。播放和队列预缓存保持按需下载及淘汰规则，因此与播放并行时，补齐的视频之后仍可能被淘汰；预缓存成功表示完成校验和发布，并不保证一直保留。临时文件及受保护的视频可能令实际占用暂时超过上限。

下载补齐的预算停止不打断已获准曲目的线路回退。同资源回退复用原预留；不同版本重新检查容量，失败版本未发布的预留可释放。回退版本超出预算时保留此前的下载错误，计入失败，并注明「回退受容量预算限制」，同时停止接纳新曲目。

删除失败记录 `cache_eviction_failed`，下次清理重试；实际删除记录 `cache_evicted`，暂不能满足上限记录 `cache_limit_deferred`。数据库无法打开时引擎启动失败；运行中查询失败时本轮不删除，保留错误日志。保留需求统计，不因删除视频丢失历史热度。

存储根目录由操作系统文件锁独占，不允许两个引擎同时写入。容量不限时不执行容量淘汰，但仍会在版本替换、最后一个版本引用释放及重启时清理被取代的视频。

## 验证

自动化测试覆盖衰减/频次排序、无需求预缓存淘汰、单一视频存储计量与版本隔离、启动清理、元数据及未知文件保留、引用计数保护、低优先级占用不挤出热门视频、活动 HTTP 响应保护、超大视频完整播放后清理，以及控制台配置持久化和负数拒绝。并发回归测试还覆盖数据库连接被占用时引用保护和释放不被阻塞、清理查询等待期间新增引用仍受保护，以及删除预留仅阻塞同一资源的新引用。

以下为旧存储结构的历史实机结果，不代表当前结构已重新完成实机验收。`c69e844` 的[联合实机验收](release-acceptance-20260925.md)将五首真实视频的隔离测试库设为 0.23 GiB：实际占用从 521,956,088 降到 220,334,586 字节，先淘汰未播放的预缓存，再淘汰低需求视频；元数据哈希和历史统计保持不变，重启后保留视频播放正常。随后真实批量下载产生的低优先级新视频在完成后被淘汰，未挤出保留的热门视频。

## 请求明细保留期

请求明细默认保留 30 天，控制台「请求明细保留天数」或命令行 `-request-retention-days` 可设置 0～36500 天；0 为永久保留。旧控制台配置未包含 `requestRetentionDays` 时默认 30 天。保存后下次启动 CDN 或下载任务生效。

引擎启动后及运行期间每分钟检查一次 `request_events.requested_at`，只删除早于保留期边界的明细，每次最多 500 条；一批删满后间隔一秒继续处理积压，无新请求时也会清理。清理在统计后台工作线程执行，每批有两秒超时，失败记录 `usage_cleanup_failed` 并在一分钟后重试。关闭时排空已接受的统计，不等待历史积压清理完毕。

`resource_usage` 的累计 GET、去重热度及时间信息长期保留，歌曲资料与版本映射不受影响。清理释放的 SQLite 页面会被后续写入复用，不自动执行可能长时间阻塞的全库 VACUUM，因此已有数据库文件不会立即缩小。保留期不是数据库字节硬上限，保留期内的高请求量及长期汇总仍需磁盘空间。
