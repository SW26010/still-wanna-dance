# Issue #20：CF 上游并发初筛（2026-10-14）

**这条实测 CF 路径上，1 MiB 分块从一路增加到三路有明显收益，四路相对三路仍有收益。单个长 Range 也很快，不能把一路小分块的速度解释成 CF 的单连接带宽上限。**

这是单资源、单直连地址、单时段的开发实验。没有修改产品默认三路、全局 6/4 请求预算或块大小，没有执行真实游戏、hosts 操作或完整缓存引擎验收；LA-037 继续待验收。

## 方法与控制

- 产品基线 `d9ef49852f4f9b8a9c3a07c9827a2c0a41f5eb53`；[实验工具](../../experiments/cf-concurrency/README.md) 单独提交为 `0cfaa58`，只增加开发工具。Go 1.25.0 / Windows amd64，`CGO_ENABLED=0`、`no_easytier`、`-trimpath`。最终分析脚本的图表布局修正与本报告一并提交。
- 从当次 HTTPS API `node=cf&id=1343` 获取有效资源，资源大小 32,867,177 字节，实际域名 `play.udon.dance`。独立 DNS 发现后，固定连接地址 `104.26.4.28`，保留 Host/SNI 和证书验证，不自动选路/切换。未配置显式代理，但不能据此排除机器或网络的透明代理/TUN。
- 原计划区间 32 MiB 大于该视频，改为所有组都下载相同的前 **30 MiB**。比较 1/2/3/4 路 1 MiB Range，以及单路连续 30 MiB Range。
- 复用产品的 `upstreamrequest` 固定通道 Transport。第一阶段直接测 HTTP 区间，不调用整文件缓存发布、spool、播放调度或请求预算。最多四路且无其他视频，因此不测试全局额度竞争。无实验层重试；标准库透明重试未单独观测。
- 每次建立新连接池，建连计入耗时。先用长 Range 预热 CDN 内容并保存每 MiB 的 SHA256；随后各组验证 206、精确范围/总长度、identity 编码、强 ETag、正文终止和逐块哈希。文件不写入常用缓存；部分区间 SHA256 不等于整文件 MD5 验证。
- 档位交错运行，组间休息两秒。顺序见工具文档；四档分块顺序平衡，长请求插在不同位置。没有强制 CDN 冷缓存、缓存破坏参数或手工更换资源域名。

## 干扰处理与保留规则

首次实网测量启动后，工具 vet 曾并行执行，`run-01` 第 1 轮存在本机负载重叠。观察到该问题后，**在补测开始前确定保守排除整个第 1 轮**，并公开说明会补跑；没有据各档快慢选择性排除。它的五组数据完整保留，不进入主汇总。

完成静态检查后，`run-02` 用相同资源、地址和顺序补跑第 1 轮。该版本只增加 `-rounds` 数量限制，传输、读取、计时、哈希和顺序未改变；两版二进制身份保存在检查摘要。主分析由 `run-01` 第 2/3/4 轮和 `run-02` 第 1 轮构成，共四个配对。两次预热内容参照完全一致，预热不计入性能样本。

保留一路的 44.55 秒慢样本；它没有 HTTP 或校验失败，不能仅因慢就删除。所有主样本没有与编译、静态检查、其他实验测速并行；未对整机其他进程流量作网卡级监控，因此不是封闭网络条件。

## 结果

下面的耗时与吞吐分别取四个样本的中位数；加速比先在同一轮相对一路计算，再取中位数，因此不等于直接相除表中两列中位数。

| 方式 | 区间耗时中位数 | 吞吐中位数 | 吞吐观测范围 | 同轮相对一路加速比中位数 |
| --- | ---: | ---: | ---: | ---: |
| 1 路 × 1 MiB | 20.65 s | 1.45 MiB/s | 0.67–1.68 | 1.00× |
| 2 路 × 1 MiB | 10.00 s | 3.00 MiB/s | 2.87–3.66 | 2.26× |
| 3 路 × 1 MiB（当前策略） | 6.75 s | 4.45 MiB/s | 3.93–4.79 | 3.10× |
| 4 路 × 1 MiB | 5.49 s | 5.47 MiB/s | 5.10–6.12 | 3.83× |
| 1 路 × 30 MiB 长 Range | 5.02 s | 5.98 MiB/s | 5.77–6.74 | 4.29× |

四路相对三路的同轮吞吐增幅分别为 **35.4%、20.9%、19.8%、27.8%**，中位数 **24.3%**。四个配对方向一致，说明在这次条件下三路到四路的增益尚未消失；仅四个配对，不报告稳定 p95、显著性结论或全天稳定增益。

完整配对耗时如下，单位秒：

| 轮次 | 一路 | 二路 | 三路 | 四路 | 长 Range |
| --- | ---: | ---: | ---: | ---: | ---: |
| run-01 / 2 | 44.55 | 9.92 | 7.63 | 5.64 | 5.10 |
| run-01 / 3 | 19.81 | 10.46 | 7.11 | 5.88 | 4.45 |
| run-01 / 4 | 21.50 | 8.20 | 6.40 | 5.34 | 5.20 |
| run-02 / 1（补测） | 17.85 | 10.08 | 6.27 | 4.91 | 4.94 |

实际请求峰值每次均达到设定的 1/2/3/4；相应时间平均在途请求数的中位数约为 1.00/1.93/2.94/3.82，排除了“增加 worker 但没有实际形成并发”的情况。

包含预热、排除轮次和补测，共 **27 组、607 次实验层 HTTP Range 请求、810 MiB 接收正文**；另有 API 请求和 1 KiB 视频预检。27 组全部成功，无观测 HTTP 失败或哈希不一致。607 个测量请求的协议/缓存/节点均为 **HTTP/1.1 / HIT / SEA**，响应 Server 均为 cloudflare。上述字节数不是网卡流量，未包含 TLS/TCP、传输重发、API 及事后安装绘图库的流量。

## 能解释什么

1. **并发对当前小分块请求有用。** 各主轮次中二、三、四路均比一路快，四路也均比三路快。这支持 #20 的并发方向，但不证明用户播放等待按相同比例缩短。
2. **串行小分块存在可重叠的响应等待。** 一路的每请求响应头耗时中位数约 224 ms，三、四路也约 220 ms；一路各轮“响应头前时间 / 请求总时间”的中位数约 44%。这里包括必要的建连/服务端等待，不能直接当作纯网络 RTT。
3. **反复重建连接不是主要解释。** 一路主样本的 120 次请求中 116 次复用了连接，即每轮首请求建连、后续复用。即使复用连接，串行请求仍存在响应等待。
4. **不能把所有差异归因于响应头等待。** 44.55 秒慢样本中，偏移 10 MiB 的一个块耗时 8.84 秒，响应头只占 0.47 秒，余下时间落在正文读取与校验/关闭阶段。没有抓包或拥塞窗口数据，不能断言具体为丢包、拥塞或服务端限速。
5. **长 Range 是关键对照。** 同一资源和路径上单连接长请求中位吞吐约 5.98 MiB/s，接近或超过四路小分块。这不支持把一路 1 MiB 分块的约 1.45 MiB/s 当成固定单连接上限；请求粒度与传输连续性值得独立研究。长 Range 没有验证播放让位、Seek 或首块可读语义，不能据此把产品直接改成整段下载。
