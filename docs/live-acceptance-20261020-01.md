# LIVE-20261020-01 队首消失到视频 GET 的实机测量

## 结论与口径

本轮只回答“观察到日志队首消失，到收到该视频 GET 的时间间隔”。共 9 笔目标交接，分别为手动下一首 3 笔、自然结束 3 笔、补充的手动热缓存对照 3 笔。

**从游戏队列日志首次可读起算，首个同视频 GET 典型约 0.8 秒；九笔的采样区间合计为 0.736–0.907 秒。** 这里的 GET 是实际向本地播放入口请求视频正文的首个解析器候选请求，不是预缓存的上游请求。之后另有可由 NSPlayer/WMF User-Agent 识别的播放器 GET，见逐笔证据。

**从 SWD 实际写出 `queue_updated`、发现队首消失起算，首个 GET 为 −1.534～+0.690 秒；9 笔中 6 笔 GET 先到。** 负数表示真实顺序是 GET 在前、轮询发现队列变化在后，不是等待时长为负。不能在 SWD 发现时刻上再固定加 0.8 秒。

| 场景 | n | 日志首次可读→首 GET：区间中点的中位数 | 该中位数的采样边界 | SWD 发现→首 GET：最小 / 中位 / 最大 |
| --- | --- | --- | --- | --- |
| 手动下一首，播放器首次读取 | 3 | 0.841 秒 | 0.783–0.898 秒 | −1.534 / −0.134 / +0.327 秒 |
| 当前视频自然结束，播放器缓存命中 | 3 | 0.803 秒 | 0.748–0.859 秒 | −1.125 / −0.124 / −0.113 秒 |
| 手动下一首，播放器缓存命中 | 3 | 0.815 秒 | 0.757–0.873 秒 | −1.330 / +0.540 / +0.690 秒 |

后两组使用相同目标视频，播放器均返回 304；中点中位数仅差 0.012 秒，小于约 0.11 秒的采样间隔，不能据此判定两种交接存在实际差异。每组仅 3 笔，不提供总体分位数、最坏情况保证或新的交接租约建议。所有目标请求均已在 SWD 预缓存中命中，本轮不覆盖冷回源、慢网和多人。

## 时间误差与采样

- SWD 原实现每 **3 秒**增量读取日志，本轮没有改变轮询周期或产品代码。`queue_updated` 是应用处理队列变化的记录，不是游戏产生变化的时刻。
- 独立采集器要求每 100 ms 检查一次文件；实际相邻检查间隔中位数 **108.913 ms**，P95 **110.762 ms**，最大 **113.958 ms**。每条完整队列行保留“前一次检查开始”与“本次完整行读到”的时间，给出首次可读的保守区间，不把配置的 100 ms 当成实际精度。
- 游戏日志原时间戳只有整秒。如果队首日志时间戳为 S，则其记录时刻处于 `[S,S+1s)`；直接计算 GET−S 有约 1 秒的量化不确定性。采集器测的是**文件可读时间**，不能消除或反推游戏内部的日志缓冲延迟。
- `request_started` 在地址解析后才记录。GET 到达以同一请求的 `request_finished.time − elapsed` 反推，保留日志小数和纳秒耗时；这是近毫秒级的到达估计，仍包含日志调用开销。目标请求均为本地 HIT，没有用解析完成时刻冒充到达时刻。
- 队首消失按相邻游戏队列快照中旧首项不再存在判定；手动/自然分类分别核对游戏的按钮事件与 `OnUSharpVideoEnd`，并通过内容 MD5、请求 ID、同次播放事件及原始行号关联 GET。歌曲 ID 相同但时段不同的重复播放分开处理。
