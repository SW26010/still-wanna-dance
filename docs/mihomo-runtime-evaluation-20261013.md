# Issue #14：完整运行时 B/C 代码评估与实施设计

**建议下一阶段采用 C（独立完整核心 + 固定认证 SOCKS5）作为唯一正式 Mihomo 执行路径。B（完整核心内嵌 + 内存入口）已经通过本轮有限可行性验证，应保留其对照证据。** 选择 C 的工程理由是核心故障可独立收敛、无需承担主进程全局运行时的卸载约定，以及本轮真实资源冷请求更稳定；代价是更高总内存、额外进程/入口/临时明文文件和组件交付管理。真实样本数量有限，不把此次差异解释为 B 的固有网络性能缺陷。

这是评估和下一阶段设计，**正式产品仍为 A，尚未迁移、发布或通过实机验收**。C 的生产生命周期、安全门禁与发行工作仍然必须实现，不能把 PoC 检查数量当作发布许可。

### 内存入口不能直接冒充旧拨号契约

固定源码中，[`inner.HandleTcp`](https://github.com/MetaCubeX/mihomo/blob/v1.19.32/listener/inner/tcp.go)先创建内存管道、异步调用 tunnel，然后返回。它没有 Context，远端错误在后续读写发生。[完整 tunnel](https://github.com/MetaCubeX/mihomo/blob/v1.19.32/tunnel/tunnel.go)使用内部拨号超时；关闭本端并不立刻终止所有尚在建立的连接。本次通过导出的 `Tunnel.HandleTCPConn` 包装通用操作计数，没有接管内部协议 socket。

**首次排队版真实失败**：每轮请求虽已取消，Transport 仍可保留脱离原请求的 Dial；32 个槽位后继续累积等待任务，goroutine 从 35 增至 195，观察窗结束仍未排空。改为满额立即失败解决积压；随后 40 路正常并发触及 32 上限，最终将实验容量设为 64，保持原 40 路并发检查。容量是独立运行策略，不写进节点身份或 K。两个失败轮次和二进制哈希均保留。

生产若选 B，`network_mihomo.go` 当前“按 Dial 错误尝试下一节点”的原始回退不能原样使用；应在请求/Transport 层做有界候选回退，并明确非 HTTP 调用的连接确认语义。不得照抄[上游 HTTP helper](https://github.com/MetaCubeX/mihomo/blob/v1.19.32/component/http/http.go)中内存入口失败后普通拨号的回退。

### 同进程只适合一个受控运行时

本轮用 `executor.ParseWithBytes → executor.ApplyConfig`，执行与 `hub.Parse` 相同的完整初始化，跳过本实验不需要的外部控制面。B 不与旧 `mihomo.New` 共存，不重设 SWD 的 DoH；SWD 日志使用 `slog`，核心自身还会初始化全局 logrus，不能推广为对任何宿主都无副作用。

实测 [`executor.Shutdown`](https://github.com/MetaCubeX/mihomo/blob/v1.19.32/hub/executor/executor.go)后仍能请求成功；它不能替代代理/provider/业务连接的关闭。补充关闭和排空后操作为 0，但核心全局对象仍保留。B PoC 明确禁止同进程二次初始化。当前 Console 的网络对象随整个 Console 生命周期存在，保存后程序重启的产品约定可以适配这个限制；测试中频繁创建多个 Console、未来热替换和不同用户上下文则需重构为隔离进程测试或共享单实例所有权。不能通过反射、`go:linkname` 或协议分支模拟卸载。

## 对等成本与选型

3 轮同节点、目标、负载的合成 SS 回环中位数：

| 指标 | B 完整内嵌 | C 完整独立进程 |
| --- | ---: | ---: |
| 128 MiB 正文吞吐 | 740.8 MiB/s | 330.5 MiB/s |
| 空闲总工作集 | 19.9 MiB | 34.8 MiB |
| 每 128 MiB CPU 时间 | 0.1875 s | 0.28125 s |
| 就绪耗时 | 29.3 ms | 616.4 ms |

C 启动包括进程与控制 API 轮询；两种模式排除服务夹具、计入各自驱动。驱动不是完整桌面程序。CPU 量化和本机调度影响小样本，详细值保留；不宣称 SOCKS5 是最优协议，也不把此表视为真实网络速度。

真实相同视频的三轮对照中，C 的 6 个冷首响应约 **410–446 ms**；B 约 **413–5451 ms**，出现 **2281 ms、5451 ms** 尾部。全部请求均成功、相同区间哈希一致。热请求双方多在约 130–148 ms，B 另有一轮约 413–467 ms。网络、DNS、核心调度与远端状态均可能影响结果；尚未定位因果，不用 6 个样本推断长期分布。

按 issue 的既定定性规则，本轮可确认 B 原生兼容且不需逐协议补丁、有限取消负载可收敛；其资源优势成立于该夹具。工程上仍建议 C：协议核心异常不会一起终止缓存/控制台，生命周期和独立升级边界更明确，且真实样本暂未显示 B 的播放首响应优势。接受 C 的本机中转、约 15 MiB 额外空闲工作集和临时文件管理成本。**这是一项可审查的选型建议，当前没有执行正式替换。**

仅在以下条件变化时重新打开 B/C 决策：明确把单 EXE/最低资源开销设为优先目标；或对等复测证明 C 本机中转已成为真实业务瓶颈，并能接受 B 的进程级故障、唯一全局核心与请求级回退改造。上游版本/导出 API/通用能力集合变化则必须做回归，不自动改变选择。复杂 K 轮换和自动订阅更新不进入此门槛。

### 受管核心最小状态机

`Stopped → Starting → Ready → Retiring → Stopped`，任意启动/运行错误进入 `Failed`；`Failed` 不发布可执行代理候选。保存节点只改变 saved 配置，active 核心不热更新。停止网关或队列不等同于销毁全局网络配置；按现有 Console 所有权管理。

1. 解密并验证节点，选出最多 K 个活跃 ID；备用节点只保存在受保护快照和 membership 中。
2. 校验核心固定版本、构建身份和可信路径。每代创建随机运行目录，先设 CurrentUser/SYSTEM ACL，再写最小 provider；认证和主配置通过 stdin，禁止继承代理/SAFE_PATHS/配置覆盖环境。
3. 生成认证 `127.0.0.1` SOCKS 入口，每入口固定单成员组；空组 `REJECT`，全局 `MATCH,REJECT`。关闭所有自动更新/健康巡检/TUN/系统代理、通用监听、嗅探和配置继承。DNS 使用受控方案且不读系统 hosts；不能把节点服务器显式指向自己的网关入口。
4. 挂入 `KILL_ON_JOB_CLOSE` 的 Job 后才恢复子进程执行。验证控制面认证、版本、实际监听、provider 数量、单成员映射和固定选中项。`-t` 成功或 API ready 单独都不能发布。健康探测由 Monitor 负责，启动不冒充节点在线。
5. 同一代只创建一次 Pool。核心退出时先撤销代理候选并终止本代请求/Transport，按 auto/强制代理现有政策处理。不对未完全退役的端口发布新身份；不做无限自动重启。
6. 正常退出先停新业务、取消在途请求并关闭连接，再有限等待核心退出、关闭 Job、清理已知 provider/主配置和本代目录。异常残留在下次启动按受管标记清扫；不能删除未知目录或另一活跃实例的材料。失败清理有状态，不宣称“磁盘绝无明文”。

C 的入口也应有独立于 K 的连接/请求预算；本次观测到 192 个暂留核心握手，说明进程隔离不等于无需资源约束。任务取消、进程退役与容量错误分别记录，不把本机故障伪装成节点健康观测。
