# 测速准备的候选回退验证

本文前半部分记录首轮候选回退修复；后续协议顺序与批内复用见文末补充，现行规则统一以[上游通道](../upstream-channels.md)为准。

2026-10-29，基于 `e42f35bedac0ba840dda4d560a1155246599c81c` 排查直连测速反复提示准备不足。用户反馈连通性三项可用，地址详情中 IPv4／IPv6 均存在成功和失败项。提供的应用日志只记录启动操作，没有测速结束原因，不能单凭该日志确认现场根因。

## 复现与修改

受控回归使用同一候选集合执行真实 Monitor 连通性检查和 Calibration 样本准备：第一条直连地址失败，第二条提供合法清单、播放地址与 Range 响应。连通性三项可用；旧准备流程却返回 `preparation_insufficient`，对可用候选的请求数为 0。只交换候选顺序即可准备 16 个独立视频、2 GiB 元数据，连续复跑保持同样结果。

修复将清单及播放地址准备交给已有 `upstreamrequest.Fetch`，在所选上游内使用有界候选列表。HTTPS 优先、协议回退、最多六次尝试及调用者期限共用原机制；不新增重试计时器或地址族偏好。正式视频计速继续按资源域名固定候选，这次验证不证明所有资源候选或完整测速都可用。现行规则见[上游通道](../upstream-channels.md#测量和推荐)。

补充 `network_calibration_finished` 低频摘要，记录上游、阶段、原因、已准备视频数／大小和实际下载字节，不记录签名地址或凭据。

## 验证与边界

- 先失败后通过的组合回归：`TestCalibrationPreparesAfterConnectivityWithMixedDirectCandidates`；覆盖首个 IPv6 失败／IPv4 成功及反向情况，断言准备阶段未下载视频正文。
- `upstreamstate`、`upstreamrequest` 包回归通过；Console 的 `TestNetworkCalibration*`、`TestNetworkConnectivity*` 定向回归通过；相关包 vet 和差异格式检查通过。
- 原始候选顺序复现修复后两种顺序均通过；健康候选实际收到 17 个元数据请求。
- 本机修复前实网准备 13.44 秒成功，44 个样本；修复后实网准备 22.00 秒成功，41 个样本、2,208,216,215 bytes 元数据。后者观测到 IPv6 超时后 IPv4 返回合法播放地址，亦观测到不同 Kiva 候选的失败与成功。歌曲随机选择、网络时段不同，不能据此比较性能。
- 实网只请求清单和播放元数据，没有执行完整视频测速、启动 VRC、修改 hosts 或用户日常配置。另一台机器的现场结果尚未复测；不将已复现的代码缺陷直接写成现场根因已确认。

原始失败、成功输出及带独立构建标签的诊断入口保留在忽略目录 `artifacts/calibration-diagnosis-20261029/`；用户提供的私有日志不入库。

## 2026-10-29 晚：回退预算与批次重复探路

基于 `783bd0fa` 工作区继续处理“连通性可用、测速样本不足”。现场摘要记录过准备 9 个视频后失败；随后同机诊断复现的是清单阶段耗尽期限，不能把后续请求时间线等同于截图发生时的时间线。

定向诊断确认两个机制问题：HTTPS 候选先全部等待后，最后的 HTTP 虽能收到响应头，却没有足够时间读完清单；单候选也会让 HTTPS 等待用掉全部调用者期限。仅调整尝试顺序后，实网仍在 30 秒准备期限内只获得约 1.28 GB 元数据，因为每首歌曲都会重新等待相同的失败 HTTPS 路径。

共享请求模块改为按候选完成 HTTPS 和获准的 HTTP 回退，删除“最后一个名额特留给 HTTP”的分轮安排；等待预算计入可能的回退。完整正文仍沿用原单次／调用者期限。新增显式的短期 `Session` 复用完整校验成功的路径与协议，普通 `Fetch` 每次创建独立 Session；测速的四个准备 worker 各持一个 Session，结束即释放。候选提供者、证书验证、业务校验、六次尝试上限、30 秒准备期限、16 个视频及 2 GiB 储备要求均沿用原契约。没有新增配置、持久化缓存或恢复轮询。

验证结果：

- 虚拟时间回归先失败后通过：单候选／六候选的 HTTPS 超时后，HTTP 完整清单可在调用者期限内读取；实际准备入口覆盖清单回退及播放地址回退。只调整顺序的中间版本在 32 MiB 视频夹具中分别准备 56／52 个样本后失败，批次复用后在原期限与门槛下通过。
- Session 回归覆盖跨歌曲复用、完整内容非法时废弃偏好并禁止继续降级、主机／路径变化与新批次重新尝试、HTTP 明确升级后继续 HTTPS。原有真实 TLS、正文截断、取消、本地错误、下载独立期限及总尝试预算检查继续通过。
- 原始实网准备入口通过：26.10 秒，44 个视频，2,156,531,745 bytes 元数据。随后独立完整测速通过：总用时 33.51 秒，46 个视频、2,178,082,647 bytes 元数据，下载并丢弃 2,424,718 bytes，单连接与 16 路窗口均完成，保存有效结果。测试期间也运行了本机 Go 检查，因此这些数据只证明功能完成，不用于性能或 CPU 开销比较，也不保证所有公网窗口都成功。
- `go test -tags=no_easytier ./cmd/... ./internal/...`、同范围 vet 通过；`upstreamrequest` 与 `upstreamstate` 整包 Windows race 通过；桌面构建、112 个链接模块许可证核对及最终 EXE 的隔离数据副本启动／资源／条款门禁检查通过。

未启动 VRC、修改 hosts 或写入用户日常数据库；视频测速正文直接丢弃。无需追加游戏专属验收。临时诊断入口有独立构建标签，仅保留在忽略目录；产品代码无调试日志。原始失败、仅改顺序仍失败的中间结果、最终通过及构建证据保留在 `artifacts/calibration-root-fix-20261029/`，此前详细诊断保留在 `artifacts/calibration-screenshot-20261029-220811/`。
