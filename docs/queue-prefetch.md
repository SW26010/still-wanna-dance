# 日志队列预缓存

控制台「房间队列预缓存」读取 VRChat 新增日志，按队列顺序准备前 N 个位置（默认 3）中具有有效曲库 ID 的歌曲。通过独立按钮开启或关闭，不依赖本地播放网关；设置中「控制台启动」的「运行控制台时自动启用房间队列预缓存」（`autoStartQueue`）默认启用。字段缺失或为 null 时采用该默认值，已保存的 true/false 保留，不跟随播放网关或废弃的 `queuePrefetchEnabled` 字段。实际游戏读取本地缓存仍需启动播放网关并完成 hosts 接入。VRChat 日志目录默认每次启动按当前 Windows 用户自动读取 `AppData/LocalLow/VRChat/VRChat`，输入框显示灰色且不可编辑。只有勾选「手动指定 VRChat 日志目录」（`manualLogDir`）后才接受并保存 `logDir`；手动模式不能为空。自动模式保存时将 `logDir` 清空，快照也不保存自动路径。旧配置缺少 `manualLogDir` 时恢复自动模式，包括曾固化的路径；原先确需自定义目录的用户需重新勾选并指定。

设置中的「队列预缓存数量」（`queuePrefetchCount`）可设为 1～100，默认 3；旧配置缺少该字段或设为 0 时使用默认值。数量按队列位置计算，非曲库条目也占位置。运行中也可保存，统一在重启应用后生效；上层最多同时准备两首，网络执行按全局块额度分配。

## 日志检测与频率

参考 dancing-log 本地检出 `c3fa28fa3b68879cb43513bc2cb53f1cc03fa1cc` 的 [vrc_log_watcher.py](https://github.com/SW26010/dancing-log/blob/c3fa28fa3b68879cb43513bc2cb53f1cc03fa1cc/dancing_log/vrc_log_watcher.py) 与 [vrc_log_parser.py](https://github.com/SW26010/dancing-log/blob/c3fa28fa3b68879cb43513bc2cb53f1cc03fa1cc/dancing_log/vrc_log_parser.py)。调查时 GitHub 返回 404，实际参考源码来自本机已有仓库。独立用 Go 标准库实现，没有引入 Python 运行依赖。

- dancing-log 默认轮询 0.25 秒。Still Wanna Dance 每 **3 秒**检查当前日志并从字节偏移读取增量，每 **15 秒**扫描新日志文件；没有新增内容时不解析、不请求歌曲 API。
- 初次启动从现有最新文件末尾开始，等待新的队列同步。不会重放旧会话；在点歌前开启最稳妥。新会话文件从头读取，按 VRChat 文件名中的会话时间选取，旧文件 mtime 改变不会倒退。
- 保留尚未写完的行，完整换行后再解码，支持 UTF-8 跨次写入。单次最多读取 4 MiB，单行最多 1 MiB。截断、替换、读取失败、异常队列行会清空待处理队列。
- 处理 `OnPreSerialization: queue info serialized:` 和 `OnDeserialization: syncedQueuedInfoJson =` 两类 JSON 数组。忽略当前视频 userData 和预览事件；不读取玩家姓名到业务状态，不持久化完整日志。
- 离房、进入新房间、应用正常退出或文件切换时清空待处理队列；日志 5 分钟无新增时也清空，等待新的同步。
- 当前文件新增日志通常在 0～3 秒内被读取，新日志发现通常在 0～15 秒内。游戏本身的日志缓冲、磁盘和系统调度会增加延迟，这不是严格实时保证。

## 下载调度

同一次读取中的快照先合并为最终队列，再通知后台协调器，最多同时准备两首。每首开始前重新检查最新顺序；解析视频地址后也再检查一次，避免接口慢时把已删歌曲提交下载。

使用设置中的回源线路（默认 Auto：主动下载先查询 node=cf，失败后查询 node=nya；参数不约束返回域名；同校验和与大小才允许在同次传输中替换）、大小/MD5 校验和 `Prefetch` 共享下载机制；详见[统一回源选路](console.md#统一回源选路)。歌曲持续处于设定的预缓存范围时，已经准备成功的歌曲不因重复同步而重新请求；离开设定的预缓存范围后清除完成标记，重新进入时再次解析地址并检查缓存，缺失则补下。完整队列中的已有缓存持续受保护，不受热度影响，也不会因移出设定的预缓存范围而失去保护；预算不足时可暂时超限，普通离队（包括空队列快照）后保留 30 秒交接保护，避免播放请求稍晚到达时预缓存已被淘汰；重复快照和 HEAD/探测请求不会延长或提前结束期限。到期主动触发回收，停止监听、换房、日志失效及退出立即清除交接保护，活动播放请求仍由独立引用保护。仅凭队列快照无法区分删歌与开始播放，因此普通删歌和清空也有此宽限期；这不保证整首播放期间始终留盘。失败最早 60 秒后重试，且歌曲必须仍在前 N 个位置（默认 3）。原始日志存在 `songId=-1` 条目，保留位置但不请求曲库。与全曲库下载补齐互斥，补齐期间临时暂停，结束后仅在用户仍希望开启且应用未退出时恢复，暂停期间关闭则不恢复；只读扫描可同时运行。队列预缓存和下载补齐各保持最多 2 个准备调用；网络执行由全局块调度管理。删歌、切房或移出窗口会取消对应的地址解析及调用，再按下文生成有限交接租约。仍有有效需求的暂停块在资源允许时续取，顺序下载重新开始。

停止、删歌、切房撤销对应来源，有限交接期内可继续共享下载。其他 GET 的实际读取需求独立存在。退出控制台关闭引擎并排空全部执行；下载补齐、队列开关和自动启动意图仍按原生命周期管理。

失败状态按歌曲 ID 保存并按当前队列顺序显示，其他歌曲成功不会掩盖仍待重试的失败。歌曲删除、队列清空、换房或停止监听时清理对应错误；重试成功只清除该歌曲的错误。已被移出队列的下载即使稍后失败，也不会恢复过期提示。

## 资源需求与优先级

2026-10-15 起使用[全局块调度](download-concurrency.md)。队列控制器仍只准备窗口内的两个歌曲调用，日志只提供顺序。资源层按当前顺序产生有限 ReadyBy，调度器按实际 Blocking、期限和独立租约分配执行能力；不再使用视频 P0～P4 或后台视频席位抢占。Blocking 只绕过启动额度并计入总在途数，普通块在总在途数低于开放额度时按 ReadyBy 启动；优先级变化和目标下降不暂停在途下载。

队首消失会撤掉该来源，并为已提交、未完成的块保留最多 20 秒交接租约，ReadyBy 在原期限与退出时刻的较晚者上一次延后 5 秒；普通队列删除直接撤销。队首与普通队列互换只更新原来源的属性，不创建交接。队列删除后重加或重置会换用新标识，旧的地址解析结果不能重新登记为新队列来源。

新 GET 注册自身的读取需求并共享已完成块、部分前缀和在途请求。同块有有效 GET 时，旧交接不参与调度属性竞争；独立队列需求仍按自己的期限竞争，交接也仍按固定租约到期。GET 取消/关闭后的交接最多 2 秒，ReadyBy 同样在较晚者上延后 2 秒；读取正常推进/Seek、完成和引擎关闭不生成交接。交接不保留原始来源，转换日志记录来源与原因，运行时只使用已算好的时间和非阻塞属性。无有效需求或交接后不继续补齐；未来再次需要时可复用本引擎保留的进度。

完整缓存的 30 秒交接保护仍由文件保留层单独管理，与下载需求租约不是同一策略。关闭引擎立即取消所有执行和租约，等待正文/写盘清理；不提供跨重启断点续传。旧等级日志按原版本解释，新调度可通过 block_schedule 事件检查块身份、Blocking、ReadyBy、放行/暂停原因和 active/open/target，通过 block_demand 与 block_demand_handoff 检查来源汇总和交接转换；常规任务日志继续区分完成、失败与取消。

开发验证见[块调度记录](block-scheduler-validation.md)。旧实机报告继续保留；新规则待 LA-040，关联 LA-037/038/039。
