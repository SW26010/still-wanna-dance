# 下载并发与播放优先

## 当前实现（#20，2026-10-14）

单视频的 Range 并发与同时准备几首歌曲分开管理。沿用现有共享 flight/spool、缓存布局和选路接口，未增加用户设置或依赖。

| 层级 | 当前约束 |
| --- | --- |
| 跨歌曲任务 | `MaxDownloads` 默认 3；后台最多占 2 个，队列预缓存/下载补齐仍最多同时准备 2 首 |
| 单视频 Range | 1 MiB 块；3 个后台 worker，另 1 个保留给读取等待；小文件只创建必要的后台 worker |
| 全引擎视频 HTTP 请求 | 最多 6 个在途，后台发起最多占 4 个，其余保留给实际读取；与歌曲任务数独立 |
| 请求生命周期 | 首请求、重定向、重试、Range 和顺序 200 回退均受预算约束；等正文关闭完成才归还 |
| 预读 | 每个有效读取器当前块之后最多 2 个块优先于远处补齐；提示随读取移动、随关闭/取消失效 |

后台 worker 先帮助缺块读取，再准备近端数据，最后补齐其他缺块；等待读取按到达顺序处理。同块无论已开始还是尚在排队，都只有一个领取者；加入读取需求后原请求提升优先级。请求排队同级 FIFO，需求降级会通知其他等待者，避免已有可用额度却互相等待。

前台冷下载先取得首块再展开后台并发，尾部读取仍能绕过首块。加入已有预缓存时，首块等待也优先。首块等待或实际 Seek 可让本资源其他未被读者需要的块暂停；正在满足其他读者的请求保持。暂停保留 worker 已接收的部分，需求完成后从剩余字节继续，并沿用已验证的重定向终点和成功通道。普通后续顺序读取不反复触发让位。已完成块保留，直到整任务结束；这不是跨重启断点续传。

每个响应仍校验状态、Content-Range、长度、编码和强 ETag；部分恢复也不例外。弱/缺失 ETag 延续已有最终 MD5 校验边界。只有完整文件大小和 MD5 正确后才发布，不能用稀疏文件长度证明数据可读。无 Range 的 200 响应保持顺序下载。真实错误使用既有有限回退，本地让位不计为通道失败或重试耗尽。

跨资源的 P0/P1/P2/P3 调度继续遵守[队列需求约定](queue-prefetch.md#资源需求与优先级)。新预算只覆盖缓存引擎的视频 HTTP 操作；API、清单、测速和空闲 TCP 连接由各自原有机制管理，代理连接仍受节点准入约束。六个请求不是系统全部 TCP 连接上限，也不提供总带宽整形或任意网络下的播放时延保证。

三后台 worker、1 MiB 块和两块预读是保守的内部策略，保持块大小及完整性规则，避免增加自适应状态或配置负担。受控相同内容 A/B 中，单请求受限时预缓存约快 2.6 倍；共享总带宽时无明显吞吐收益，首块保护及 Seek 让位消除了初版的等待退化。真实线路的限速、错误率和音画表现仍待 LA-037，不外推回环结果。命令、原始对照和自动回归见 [#20 开发验证](issue-20-validation.md)。

## 2026-09-26 历史评估

以下保留当时的实现、建议和环境限制；“尚未实现 Range”“没有播放抢占”及 race 工具缺失不代表当前状态。

Auto 下的下载补齐、队列预缓存先查询 node=cf，失败后查询 node=nya；固定模式仅选择查询参数。资源来源以 API 的实际返回域名集合为准，不与 CF/HKG 名称绑定。同内容候选可用于失败回退，相同 URL 不重复尝试。通过快速存在性检查命中的 MD5 文件直接复用，缺失内容按 MD5 去重。已有共享下载继续当前传输，避免重复下载。

### 当时的并发与限制

| 层级 | 当前行为 | 扩大并发所需修改 |
| --- | --- | --- |
| 下载补齐 | `batch.go` 固定两个 worker | 将 worker 数连接到后台并发设置 |
| 队列预缓存 | `queue.go` 同时处理最多两首，只准备设定的预缓存范围 | 同步调整 active 上限和结果通道容量；保留队列顺序及失效取消 |
| 下载引擎 | `cache.go` 后台额度为 `max(1, min(2, MaxDownloads-1))`，默认总额度三份 | 显式配置后台额度并保证总额度至少多一份，不能仅提高 MaxDownloads |
| 同一资源 | 共用下载、校验和发布，多个请求不重复占用名额 | 保留共享任务的额度归属 |
| 取消任务 | 取消等待者；已开始的共享下载继续占后台额度 | 不能在调用者取消时提前归还额度 |

两首后台下载和一个冷缓存播放可以同时占用三个名额。预留的是任务名额，不是带宽；当前没有带宽限速或播放抢占。队列预缓存和下载补齐互斥，但只读扫描可同时运行，扫描仍会竞争网络请求和磁盘校验资源。

### 当时的可行方向

优先考虑可配置的跨歌曲并发：保留默认两首，先在下载补齐试验三至四首，同时保留一个播放名额。队列预缓存范围已可设为 1～100 个位置（默认 3），并发数仍为两首。扩大并发需要覆盖调度器和引擎，而不是只修改 HTTP 连接池。

单视频 Range 分段并发需要额外设计：检测真实 Range 支持、验证每段 Content-Range 与长度、约束分段总连接数、协调失败及取消、合并后全文件 MD5 校验。现有 spool 按连续写入字节数向播放器开放数据，不能直接改为乱序写入；需先跟踪连续可读区间。两线路元数据不一致时不能拼接内容。其复杂度明显高于跨歌曲并发，本次未实现。

吞吐收益尚未实网测量。后续可用相同的冷缓存歌曲集合比较 1/2/3/4 首并发，记录总耗时、总吞吐、错误与重试次数、同时播放的首字节延迟及磁盘占用；分别测试纯下载与播放共存，避免仅凭小段延迟判断大文件吞吐。本次保持现有并发上限。
