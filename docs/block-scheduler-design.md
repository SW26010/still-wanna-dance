# 以期望完成时间驱动的全局块调度

> 本页说明当前已实现的块调度架构。下载需求与资源管理的现行规则、接口及验证边界，统一维护在 canonical 文档[下载需求与资源管理设计](download-resource-design.md)。下载窗口已实现固定 M，块下载停止后结束旧任务、按需新建任务，不保留暂停／恢复。`need-by + 30 秒` 下载截止已接入调度器；截止后通过共享会话失败路径结束 GET，由来源集合撤销、重新整合，仍有效的准备来源在旧会话清理后重新取得资格。

**本次重构的核心设计，是把播放、预读、队列和补齐统一表达为对内容块的独立需求，再用“何时需要这块数据”驱动全局下载。** 视频语义留在需求管理层；调度核心只处理内容块、期望完成时间、需求有效期、真实读取阻塞和执行额度。

这使三个问题各有明确的答案：`ReadyBy` 决定先准备哪些块；固定提前量 `M` 决定何时允许启动；可启动积压驱动并发逐路增长，包括已入窗任务与允许提前执行的独立补齐需求。并发量由运行中的需求形成，无需预先反推一个目标并发数。同一块无论被多少来源需要，都共享一次执行，各来源仍能独立退出。

本文说明当前设计及其理由；具体参数、协议和资源边界见[下载并发规则](download-concurrency.md)，逐次实现与自动检查见[开发记录](block-scheduler-validation.md)。

## 为什么从整视频调度改成块需求

重构前已经具备 1 MiB Range 分块和共享下载，但调度同时受整视频 P0～P4、视频任务席位、每视频固定 worker 和全局 HTTP 额度约束。一段真实读取与同一视频中很晚才用到的数据容易继承同一个视频等级；跨层限额也使块在到达全局竞争之前就被挡住。

设计目标有三项：减少同时发起大量连接带来的 CPU 启动尖峰，在单路受限时利用多路下载供给数据，并把下载能力用在即将需要的块上。对应的机制是全局缓增、共享执行额度和块完成期限；实际收益须由新版本的对照验收确认。

| 问题 | 重构前的组织方式 | 当前设计 |
| --- | --- | --- |
| 先下载什么 | 按整个视频分级，再在视频内部选择块 | 所有来源转成块需求；普通块比较最早期望完成时间，实际读取缺块单独标记 Blocking |
| 共享与撤销 | 围绕共享视频任务安排席位、优先级和重连宽限 | 保留每份来源需求，按块汇总；撤销一份不会抹掉其他需求，交接也有独立租约 |
| 何时增加并发 | 视频席位、每视频 3+1 worker、总请求 6/后台 4 的多层约束 | 一个全局块调度器控制网络执行；普通额度按所设节奏和软上限开放，默认从 1 路按需缓增至 16 路，Blocking 可立即超限 |
| 如何提前准备 | 视频等级和近端读取窗口表达紧迫程度 | 从自己的 HTTP 请求、媒体大小和时长推导绝对 ReadyBy，再用固定 M 窗口准入 |

这次变化的重点是**需求、时间和执行的统一建模**。既有的分块传输、文件一致性、本地视频校验和发布继续由资源层负责。

## 四层职责

```mermaid
flowchart TD
    A["需求证据：HTTP GET / 队列 ID 顺序 / 本地媒体资料 / 补齐请求"]
    B["需求管理：推导期限、保留独立来源、撤销与交接、按块汇总"]
    C["全局块调度：租约、期限堆、固定 M 窗口、公平分配、并发缓增"]
    D["执行与存储：Range、重试、完整块、响应检查、完整文件校验与发布"]
    A --> B --> C --> D
    D -->|"可读耗时与执行完成"| C
    D -->|"本地读取等待开始／结束"| C
```

需求管理层认识 GET、队首、普通队列、补齐和交接，负责将来源语义转换成通用属性。调度器不识别歌曲、视频等级或“继任者”；同等紧急的任务通过不透明 `Owner` 公平分配。资源层提供兼容的内容身份和执行器，继续管理实体版本、选路、临时文件、强 ETag 及最终 MD5 校验。

产品以 MD5、大小和块号标识内容块，并由资源会话约束实体及选路一致性。URL 本身不作为共享身份。文件级生命周期仍然存在，网络执行额度统一交给块调度器；`MaxLocalValidations` 只限制本地文件校验，并非网络并发数，CLI 继续使用 `-max-downloads`。

## 三个独立问题：何时需要、是否仍需要、是否正在等

| 属性 | 回答的问题 | 不能混用的语义 |
| --- | --- | --- |
| `ReadyBy` | 希望这个块最晚何时完整可读？ | 期限已过仍可能急需，不能据此取消任务，也不是下载超时 |
| `LeaseUntil` | 这份需求有效到何时？ | 决定需求存亡，不代表本地视频文件保留期，也不延长执行超时 |
| `Blocking`（调度器内部） | 这一刻是否确实有 Read 等待这个缺块？ | 由本地读取等待独立派生，不在普通 Need、需求集合、交接或块使用接口中传递 |
| `Opportunistic` | 是否另有有效的无期限普通需求，允许提前使用空额度？ | 只绕过启动窗口，不绕过普通额度和缓增，不等于 Blocking |
| `WindowClosed` | 来源是否明确关闭当前入窗资格、等待事实变化？ | 不随墙钟自动打开，不结束来源、租约或在途任务；独立来源与实际读取仍可准入 |

普通需求有可更新、可关闭的身份，核心以句柄管理。主动撤销是正常路径，租约到期负责兜底；关闭或过期后的旧更新不能复活需求。续期必须依据来源仍然有效，不能因为下载还在进行就给自己续命。实际读取等待由 ReadRequests 独立登记，不依赖普通需求租约；本地 Read 返回、出错、取消时撤销，会话关闭清空等待。最后普通需求和读取等待均结束时立即结束旧任务，不保留供重接的任务元数据；响应关闭及写入收尾完成后释放执行额度和任务容量。Schedule 原子登记任务及普通需求，或为此前登记的读取等待接入执行器；已结束句柄不能复活，新需求待旧清理完成后建立新任务。完整块由本地资源层独立保留，未完成块从块起点重下。

例如块 K 同时被 A 的实际读取、B 的预读和补齐需要：A 退出只撤销 A 的贡献，B 的 ReadyBy 和补齐的提前准入仍有效；B 再退出，补齐可继续使用普通额度。K 始终只有一个共享任务。已经执行的块在仍有有效需求时自然完成，优先级变化不触发抢占。

合并时先排除失效来源，再处理覆盖关系：**同块有有效 GET 时，交接不参与调度属性竞争；独立队首和普通队列仍照常参与。** 入窗资格关闭的贡献不改变其他贡献的入窗时间；若所有贡献都关闭，保留最早有限 ReadyBy 及有效租约，但不进入普通准入堆。需求集合汇总可准入贡献的最早有限 ReadyBy 及独立的 Opportunistic 权限；调度器再独立合入本地读取等待，维护 Blocking 和实际等待时刻。任何有效来源都能维持任务存活，各份租约分别到期；交给核心的最晚 LeaseUntil 只是摘要的最终有效期，不能让已经到期的紧迫属性继续生效。

## 交接表达有限需求，不识别继任关系

交接由需求管理层在来源退出时计算一次，再与其他来源一起汇总。每块在同一次摘要更新中撤销旧贡献并加入交接，避免中间出现“无人需要”而误取消执行：

| 来源事件 | 下载需求处理 |
| --- | --- |
| GET 取消或关闭 | 交接最多保留 2 秒；`ReadyBy = 原 ReadyBy + 2 秒` |
| 队首从队列消失 | 交接最多保留 2 秒；`ReadyBy = 原 ReadyBy + 2 秒` |
| 普通队列项删除 | 直接撤销该来源 |
| 队首与普通项互换 | 原地更新来源与期限，不生成交接 |
| 读取推进 / Seek、块完成、引擎关闭 | 不生成交接 |

交接不持有读取等待或 Blocking，也不继承提前准入权限；租约固定为来源退出时刻加宽限；通知处理延迟、重复关闭及无关更新都不能延长它。交接不再生成交接，原始来源仅记录在转换日志，运行时只保留算好的通用属性。

新 GET 直接登记自己的需求并复用相同块，不必判定它是不是旧请求的继任者。新需求可以只接上部分块；其他块按各自租约结束。新队列需求也能共享下载，但不会继承旧 GET 的紧迫性或续长旧交接。本地保护按有限使用需求的独立提前窗口生效，最后一份块需求结束后按配置延续（默认 300 秒，0 表示不延续）；已移除队列专属 30 秒文件保护。

交接已按完整使用范围维护，包含已下载未消费块；有效期按真实退出时刻冻结，need-by 只在原值上平移。来源集合输出不含来源身份的 blockUse 摘要，下载协调器不再持有来源贡献或交接数组，本地保护复用同一整合投影。具体规则以[下载需求与资源管理设计](download-resource-design.md#常规播放交接与同块需求重新接入)为准；完整块存储与下载停止语义均已接入。

## 用自身数据推导播放与队列期限

VRC 队列日志只提供歌曲 ID 的顺序和变化；标题、时长和媒体大小来自本地资料。大小 `S` 优先取同一 MD5 的 `media.byte_size`，来源是已验证资源 URL 的 `s`；新 URL 尚未入库时可直接使用其已验证大小。时长 `D` 取匹配资源的歌曲清单 `end`，作为完整媒体时长近似，不减 `start`。该选择的样本依据见[视频元数据研究](research/video-metadata-20261015.md)。

地址解析成功即可将 URL 观察与对应资源大小一起保存，无需等待视频正文下载，也不覆盖清单已有的歌曲映射。这样本地尚无的视频也能利用已知大小细化期限；解析失败、旧结果及事务边界见[资源元数据验证](song-url-metadata-validation.md)。

设 `t₀` 是 GET 刚到达的时刻，`a` 是按实际响应语义解释的 Range 起始字节，`b` 是块起点，均在媒体范围内：

```text
平均总码率 R       = 8 × S / D
估计播放位置       = D × a / S
GET 块 ReadyBy(b)  = t₀ + max(0, D × (b − a) / S)
预计媒体结束 E     = t₀ + D × (1 − a / S)

队首开始 Q₁        = min(所有当前有效 GET 播放时钟的 E)
第 j 首开始 Qⱼ     = Q₁ + 前面各首预计时长之和
队列块 ReadyBy(b)  = Qⱼ + Dⱼ × b / Sⱼ
```

上述 GET 期限只用于与实际请求字节区间相交的块。起点位于块内时，该相交块的负偏移截为 0；起点之前的整块和结束位置之后的整块不产生该 GET 的需求，完整补齐必须有独立来源。`ReadyBy` 表达需要数据的时刻，提前策略统一放在后面的 `M`，不在这里再减一次提前量。读取推进和下载进度不重置 `t₀`；有限 Range 的结束字节限制下载需求，但不当成整部媒体的播放终点。无 Range 对应整文件，合法单 Range 支持后缀形式；If-Range 不匹配而返回整文件时，需求范围和估算起点一并恢复为整文件。HEAD、无效和多段 Range 不提供播放时钟。

无有效 GET 时的起点规则见 [canonical 队列预计使用时间](download-resource-design.md#队列预计使用时间)：保留尚在未来的估算，已落后的起点取当前时间。来源层复用使用需求计时器按 10 秒节奏维护有限期限并统一通知，无下载或新快照时也生效；滚动阶段的下载和保护资格按块距队首的相对时间判断，不在刷新间隙随墙钟自动入窗。有效 GET 继续按固定播放时钟推导。重复快照本身不重置基准；重排及元数据变化重算受影响的期限，退出成员及交接保持冻结时间，迟到的地址解析不能复活旧成员。

缺失值使用一致的补全规则：大小和时长都有时直接计算；只缺一项时按 2 Mbps 推导缺项；两者都缺时使用 45 MiB、210 秒，派生码率约 1.8 Mbps。未知队列占位仍计入典型时长。估计值只用于调度，不写回媒体事实，不用于 HTTP 长度、Range 边界或完整性检查。

这是一种播放时间近似。当前直接取所有有效 GET 时钟的最早结束值，没有按连续正文行为筛掉尾部索引或探测请求；这些请求可能让队列提前准备。变码率、预读、Seek、暂停和播放器缓冲也会造成偏差，不能声称所有估计都必然早于实际需要。真实 Read 缺块由 Blocking 兜底，效果与代价仍需观测。

## 用固定 M 窗口决定启动

`M` 是完整下载提前量：普通有限期限块在 `ReadyBy ≤ now + M` 时入窗，入窗时刻为 `ReadyBy - M`。等号可启动，仍需执行额度；未入窗候选等待堆首定时事件。已经执行的块不重复申请额度。所有块共用 M，期限排序不变，不保存逐块预计启动时间。

默认 M 为 500 秒，建议 200～2000 秒；控制台「提前准备时间 M（秒）」及引擎配置范围为 100～16000 秒，0 使用默认值，保存并重启后生效。约 67 秒是 1 MiB 块在 0.125 Mbps 下的纯传输基准，100 秒下限不保证慢网或排队下及时完成。范围外的非零值直接拒绝，不作迁移。

动态耗时估算 T、衰减状态及 start_urgent 诊断已删除。成功标准块仍报告实际准入至可读耗时，供测速完成块计数和日志使用；该观测不影响启动窗口、排序或额度。尾块、部分续传、失败执行及顺序 200 不混入标准块观测。清理仍占用 active，直到执行退出。

例如视频大小 50 MiB、时长 1000 秒，GET 在 t₀ 从 10 MiB 开始，20 MiB 处的块 ReadyBy 为 t₀ + 200 秒。M=120 秒时，该块在 t₀ + 80 秒入窗。实际缺块读取可独立贡献 Blocking，无期限补齐仍可使用空余普通额度；两者不改变播放时钟。

## 并发由可启动积压驱动

“可启动积压”包括已入窗的有限期限任务，以及具有有效独立补齐需求、允许提前执行的任务；两者都可能因普通额度已满而等待，也都能驱动缓增。

增长间隔为正时，普通开放额度 `open` 从 1 开始。调度器先按期限立即复用已有空额度，只有存在可启动积压、且 `active ≥ open` 时，才按所设间隔最多新增一路，直到所设软上限。无可启动积压即停止增长；执行和可启动工作都清空后回到 1。连续替补不会每块重新等待增长间隔。间隔为 0 时关闭缓增，直接开放软上限额度，仍按需执行。默认 16 路 / 250 ms，设置范围及生效规则见[运行参数](download-concurrency.md)。

已接入资源在确认 Range 支持及实体身份后，展开各有效来源所覆盖的全部未完成块：GET 按请求区间，队列和独立补齐按整文件。没有每视频固定候选数或独立并发额度，单视频在需求入窗且持续积压时也能用满所设软上限。首次响应头前只调度一个初始化块，冷 Range 从请求区间内的块开始；并发接入的读者共用当前初始化请求，确认实体后各自恢复区间边界。上游返回顺序 200 时仍只执行一次整文件回退。

固定“当前块及后面两块”的读取窗口已删除，普通 GET 需求统一表达预先准备，本地 Read 仅向调度器报告当前缺块等待的开始/结束；调度器维护 Blocking，多读者独立撤销。客户端断开、服务端取消和 Reader.Close 共用本地等待清理，交接不参与。已下载区间仍有 GET 读者消费时保留资源会话，不生成区间外补齐任务；最后一个来源退出后沿使用交接、完整块保留和回收规则处理。只有完整文件校验成功才发布正式视频。任务容量沿用全局保护，超容量推迟注册并等待容量变化，Blocking 可回收尚未执行的普通候选容量，不通过隐藏候选改变排序。

两种窗口例外必须分别理解：

- **Blocking**：实际缺块等待立即执行，绕过窗口、缓增和所设软上限；仍计入总 active，受任务/资源容量约束，同块继续去重。
- **Opportunistic**：无期限补齐可在有限期限堆首尚未入窗时使用普通额度；同块兼有有限期限和补齐时保留两种准入依据，但只有一次执行。已入窗的有限期限候选优先，补齐撤销只撤掉自身提前权限。

所有执行直到正文关闭与收尾结束才从 active 扣除。普通准入仍要求 `active < open`，因此 open=4、4 路普通加 2 路 Blocking 时，总 active=6；回落到 4 仍不补位，回落到 3 才能补一路。Blocking 出现、消失或普通期限临近都不取消仍有有效需求的在途请求。

此规则按多路能够增加有效供给的假设工作，不做总带宽整形。固定 M 不能保证任意数量的同期限块准时，实际总带宽不足时增加并发也未必增加吞吐。迟到须同时核对 ReadyBy 的依据、M、窗口内排队、并发准入及执行故障，不能只归因于 T 不够精确。

## 事件驱动与生命周期边界

核心一个事件循环持有任务和索引堆，等待需求变化、执行完成或最近的入窗/增路/下载截止/租约时刻。已入窗但满额度的任务等待完成或缓增事件，不把过去的入窗时间反复装成立即触发的定时器。没有每 500 ms 全任务汇总、排序和目标并发反推，也没有每块独立的轮询协程。

定位共享块、汇总该块的有限来源、调整相关索引即可响应变化。单个堆项调整为 O(log N)，检查堆首是否入窗为 O(1)；同 Owner 的公平性更新可能调整该组多个块，不能把整个事件处理夸大为恒定成本。网络、磁盘和正文关闭在执行器中完成，调度事件循环不等待这些操作。

事件驱动不等于系统没有定时工作：资源协调器仍每 10 秒确认来源并续 30 秒活跃租约；VRC 日志按[队列文档](queue-prefetch.md#日志检测与频率)增量读取。缓冲只在实际执行时取得，全局任务与使用需求数量有界，完整块由引擎本地资源注册表保留，已移除暂停检查点上限，具体上限见[运行规则](download-concurrency.md)。

调度等待不消耗网络尝试预算：实际 HTTP 请求的响应头及正文共用一次 DownloadTimeout，默认 10 分钟；重试候选各自重新计时，不按剩余候选数平分，不另加包含重试的整轮执行时限。顺序 200 使用同一本次尝试时限，本地校验/发布各自计时。更早的父级取消与任务截止仍然生效。有限 ReadyBy 的下载截止为 ReadyBy + 30 秒，排队和运行共用索引堆唤醒；Blocking、其他无期限贡献和租约续期不能延长它。真实来源变化可在到期前更新整合时刻；已到期任务先结束，迟到更新不能复活。完成和到期同时可观察时先处理截止；响应关闭及写入收尾完成后才释放额度。顺序 200 正文与 Range 一样先结束下载任务，随后独立进行本地合并发布。来源撤销、租约到期、调用方取消、执行失败和引擎关闭继续独立控制生命周期；跨重启不恢复部分下载。

## 按需块观测（2026-10-20）

`Server.ObserveBlocks` 在首个订阅时建立共享观测任务；需求、块可用性和调度变化仅作非阻塞唤醒。未来窗口与保护边界使用一次性到期通知；变化事件和到期通知共用触发后的 50 ms 合并窗口，相邻边界不绕过合并反复构建快照，没有固定轮询。首份快照立即生成，后续窗口只延迟界面观测，不延迟实际调度或保护回收。观察者复用现行使用投影和整合函数，读取调度器提供的实际读取等待与执行状态；不拥有需求、文件引用或下载任务，不续约、不干预调度。

最后一个订阅关闭时移除调度通知、取消并等待观测任务退出，释放快照、来源标识及视频展示资料缓存。没有订阅时，业务路径只有空指针／空订阅集合检查，不生成快照、事件历史、额外定时器或后台任务。快照在业务锁内建立使用投影、复制来源展示资料及本地可用性／保护状态，来源资料每次快照只按来源复制一次；每块的需求整合、来源身份分配、详情排序在锁外处理已脱离共享状态的值，来源指针只作为身份键、不在锁外解引用。JSON 编码、客户端差分及网络发送也在锁外，慢客户端不积压事件队列。

下载任务标识的构造与解析统一由 `cacheproxy/download_task_key.go` 维护，沿用 `resource/size/block`；调度器将它视为不透明字符串，使用需求和展示仍按资源及块号定位。Range 与顺序下载成功写入完整块后，共同调用 `notifyBlockStored`，分别通知观测和请求回收；`requestBlockReclamation` 只按现有策略请求回收，关闭回收策略仍会发送写入观测通知。

交接的歌曲展示信息从已有资源身份、观测期间的标题和本地目录恢复；无需在核心交接对象中增加界面字段。仍缺标题的视频在业务锁外按批查询本地目录，已知歌曲 ID 优先；仅知资源时取目录中稳定排序的关联歌曲，不据此断言原交接来自该歌曲。查询有取消和超时，结果（含未找到）只在当前可见资源存续期间缓存，身份变化可重新补齐，不随下载事件反复查库；资料不可用时仍保留标识兜底。UI 关闭时不做查询或维护该缓存。

多个歌曲 ID 共用资源时，若本帧块仍包含缓存的展示 ID，则继续沿用；否则按 ID 字符串顺序选择当前已知标识，没有已知标识时沿用缓存。同一块有多个来源时，先按此规则成对选择歌曲 ID 和标题，再以相同规则汇总到资源，避免先取一个来源的 ID、再借用另一个来源的标题。先使用所选 ID 的当前非空标题，同一 ID 的多个当前标题按字符串顺序确定；缺少当前标题时保留相同 ID 的缓存标题。选择不依赖来源顺序或 map 遍历顺序，其他歌曲的标题不能覆盖所选 ID 的标题。来源详情和需求行保留各自明确的歌曲 ID，仅在身份一致时借用资源展示标题。

控制台 `/api/block-demands/events` 使用与现有 SSE 一致的 Host/Origin 检查，并拒绝浏览器跨站请求；首次连接发送完整状态，后续只发送修改和移除项，重连重新发送完整状态。运行中 `blocks` 事件的顶层 `at` 使用发送时的服务器时刻，供前端作为“现在”的时钟锚点；多个窗口复用较旧的共享快照时也遵守此规则，不修改快照或块自身的定位、need-by、截止及保护时间。时间流逝本身不产生事件。`?block=<资源标识/块号>` 只推送所选块的属性与来源。页面订阅不得创建引擎；引擎尚未创建时沿原连接等待启动事件，取消后释放等待者，不靠定期重连探测。关闭引擎会结束事件流。推送有写入超时，来源详情不包含签名 URL、代理配置、文件路径或内部指针。

同一快照还按「来源标识 + 视频资源」聚合需求矩形，包含来源种类、歌曲／标题、队列位置，以及按视频内块号排序的块 ID 引用；组装与排序在业务锁外。块与需求的 `totalBlocks` 从已有内存视频大小计算，包含不足一块的尾部，表示完整视频范围而非本项需求的剩余块数，未知时为 0；详情以 `13/45` 显示视频内编号，需求行据此保留块在视频中的位置和空档。SSE 的 `demands` / `removedDemands` 与块增量同时发送，来源撤销或队列换位即使不改变共享块的综合状态，也会更新需求视图。保护尾部没有使用来源，不生成需求矩形。块的 `songID` 用于标题与初始配色，前端在视频仍在视图时沿用其已分配颜色，界面块序号从 1 开始，不修改后端的零起始索引。该聚合只存在于按需观察者中，不增加核心来源、续约或关闭 UI 期间的历史维护。

显示集合包含有效使用块及本地仍可用的延续保护块，因此总显示量可能超过 4096；容量计数仍只针对有效使用。保护期块在本次观察期间有已知有限 need-by 时沿用最后显示位置；此前已经退出的块以真实需求结束时间（保护截止减当前生效的延续时长）定位并明确标注，不为 UI 关闭期间维护历史。当前界面保留视频配色并以半透明显示保护期块，初版灰色仅属历史外观。无有限时间的块保持无期限语义。块可读不代表完整视频已通过 MD5 校验并发布。
