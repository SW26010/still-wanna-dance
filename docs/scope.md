# 范围与实现方向

状态：2026-09-25 的项目起点。本文的设计方向是提议，不代表原版内部实现已被确认。

更新：Go MVP 已按下述可靠性目标实现，具体行为以 [MVP 手册](mvp.md) 为准。首版只接入两个视频 HTTP 域名，暂不实现 API、TLS、SHA 或管理 UI；冷缓存边下边播，完整校验后才发布缓存。原版待测问题仍保留，不以实现自行选定的行为替代原版证据。

## 目标

独立实现本地服务，使 Windows 上的 VRChat WannaDance 可以读取已有视频缓存，在缺少文件时回源，并将完整下载的视频用于后续播放。以外部可观察的兼容行为为依据，不要求恢复原版源码。

第一阶段针对用户自己的 Windows 电脑和 WannaDance 实际播放链路。后续是否支持其他舞房，由新证据和需求决定。

## 存储要求

当前采用单一 canonical 存储：视频平铺于 `videos/<歌曲ID>-<版本键>.mp4`，歌曲资料、版本映射与请求统计保存在 `stepstash.sqlite`；不考虑旧格式兼容及数据迁移。详见[统一存储](storage.md)。

## 第一版拟覆盖

- 接收 `play.udon.dance` 和 `nya.xin.moe` 对应的视频 HTTP 请求。
- 根据歌曲及版本信息定位缓存，提供文件读取、HEAD 与播放所需的 Range。
- 无缓存时访问正确上游；完成后验证文件并发布可重用缓存。
- 在冷缓存、热缓存、切歌、恢复进度时提供足够日志，区分客户端中断、上游失败和本地错误。
- 配置可选择监听地址、缓存目录和上游；默认本机使用的具体实现方式待设计。

API 路由和 443 SNI 透传的范围应单独决定。已经验证的最小实机接入方式只映射两个视频域名，保留 API 的原始路径；这可以避免原版 API 未命中时丢失 `node` 的行为。

## 尚不作保证

- SHA 路由：已知入口超时，最终视频响应未知。
- 与所有 VRChat 平台、播放器后端或其他舞房兼容。
- RTSP、Redis 鉴权、全量镜像下载器的兼容；这些没有纳入本轮验证。
- 原版错误行为逐项复现。Range 的越界及后缀解析错误应记录为差异，后续明确兼容策略。

## 建议的服务边界

| 部分 | 责任 | 当前状态 |
| --- | --- | --- |
| 请求入口 | 识别 Host、路径、查询参数、方法与 Range | 核心样本已知，严格校验边界待测 |
| 路由 | 保留原始 Host/SNI，选择不会回环的上游 | CF/HKG 的路径已知 |
| 缓存索引 | 定位歌曲与内容版本，避免将不同版本误认为同一文件 | 缓存键与失效策略待设计 |
| 下载管理 | 临时文件、同曲并发、取消与失败恢复 | 完整成功路径已知，边界待测 |
| 文件响应 | 返回实际内容、正确长度和 Range | 常见请求已验证 |
| 可观测性 | 记录请求关联 ID、命中/未命中、传输与落盘结果 | 测试观测器已有可参考字段 |

推荐采用“临时下载 → 完整性检查 → 发布缓存”的设计，避免将半文件作为完整缓存返回。同曲并发应有明确的协调规则。这些是可靠性目标，不是对原版内部算法的陈述。

## 实现前的下一步

开发语言为 Go，后续简单 UI 计划采用本地网页；环境说明见[开发环境](development.md)。MVP 的版本校验、并发与中断恢复使用可控上游自动化测试验证。[待验证清单](open-questions.md)中的原版黑盒边界和真实游戏验收仍需继续完成。

现有文档已足够启动方案设计与第一版工作，不足以宣称完整兼容规格已经冻结。
