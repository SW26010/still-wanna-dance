# 日志排障与验收证据

原始日志文件是主要排障材料，可直接读取、搜索或交给 AI；程序或 WebUI 无法启动时仍可离线阅读。日志记录诊断信息，不承担业务状态恢复。设计取舍与本轮验证记录见[日志调整记录](logging-design.md)。

## 行格式与职责

新日志只写一份 UTF-8 结构化文本，一条记录占一个物理行。例如：

```text
2026-11-13T20:35:42.1234+08:00 [INFO] "HTTP 请求已完成" pid=1234 session_id=example event_name=request_finished request_id=42 status=206 bytes=1048576 outcome=completed
```

前三项固定为完整时间、方括号内的级别、简短中文摘要，不带 `time=`、`level=`、`msg=`。其后使用标准 `key=value`。消息及属性沿用 `slog.TextHandler` 的按需引用、转义及分组规则；换行、引号、控制字符不会打断记录边界，不输出实际终端色彩控制序列。自有事件保留原事件名作为 `event_name`，字段名和标识保持英文；系统与第三方错误保留原文。现有 `block_schedule` 的 `event` 仍表示调度子事件。

摘要说明这次发生的事情，可以按已有结果或原因区分。例如 `cache_task_finished` 区分任务完成、失败、取消、超时和未保留完整视频；完成不等于新发生了一次下载。同一事件在不同级别输出时，摘要与事实一致，不因级别变化机械改写。自动验收按 `event_name` 和必要字段判断，不匹配中文措辞。

文本保留字段内容供人和 AI 阅读，不承诺无损恢复 JSON 的类型或嵌套结构：数值 `42` 和字符串 `"42"` 可有相同文本表示，数组可能表现为字符串。产品不维护字段类型表、日志 schema 或通用转换器。事件含义不变时保持标识稳定；确需调整关键约定时同步本项目消费者，不把每项诊断属性变成永久对外协议。

业务产出处负责摘要、稳定标识、结果及级别，沿用原有结果判定；不设置全局翻译表或事件注册框架。`internal/applog` 统一过滤级别、进程与会话身份、时间和排版；标准 `TextHandler` 负责属性编码、引用转义、分组和并发序列化，薄 Writer 只改行首三个受控前缀，不重写消息和业务字段。随 Go 升级复核定向格式测试，不将薄适配扩展成可配置排版器。文件 Writer 负责同步写入、轮转、清理和故障反馈，不反解析正文。

## 时间与精度

时间采用带偏移量的本地 RFC3339，布局为 `2006-01-02T15:04:05.0000Z07:00`。小数秒固定四位（100 微秒显示粒度），截断多余位数；这不保证时钟达到该测量精度。每条记录携带偏移量，无需依赖启动消息或文件头；零偏移可输出 `Z`。[RFC3339](https://www.rfc-editor.org/rfc/rfc3339#section-5.6) 允许可变位数小数秒，四位是本项目约定。

其他 `time.Time` 属性使用相同格式，零时间仍以 UTC 零值表示，保留未设置语义。`time.Duration`、`elapsed_ms`、`first_body_ns` 等时长和数值字段沿用各自单位及精度，不套用时间戳的截断规则。业务计时、数据库时间和文件修改时间不受影响。

## 分片、保留与升级

日志保存在当前配置实例的 `logs/`；路径隔离见[存储契约](storage.md)。按写入时的本地自然日命名，例如 `20261113.log`、`20261113-1.log`、`20261114.log`。

- 跨日后的第一条记录触发新日期分片；不增加午夜定时器。每片最多 1 MiB，总预算 20 MiB；下一条完整记录超限时递增序号，不跨文件拆分，单条超限沿用写入失败反馈。
- 重启只续写当前本地日期下最新、未满的文本片；同一天不同启动通过 `session_id` 区分。时间回拨后仍使用实际写入日期，排他创建、递增数值序号，避免覆盖旧内容，不沿用未来日期文件名。
- 启动、切换日期和新建分片时为当前片预留完整 1 MiB，再清理最旧文件；普通逐条写入不扫描目录。新文件按日期、数值序号排序，保护当前写入片，实际保留量可能略低于预算。
- 旧 UTC 时间分片（如 `20261103T000000Z[-序号].log`）和 beta4 的 `app.log`、`.1`～`.3` 保持原样，不转换、不追加新文本；继续计入预算，先按各自旧顺序清理，再清理新文本。新旧格式不混写同一文件，不以新旧名称的混合字典序或解析正文决定保留顺序。
- 未知名称文件保持原样，不读取、不清理、不计入受管理预算；关闭日志时不创建、追加或清理文件。

写入直接同步交给文件，无用户态异步队列。日志创建失败及运行中 I/O 故障沿用现有应用故障处理，具体见[程序日志](console.md#程序日志)。状态轮询不写诊断日志。

## WebUI 范围

「关于 → 介绍 → 文件位置」展示程序日志目录，日志级别在「设置 → 常规」管理。程序日志目录属于当前配置实例，与读取 VRChat 日志的目录无关。按时间导出材料使用「关于 → 使用帮助 → 反馈问题」中的诊断收集表单；不提供目录打开按钮。

WebUI 不提供日志阅读器；原 `/api/logs`、`/api/logs/export` 与 `#/logs` 日志页仍已移除。原始文件可离线阅读；按时间收集排障材料使用下述诊断包，不恢复通用日志查询或字段解析。

### 收集诊断信息

唯一入口位于「关于 → 使用帮助 → 反馈问题」卡片。卡片内直接展示表单，“最近 X 小时”数字框默认 24，导出时以当前时间计算；编辑本机起止时间切换为自定义范围；问题说明可留空，直接下载 ZIP，不自动上传或脱敏。填写的说明单独保存为 `用户说明.txt`。

`POST /api/diagnostics/export` 复用管理接口的 Host、条款、Token 和 Origin 准入。参数为 Unix 毫秒 `from`、`to` 和可选 `note`；范围开始包含、结束不包含。读取当前生效的数据库、SWD 日志目录和有效 VRC 日志目录，不启动引擎、修改配置或写入业务数据库。

- `requests.jsonl`：单次 SQLite 查询快照内、到达时间命中的全部请求原始字段，包含 HEAD、失败、取消及未完成记录，不沿用页面分页和隐藏过滤，不拼接当前曲库名称。结束信息为收集时已有记录，区间外开始的请求不补入。
- `swd/`：跨现行及保留的旧分片按记录时间裁剪，兼容旧 JSON 行，只读取时间字段，保留正文。
- `vrc/`：跨 `output_log_*.txt` 收集，按 `yyyy.MM.dd HH:mm:ss` 以本机时区解释，无时间戳续行随上一条记录保留。无法还原历史时区变更；不以文件修改时间筛选。
- `manifest.json` 和 `说明.txt`：记录构建、范围、收集时间、VRC 时区假设、记录／文件数量与读取问题。无匹配记录不证明没有活动，也不推断保留覆盖水位。

各来源分别读取；日志只读打开时的文件大小，避免等待持续追加，不保证跨来源原子快照。文本片段统一以 LF 换行。单个来源或文件失败仍导出其余材料，并明确部分收集；超长日志行（超过 4 MiB）停止该文件并记录错误。总收集期限为两分钟，取消会终止读取；ZIP 在系统临时目录生成后下载，请求结束删除临时文件，不持久保存导出任务。进程被强杀时可能残留系统临时文件。

自动验证与真实 Console 浏览器下载证据见[诊断包验证](validation/diagnostic-export-20261114.md)。

## 开关与级别

默认 `info`，记录 Info、Warn、Error。Info 保留引擎配置、请求和共享任务结果、完整视频发布及其他操作摘要；下载阶段、进度、共享任务关联及逐块调度等过程细节属于 Debug。桌面在「设置 → 常规 → 程序日志级别」选择，保存为 `logLevel`，重启整个程序后生效。缺失、null 或空字符串使用 info，其余未知值拒绝。

`off` 关闭所有诊断记录。桌面不会为诊断输出创建、打开、写入或轮转日志文件，已有日志保留，可在文件系统中自行查看。游戏日志读取、请求历史和运行统计不受影响。其他级别表示最低记录级别，例如 warn 保留警告和错误。关闭日志不会取消进度统计或业务状态采样。

日志初始化前先按现行配置格式读取级别；配置文件读取、格式校验或日志级别解析失败时使用 Info 记录启动失败，并保留原配置。日志文件创建失败仍会阻止已启用日志的正常业务启动；桌面故障通过独立于日志级别的[故障入口](settings-lifecycle.md)打开 WebUI，无法打开时显示原生错误。

桌面块工作区清理先使用遵守该级别的 stderr logger，清理完成后才打开文件日志。配置读取错误暂存到清理之后处理，避免配置损坏或日志目录不可写时跳过残留块回收；`off` 同样关闭这段清理的诊断记录。

保持同步写入和有界轮转，不增加异步队列。Debug 在调度路径记录较多事件，排障后应恢复 Info。当前没有开关前后的性能对照，不能将该设计解释为零开销或帧率保证。

## 如何关联事件

- `session_id`：一次程序日志会话。`application_build` 记录 Go 构建信息中的版本、提交和工作区修改标记（构建器未嵌入时不提供提交）。不同启动不能只靠 PID 区分。
- `service_id`：一个本地资源引擎实例，重新创建会变。`request_id` 和 `flight_id` 都只在这个实例内有效。
- `trace_id`：一次播放请求或歌曲预加载操作。队列启动、上游解析、预加载及结束事件使用同一个值；共享地址查询和共享下载分别使用最初创建它们的操作标识。地址查询只继承该标识，取消责任仍由引擎持有，不随单个等待者退出而取消。
- `resource_key`：视频内容版本的指纹。Debug 下用 `cache_task_attached` 将每个操作连接到 `(service_id, flight_id)`，再查看这一共享任务的下载日志。同一版本重试会产生新的 flight；Info 可按资源查看结果，但不能总是准确关联到共享任务。
- `song_id`：曲库列表中的歌曲 ID。多个歌曲可能共用资源，不能把它与资源指纹混为一谈。历史淘汰事件的 `key` 与 `resource_key` 是同一指纹。
- `host`：请求或下载会话的资源域名；`upstream_host`：建立上游响应时实际选择的域名，可能经过重定向或回退。两者分别记录，不能以重复字段覆盖原始身份。

例如在 Debug 下，两个播放请求共享一个下载时，会看到两个不同 `trace_id` 的 `cache_task_attached` 指向同一 flight；下载和发布只记录一次。客户端中断、移出队列不一定中止共享下载，必须分别检查请求结果和 flight 结果。

## 过程和结果

| 事件 | 用途 |
| --- | --- |
| `cache_engine_ready` | 引擎配置摘要、视频预算及启动清理的残留临时文件数；零预算是正常策略，残留不能直接证明上次为何退出 |
| `temporary_cleanup_removed` / `temporary_cleanup_skipped` | 回收的暂存路径，或因未知内容、异常类型保留的路径；实际删除失败使引擎启动返回错误 |
| `config_work_cleanup_removed` / `config_work_cleanup_failed` | 配置锁持有者回收明确的原子写入工作槽；失败阻止 Console 创建 |
| `vrchat_detected` / `vrchat_exited` | 开启「随 VRChat 退出」后，本次首次检测到游戏、随后确认当前会话内游戏进程均已结束；后者请求正常退出 SWD |
| `vrchat_process_check_failed` | 游戏进程状态暂时无法确认，不触发退出；持续失败只在开始时记录一次，成功检查后恢复判定 |
| `snapshot_load_failed` / `monitor_throughput_state_load_failed` | 可重建状态未恢复的原因；不生成连续损坏备份 |
| `proxy_channel_identity_corrupt` / `proxy_channel_identity_unavailable` | 密钥原文件保留，代理使用临时身份；持久样本关联需恢复原密钥 |
| `cache_capacity_wait` / `cache_task_attached`（Debug） | 等待正在退出的共享下载会话清理及附着结果；`wait_ms` 包含此前等待，不是调度器块席位等待时长 |
| `request_finished` | 请求方法、Range、版本，以及最终 HTTP 状态、实际写入字节、Content-Range/Length、耗时、结果和写入错误；`request_started`、`served`、`client_disconnected` 和 `playback_local_hit` 为 Debug |
| `upstream_response` / `range_unavailable` / `download_first_byte`（Debug） | 初始化或顺序下载响应的实际上游域名、状态、声明长度及回退；从视频准备任务开始到读到第一批正文的毫秒数（包含本地视频检查）。上游响应不是每次块请求的响应清单 |
| `download_stage`（Debug） | 阶段变更及上一阶段耗时：本地视频校验、块或顺序下载、`hash` 合并校验、发布文件、数据库登记；块下载阶段可能包含调度等待 |
| `download_progress`（Debug） | 每个仍活动的 flight 每 15 秒一条；阶段、已读取正文大小、预期大小、最近一个周期平均字节/秒、距最后数据的 `idle_ms` 和阶段耗时。短任务无此事件；时钟未推进时速度记为零，字节留待下一次有效采样 |
| `download_verified`（Debug） / `download_integrity_failed`（Warn） | 完整视频的大小和 MD5 是否满足预期；`hash` 阶段读取完整块快照、写入发布暂存文件并计算 MD5，与下载阶段分别计时 |
| `download_published` | 完整校验、正式文件发布和数据库登记均已成功；不能保证该资源随后不会因容量策略被淘汰 |
| `cache_task_finished` | 共享任务最终阶段、耗时和 `completed` / `failed` / `canceled` / `timeout` / `not_retained` 结果；成功命中也会出现，不能将它单独当作新下载成功 |
| `download_started` / `local_blocks_reused` / `cache_not_retained` / `cache_task_canceled`（Debug） | 下载开始、复用块及任务未保留或取消的细节；最终结果仍见 `cache_task_finished` |
| `prefetch_resolved` / `prefetch_started`（Debug） / `prefetch_finished`（Info） | 共用播放地址查询的结果与耗时、资源域名及 MD5，以及预加载结果；`success=false` 表示本次地址解析失败。解析日志的 song_id 是实际查询歌曲，固定资源反查的歌曲不改变下载操作的歌曲身份；完整 URL 不入日志 |
| `queue_updated` | 有序 `song_ids`（保留 -1 占位）、房间重置代数；用于更新队列需求，不记录歌名、玩家或房间原文 |
| `queue_song_canceled` / `queue_song_discarded` | 队列变化取消等待或旧结果被丢弃；不是下载失败 |
| `batch_started` / `batch_finished` | 批次开始与结束汇总；结束区分仅扫描、缺失数量、取消和是否处理完列表。扫描完成仍可能存在缺失文件；处理中进度通过运行状态展示 |
| `network_calibration_finished` | 手动测速结束摘要：上游、阶段与原因、已准备视频数／总大小及实际下载字节；区分样本准备不足、取消和下载阶段结果，不记录签名地址或凭据 |
| `network_calibration_local_songs_failed` | 测速未能读取本地歌曲或已有 URL 的原因；该轮只利用已取得的候选，不触发清单同步、不修复或重建本地数据库 |
| `block_schedule`（Debug） | 块排队、开始、结束、期限退出、采样与开放数量变化；`event` / `reason` 说明事件和原因，`block_key` 标识块，附带活动数、开放量及期限等调度信息 |
| `block_demand` / `block_demand_handoff`（Debug） | 单块有效需求及 GET／队列来源退出后的交接期限，用于核对需求、租约和本地保护边界 |
| `playback_timing` / `queue_playback_timing`（Debug） | GET 与队列使用媒体信息推算的播放时间；不能直接证明播放器已开始或完成播放 |

`bytes` 在下载进度中表示已从上游读取的正文，在请求结果中表示成功写入响应的数据；二者口径不同。`idle_ms` 在本地视频检查或文件发布阶段也会增长，只有结合 `stage` 才能判断是否在等待网络。进度采样只观测，不改变超时、回退或下载优先级。

## 可判定的验收范围

以下结果证据需要至少启用 Info；共享任务的精确关联、下载过程和调度细节需要 Debug。日志级别过滤导致事件缺失时，不能据此推断业务未发生。旧报告中的 `cache_capacity_rejected`、`batch_progress`、`metadata_sync_url_reject_failed` 属于当时实现，当前版本不再输出。v9 下载失败只影响本次执行与重试，不保存 URL 失效状态；地址规则见[媒体地址模型](song-catalog-design.md#媒体地址模型)。

1. 本地未命中：核对 `request_finished` 的状态、字节数和结果，并结合 `cache_task_finished` 判断任务结果；仅在预期完整视频持久发布时核对 `download_published`。例如零预算下普通视频的请求可以成功，任务结果为 `not_retained`，无需发布完整视频。需精确关联共享 flight 或查看实际发生的校验细节时启用 Debug，沿 trace 查找 `cache_task_attached` 和 `download_verified`。
2. 本地视频命中和 Range：核对 `request_finished.cache=HIT`、状态 200/206、范围及实际字节；HEAD 正文为 0 是正常情况。
3. 异常和中断：200 只表示响应头已发出。最终 `outcome=aborted/failed/canceled` 或写入错误不能算成功。一个小 Range 成功也不能证明整段视频已成功发布。
4. 队列与回退：以有序队列快照、代数、操作 trace 和实际线路为依据，核对取消、重试和最终结果；`queue_song_ready` 表示当次预加载成功，不保证以后始终留存。
5. 正常关闭：桌面主程序应有 `application_stopped`。缺少结束事件只能视为证据不完整或非正常结束的线索，不能推断崩溃原因。

日志只能支持服务端传输、校验、入库和任务调度的判断。实际 VRChat 播放、音画同步、切歌体验以及 UAC/托盘交互仍需游戏侧日志或现场验证。当前版本仍需联合实机验收，不能用旧构建的记录替代。

不记录请求查询参数、鉴权头或原始 VRChat 正文；预加载解析/下载的标准 URL 错误会去掉 URL，保留可用于判断取消和超时的底层错误。日志仍含本机路径、视频路径和网络错误，分享前应检查。容量清理可能丢失早期记录，复现后应及时复制日志目录中的分片，保留从启动到结束的一组证据。强杀、断电和其他 goroutine 的未恢复 panic 仍不保证留下原因。

非法重定向 `Location` 的解析错误可能由 `net/http` 将完整地址嵌入普通错误文本。此类错误统一显示为 `failed to parse Location header (URL details redacted)`，不保留地址或原始解析详情；错误关联仍保留，便于程序判断。地址解析、下载、版本确认、曲库接口与 DNS HTTP 请求都在返回此类错误前脱敏。
