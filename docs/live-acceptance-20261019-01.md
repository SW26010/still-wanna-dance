## #36：完整本地视频与正文放行

先重新校验三份完整 MP4 的 MD5，所有文件的 moov 均位于开头。夹具保持 Range、Content-Length 与正常 EOF 语义，额度用尽时暂停正文，不伪造短文件。仅 WMF GET 共享限额；解析器 GET 单独记录、未限额。计数是服务器 Write 接受的正文量，含 Flush 失败前被接受的字节，不能证明游戏已消费。区间合并值与重复传输总量分别保留。

| 场景 | 实际结果 | 判断 |
| --- | --- | --- |
| 正式 8935，不限量 | WMF `bytes=0-`，交付完整 21,996,300 字节；用户播放未见异常。游戏加载 1.876251 秒，另有世界主动等待 8.123749 秒 | 正常基线；不能将世界等待算成下载等待 |
| 预览 2502，不限量 | 前缀请求后改取 `bytes=10534912-80602638`；用户预览正常，约 20 秒起播 | 确认预览非零起点与取消/重连模式 |
| 正式 4598，256 KiB 长暂停 | 用户播放器错误；真实请求自动重试，解除额度后自动恢复正常播放 | 保留失败；长暂停超时干扰，不能作稳定下界 |
| 正式 4598，1 MiB，首个 WMF GET 后约 12 秒解除 | loaded 与 video-start 均在解除前，服务器已放行 1 MiB；用户未见异常 | 当前重复加载条件下的事件关联上界 |
| 正式 4598，512 / 768 KiB，同样约 12 秒解除 | loaded/start 均在解除后；用户最终未见异常 | 与 1 MiB 档形成事件关联区间，不能仅凭最终正常判断额度足够 |
| 预览 8935，两次 1 MiB 档 | 先前预览 GET/旧歌消耗共享额度，目标随后请求非零位置；用户约 1/3 起播、重复样本未见异常 | 两笔均不作独立预览起播阈值 |

4598 的观测支持 **大于 768 KiB、至多 1 MiB** 的事件关联供数区间，但不是普适的实际首帧最小值：同曲重复加载不能完全排除客户端内部缓存，人工反馈没有首帧同步。1 MiB 档另有解析器接受 180,224 字节重叠前缀，不能隐去；跨请求总传输量与唯一视频字节不同。

这组数据没有发现明显小于 1 MiB 的稳定起播额度，不足以据此证明“完整 1 MiB 块可读”带来显著的额外等待，也不足以决定修改正式下载器。#36 的正式/预览 GET 与供数证据已形成，预览最小额度和同步首帧测量仍有边界。

提交前复核修正了独立夹具的两处问题，详见[复核证据](evidence/live-20261019-01/probe-review.json)。汇总现仅将 GET 200/206 计入视频区间和歌曲字节，失败响应仍保留实际 Write 字节作诊断；用新旧汇总器重算全部 8 组原始日志，输出完全一致，本轮不存在 416 误计。当前夹具还会在等待正文额度前 Flush 响应头；历史二进制尚无此修复，不能追认成纯正文暂停。

原日志中，256 KiB 档的重试以及两笔预览各有一个新 GET 在额度已耗尽时进入，WriteHeader 到首次 Write 分别间隔 22.896、10.810、10.832 秒；这不是独立测得的网络响应头延迟，但结合回环回归说明头部可能一起等待。这三笔原本已排除出稳定阈值；512/768 KiB 和 1 MiB 正式对照没有此类新 GET，原事件关联区间保留。原始二进制、来源哈希和 v2 附件冻结保留；修复仅经过开发测试，没有补造新一轮游戏结果。

历史 1 Mbps 卡顿/不恢复失败继续保留。本轮两笔冷播放明确失败后均有实际重请求和带宽恢复后的起播，没有再现永久等待；不能据有限样本宣布所有慢网根因均已消除。低于媒体所需带宽不承诺持续不卡顿。
