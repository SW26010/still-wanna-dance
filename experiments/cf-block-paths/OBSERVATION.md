## A：已有会话核算

使用 `analyze_sessions.py` 读取原始 `product.json`，先复用原分析器的内容、顺序、字节和身份验证，再以同轮、同顺序的三个资源配对。`G = ordinary − strategy`，正值才表示节省。

- 主表同时列实际 `Started → Finished` 和会话开始到最后一次真实预取返回的墙钟。前者含独立文件复核及清理，后者不含最后一次外部文件复核，但包含此前任务间的记录保存。两者均包含实际承担的初始化等待，不由任务时长求和代替。
- 初始化加各任务秒表之和只作敏感性检查；本协议任务顺序执行，不能把此算法移植到并发会话。
- 保留到第 1/2/3 个任务的实际累计墙钟和额外正文；准备失败、业务失败、整窗失败及缺测全部显示。未完整成功的三任务会话不生成成功收益值，不借别轮或别歌补对。
- 晨间未固定 IP 的 v1 trace 不作路径归因；已完成的 v2 smoke 仅证明观测接线，不能冒充新的策略收益窗口。

预先固定的观测问题：

1. ordinary 成功媒体响应的真实远端、IPv4/IPv6、复用、CDN 状态及失败/重试；只有 hostname-verified TLS 记录可归因。未用过的候选不赋予优劣。
2. 每个任务的 API 请求时间区间、媒体请求时间区间、最后请求结束到预取返回的剩余时间。重叠请求采用区间包络，不求和当墙钟。
3. 收到响应头前的时间包含连接池、DNS、TCP、TLS、服务端等待；收到头至正文关闭也包含消费和关闭开销。现有 v2 没有独立首字节、纯建连、写盘和校验秒表，禁止给这些混合区间换标签。
4. 与同轮原方案比较实际会话总成本；各窗口分别报告，不用块数充当独立实验数，不以独立 smoke 增加策略样本。

只有发现重复失败、明显等待或可重复的选择缺口，才另行冻结低成本反馈实验。一次完整成功或某族被使用不证明该路径最快；本窗不新增被动评分、历史粘连、永久黑名单或额外 IP 回退。

## C：非游戏验证和下一次最小实机操作

先核对现有业务优先机制及受控回归：下载（含预取）在出站前登记资源活动，正文 Close 完成才释放；自动资源探测被业务抢占且中断不污染质量，释放后仅轻量重检；手动检查允许与业务并行。API/清单检查不在资源暂停范围内。这里验证机制和边界，不能声称已量化公网竞争或 VRC 首帧收益。

下次实机复用 LA-040 环境：

1. agent 准备独立配置、源码/EXE 指纹、Debug 调度日志、连续服务/游戏日志及进程采样，固定同一网络、路由、资源、正常配置和缓存条件；用户确认正式队列停止并关闭预览，避免旧播放器干扰。当前不提前启动服务、游戏或修改 hosts。
2. 对一首实际冷播记录播放动作、API、播放器 GET/Range、缺块排队/启动/完成、首正文交付、游戏开播事件与用户可见画面。首次使用条件以实际 GET 和本地块检查判定；304/已有块不能充当冷播。只有服务端时间时标为 Range/首正文中间指标，游戏回调也不直接等同精确首帧。
3. 在相同条件加入固定后台预取作为对照；保留操作次序和时间误差。先观察实际重叠及 `resourcesPaused`/检查状态；只有自动 Monitor 与关键路径确实重叠且值得解释时，另做实验隔离下的开/关对照。不要以手动 CheckThroughput 代替自动 Monitor，也不增加产品开关。
4. 如同期覆盖冷 Seek/未完成队首接手，共用采集；用户只承担游戏动作和音画反馈。agent 关联 `service_id`、`trace_id`、`resource_key`、`request_id` 与调度 block_key，区分播放器、解析器、队列和探测；CPU/帧时间用于核对竞争，流量与业务延迟共同计入成本。

现有采集入口为 `experiments/live-get-probe/{product-observe,capture-interaction,game-events}.mjs`，字段口径见 [日志](../../docs/logging.md)。`capture-interaction` 是旧事件白名单，不能直接作为新调度完整证据；开测前应针对本次需要纳入 `block_schedule`、响应头/首正文及 Monitor 状态，保留原始来源再脱敏。没有实际开测就不创建 LIVE 通过报告。
