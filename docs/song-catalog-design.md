# 曲库、资源关联与歌曲需求统计

更新日期：2026-11-07。Udon HTTPS 为歌曲资料的主来源；Udon HTTP、Kiva HTTPS 与 WannaInfo HTTPS 为同级完整备用清单，四个来源并行请求；HTTP Udon 复用 Udon 解析器，Kiva/WannaInfo 共用现有备选格式适配器。改造依据及分组验证见[决策记录](research/udon-catalog-decision-draft-20261029.md)。

当前数据库为 v9，按[媒体地址模型](#媒体地址模型)把地址归属于 media。合法 API 响应在同一事务更新资源、地址及本次歌曲映射；实际提交顺序决定覆盖，旧时间与失败规则仅属历史。

当前需求与资源边界见[下载需求与资源管理设计](download-resource-design.md)，演进背景见[早期加载设计](history/song-loading-design.md)。

本文维护曲库、资源关联与需求统计模型；存储格式及旧版本拒绝规则见[存储契约](storage.md)。

歌曲屏蔽与收藏独立保存，其业务规则以[下载需求与资源管理设计第 8 项](download-resource-design.md#8-歌曲屏蔽与收藏)为准，不改歌曲评分或统计含义。

## 目标与范围

优先永久保存歌曲 ID 到当前 MD5 的映射，同时保留歌曲资料供后续使用。原则是最小必要、职责分离、标准约束和可维护性，沿用 SQLite 与现有驱动，不引入新数据库、通用同步框架或自制版本系统。

“增改不删”定义为：新增记录、更新已有记录，上游清单缺席的记录保留；不要求保留每次修改前的值。歌曲资料、资源记录、当前映射和日常歌曲累计统计均适用。用户明确确认的 [VRCX 历史初始化](#vrcx-历史初始化)可整表替换歌曲统计。本地视频存储和请求日志仍按各自保留策略清理。

本轮不保存历史歌曲—视频关联、不保存完整清单快照，也不实现面向游戏响应的歌曲列表故障兜底。当前在业务启动前静默一次性迁移受支持的 v8，普通业务仍只读写 v9，更早格式及异常库拒绝并保留，详见[v8 到 v9 的静默迁移](storage.md#v8-到-v9-的静默迁移)。

### 干净重构，不保留过渡架构

直接围绕新模型重构数据库结构、领域类型、读写入口及所有调用方，不为旧结构保留兼容视图、旧表名别名、双写、旧格式业务读取分支或过渡适配层。旧业务数据只在打开入口经 v8→v9 一次性迁移转换；已确认删除的历史累计不作转换，详见[迁移范围](storage.md#v8-到-v9-的静默迁移)。

旧模型被替代后，删除旧结构的业务建表、查询和写入实现，清理废弃接口及不再适用的旧业务测试；保留 v8 冻结 DDL、样本及迁移所需的结构校验和测试。新业务测试验证新模型和本设计要求。不把新表包装成旧模型继续使用，也不让新旧两套实现长期并存。沿用现有 SQLite、驱动和仍适用的下载、文件校验及并发保护机制，不重复实现已有能力。

数据库打开按所选文件的格式版本与结构校验，仅将受支持的 v8 原地迁移为 v9，不推断历史布局或迁移其他旧格式。视频管理只处理当前格式的正式文件名，其他文件原样保留；目录类型、独立资源锁、恢复文件及工作区清理边界遵循[存储契约](storage.md#数据库打开约定)与[运行生命周期](runtime-lifecycle.md)。不授权删除用户已有资料。

## 数据职责

四张核心表分别保存一类事实：

| 表 | 唯一职责 | 主键 |
| --- | --- | --- |
| `songs` | 歌曲资料 | `id` |
| `media` | 视频资源属性 | `md5` |
| `song_media` | 歌曲到当前视频的映射 | `song_id` |
| `song_usage` | 本地歌曲需求统计与衰减累计值 | `song_id` |

`catalog_members` 单独保存已接受完整清单的当前成员；`catalog_state` 保存歌曲清单来源及版本，不存清单正文或歌曲副本。内置资源只在建库时导入，不保存导入状态，见[清单版本记录](#清单版本记录)。请求明细、流量统计、文件校验继续独立承担原有职责，不属于这四张核心表。

### songs：歌曲资料

**2026-11-01 已确认，v9 保留 `songs` 的全部现有字段、类型及约束。** 用户希望尽可能保留已接收的歌曲清单资料；即使部分字段目前没有业务读取，或 v9 不再计算清单摘要，也不因此删列。清单解析和归一化继续遵循现有规则。

明确的标量使用原生列，名称和语义对齐 Udon。父级共有的分组名称和 major 拍平；Kiva/WannaInfo 共用适配器。不保存完整歌曲 JSON、完整分组树、标签翻译、顶层新歌集合或冗余 danceid。

| 列 | SQLite 类型 | 来源适配 |
| --- | --- | --- |
| `id` | INTEGER PRIMARY KEY | 正整数歌曲 ID |
| `name`、`artist`、`dancer` | TEXT | 同名字段 |
| `playerCount` | INTEGER | 同名字段 |
| `volume` | REAL | 两种格式统一为 float32 可表示值，消除 Unity 序列化的小数差异 |
| `start`、`end` | REAL | 同名播放起止参数 |
| `flip` | INTEGER | 同名布尔值 |
| `double_width` | INTEGER | 备选 doubleWidth |
| `skip_random`、`disable_public` | INTEGER | Udon 的 0/1 与备选 skipRandom/disablePublic 布尔值统一 |
| `rpe` | INTEGER | 同名字段 |
| `major` | TEXT | 父级 major |
| `groupName` | TEXT | Udon 父级 groupName／备选父级 title |
| `tag` | TEXT | JSON 数组；清单显式 null 表示空数组 |
| `shader_motion` | TEXT | JSON 数组；Udon 空字符串规范化为空数组，备选 shaderMotion |

不再保存备选独有的 genre、composedTitle、composedTitleSpell、ayaId、originalUrl。标题直接使用 name。未知字段忽略，不建立扩展 JSON 或额外集合表。两个逐歌数组整体保存并校验形状，其他标量保留 NULL 与已知零值的区分。

歌曲可先由播放观察发现，因此允许只有 `id` 的占位记录；占位歌曲不自动进入 `catalog_members`。布尔列仅接受 NULL、0、1。接受完整清单时完整写入定义字段，不能用缺失值维持更旧的歌曲资料。

`checksum` 只作为备选资源证据写入 media/song_media，不进入 songs。Udon 无 MD5 的完整清单同样可接受。

### media：资源属性

| 列 | 类型与约束 | 用途 |
| --- | --- | --- |
| `md5` | TEXT PRIMARY KEY | 小写 32 位十六进制内容标识 |
| `byte_size` | INTEGER NULL | 已知文件字节数，正整数；未知用 NULL |

MD5 同时是资源身份和正式文件名 `videos/{md5}.mp4` 的依据，不重复保存内容版本键或源路径。完整视频地址保存在 `media_urls`，不从资源属性拼造地址；旧清单摘要只保留在冻结历史中。

资源记录不等于文件本地已有。清单提供 MD5 时即可创建记录，是否存在文件仍由文件系统检查决定。多个歌曲可以共用一个资源；播放参数属于歌曲，不能放到共用视频上。

### song_media：当前关联

| 列 | 约束 |
| --- | --- |
| `song_id` | INTEGER PRIMARY KEY，外键关联 `songs.id` |
| `md5` | TEXT NOT NULL，外键关联 `media.md5` |

每首歌最多一条当前关联，没有已知关联时不创建该行。为 `md5` 建普通索引，支持反查当前歌曲和汇总资源分数。外键检查必须在数据库连接上实际启用，不使用级联删除。

歌曲从 A 更新为 B 时直接更新这一行。不保存 A 曾经属于该歌曲的关系，也不维护 `is_current` 标志、历史关系表或歌曲表中的 MD5 副本。A 的资源记录和文件可以继续存在；无当前歌曲引用时，其保留分数为零。

### song_usage：歌曲需求统计

| 列 | 类型与约束 | 用途 |
| --- | --- | --- |
| `song_id` | INTEGER PRIMARY KEY，外键关联 `songs` | 统计归属 |
| `demand_count` | INTEGER NOT NULL，非负 | 累计有效需求次数 |
| `demand_score` | REAL NOT NULL，非负 | 上次有效需求时的指数累计值 |
| `last_demand_at` | INTEGER NOT NULL | 对应时刻，Unix 毫秒 |

无需求时可以没有统计行。占位歌曲和第一条统计应保持外键一致。统计独立于清单更新、MD5 更换和文件删除；不将统计写进歌曲资料或关联表。

### song_preferences：本地歌曲偏好

`song_preferences` 只保存用户对歌曲的屏蔽或收藏标记，普通状态无记录；精确 DDL 和版本约定见[歌曲偏好存储](storage.md#歌曲偏好存储)。它独立于上游资料及需求统计，清单同步、MD5 更新、VRCX 初始化和文件清理均不覆盖偏好。

资源策略根据当前 `song_media` 关联推导，不复制 MD5 偏好或修改需求分数。收藏只影响保留资格，不代表下载需求、已保存状态或实际播放统计；共享、预算及生效规则统一回到 canonical 第 8 项，不在本页维护第二套规则。

## 媒体地址模型

**当前实现（2026-11-01）：数据库 v9。** 以下规则替代旧歌曲地址归属、查询时间排序、24 小时复用和失败失效策略。字段以[存储契约](storage.md#媒体地址存储目标)为准，开发验证见[v9 开发验证](validation/storage-v9-20261101.md)。

### 关系与职责

实际视频 URL 对应固定 media，关系为 `song → song_media → media → media_urls`。多首歌可共用一个 media，一个 media 可有不同节点的地址。`/Api/Songs/play?id=...` 是按歌曲查询的解析入口，与其返回的视频 URL 分开理解。

以 `media_urls` 完整替换 `song_urls`，只保存 `md5、node、url`，主键为 `(md5, node)`。同一资源、同一节点保留最后写入的一条完整 URL；不同歌曲取得同一资源同一节点的地址时共用该行。这会合并原来按歌曲分别保留的同来源地址，接受候选数量减少的取舍，不新增地址历史或多候选保留机制。

- `media` 继续保存 MD5 与大小；`song_media` 继续只保存歌曲到当前 MD5 的关联，不加查询时间或“已确认”标记。
- `node` 保存实际 API 参数，来源许可继续由 `playbacksource` 统一定义，当前只允许 CF；node 不保证返回 URL 的实际 CDN、域名或 IP。
- API 入口由现有播放来源模块管理。当前只有一个播放 API 体系，地址表不再保存 `api`，也不保留 HTTP/HTTPS API 字符串的重复身份和兼容行。
- 不保存 `song_id`、`query_song_id`、`query_started_at`、`observed_at`、`failed_at`，不改用布尔失效标记或另建观察版本。资源大小不在地址表重复保存。
- 地址记录不证明视频已下载或当前请求一定成功。完整 URL 原样保存供请求使用，实际协议执行、来源校验及日志脱敏沿用各自规则。

### 写入与更新

取得合法的播放 API 结果后，从实际视频 URL 解析 MD5 和大小，在同一事务中补 `media`、更新 `(md5, node)` 的 URL、补缺失的 `songs` 占位行，并更新本次查询歌曲的 `song_media`。无需等待视频正文或文件发布；存储失败整体回滚，沿用现有映射锁、外键和存储故障处理。

有效结果按实际提交顺序覆盖，不再按查询发起时间比较新旧，也不把这套排序移到 `song_media`。请求时间不是上游资源版本；接受并发请求乱序完成可能覆盖映射或地址的取舍，后续成功查询继续更新。清单版本水位及其并发保护不受此决策影响。

| 事件 | 目标行为 |
| --- | --- |
| 查询歌曲 S 返回 media B | 只更新 S 的当前关联，并写入 B 的属性和地址；不推断其他歌曲也切换到 B |
| S 从 A 改为 B | A 的地址仍归 A，保留其记录；仍关联 A 的其他歌曲继续共享 |
| 同一 media、node 返回另一 URL | 更新同一行，不保留全部历史 URL；新地址不构成旧地址已失效的证明 |
| 读取已有 URL | 只取得资源地址，不作为新的 API 结果，也不据此更新歌曲关联 |
| API 查询失败、取消或返回不合法内容 | 不覆盖已有资料，不清空已有地址 |
| 视频下载失败 | 仅影响本次执行、重试和错误反馈，不删除或标记数据库中的地址失效 |
| 纯视频 URL 请求或下载完成 | 沿用资源属性写入；明确歌曲 ID 的完成记录只补关联空缺，不覆盖已有映射，也不凭空填写 API node |
| 本地视频删除或失去当前歌曲引用 | 地址及资源资料保留；文件存在性、资源分数和保留资格仍按各自规则判断 |

### 地址使用、刷新与后台补齐

不假设 URL 有固定期限，不设 TTL、后台续期任务或“年龄过大”筛选。各入口复用地址读写和 API 响应入库机制，并按操作需要查询；普通播放、队列以及实际开始补齐的明确歌曲使用时会后台检查更新，测速按[测速地址恢复的取舍](upstream-channels.md#测速地址恢复的取舍)处理。一次业务加载中的并发请求复用查询，不对每个 Range 或下载块重复查 API，也不为本次改造扩展检测和测速的请求频率。

普通播放、队列已有本地资源时立即使用，后台查询继续更新；缺本地文件但已有地址时可先尝试该地址，缺地址或本次候选耗尽时等待解析结果。刷新不替换已经确定资源身份的在途响应。歌曲入口通过当前 `song_media` 查对应 media 的地址，资源入口直接按目标 MD5 查地址；来源过滤先于候选数量限制。

批量补齐复用已有地址时，并行检查本次明确歌曲的播放 API；已有地址的下载不等待该查询，合法结果更新后续映射，当前任务仍固定原 MD5。任务完成前被取消时，仅由该任务使用的查询随之取消；已被其他调用复用过的查询沿用服务生命周期，任务正常完成后的后台检查也可继续。同一次任务重试复用已发起的查询及其结果，即使歌曲映射已变化也不遗漏，不因查询已完成再查一次。纯扫描、批量筛选时已跳过的完整文件不触发检查；没有明确歌曲的资源补齐只在需要地址时按当前关联解析。

歌曲入口已有明确 song ID 时直接用它查询，缺映射歌曲也可正常解析。按固定 media 刷新地址、需要寻找查询歌曲时，只从当前 `song_media` 反查，不保留历史查询歌曲线索。固定资源没有当前关联时仍可使用本地文件或已有地址；这些途径不能满足请求时，明确反馈无法取得所需资源，不猜测歌曲或另建历史关系。查询得到其他 MD5 时，可正常更新被查询歌曲的映射和新资源地址，但固定 MD5 的预览、补齐或重取不能切换目标。

后台补资料检查 `song → media → URL` 的完整链路：缺映射、资源大小未知（`media.byte_size` 为 NULL），或对应 media 缺少当前允许节点的合法非空地址时，才是待查候选。v9 的已知大小按存储契约约束为正整数。一个资源地址补齐后，所有当前关联歌曲共享这项完整性；不要求每首歌都单独通过 API 确认。链路完整不保证映射永远最新或网络一定可达，后续实际查询自然更新。下载失败不把完整链路持久化为缺项，也不产生另一套失败补齐队列。候选评分、每遍公平尝试和正常抽样沿用现有机制。

| 调用方 | 需统一落实的边界 |
| --- | --- |
| 播放、队列 | 复用资源地址；查询生命周期、准入、共享下载和取消责任保持原约定 |
| 固定资源预览、已固定 MD5 的补齐及重取 | 地址必须满足目标 MD5 及大小；新映射不能改变本次目标，保持既有候选预算和重试上限 |
| 检测、Monitor、手动下载测速 | 已取得的 API 响应交给统一写入入口；地址候选按 media 读取和去重，不再依赖地址自带歌曲 ID、时间排序或失败标记 |
| 测速准备与执行 | 保留已有地址优先、缺样本才解析、准备后再下载的生命周期；下载失败计入本轮结果，不调用地址失效写入；重复测速的限制见[测速地址恢复的取舍](upstream-channels.md#测速地址恢复的取舍) |
| 歌曲统计、偏好与播放参数 | 使用本次业务请求的歌曲身份；B 复用通过 A 取得的地址，不把 B 的需求、屏蔽或播放参数归给 A |
| 文件、块与保留策略 | 沿用 MD5 身份、内容校验、预算、保护和共享机制；本次不改调度器或清理视频文件 |

失败时继续使用现有有界重试、候选去重和错误反馈，本次已失败的地址不在同一次尝试中无限重入。内容或长度校验不符仍按现有校验边界拒绝，不据此额外推断 URL 本身失效或改写地址记录。

### 不显式判定 URL 失效的依据

当前没有已核实的上游契约或可识别信号能证明 URL 本身已失效。下载错误、HTTP 状态、内容校验失败与 API 返回新 URL 都不足以单独支持持久化删除或失效标记；未来取得可靠证据后再讨论对应规则，本次不预留失效字段或处理分支。

- [2026-10-15 元数据采样](research/video-metadata-20261015.md#信息从哪里获得)记录的 264 条 URL 参数只有 `e`（MD5）和 `s`（大小），没有显式到期时间；不由此断言地址永久可用。
- [2026-10-07 实施记录](history/implementation-progress-20261007.md)中的 24 小时是本地复用策略，不是上游签名有效期的保证，不能据此要求新模型继续保存观察时间。
- [Wi-Fi 实测](validation/wifi-ip-selection-20261029.md)出现同一 URL 在一个 IP 上返回 403、其他路径仍可读取同一内容的反例；不能把路径失败当作资源整体失效。
- [测速验证](validation/calibration-candidate-validation.md)中的 404 失效来自受控夹具，只证明当时设定的标记行为。旧版一般下载失败后调用 `RejectSongURL` 同样是实现策略，不是上游失效证据；这些记录保留，不作为新规则的验证结论。

### 实施边界与验证要求

本次实现一起替换了数据库结构、领域类型、地址读写入口、元数据候选查询、各调用方及相关测试；不保留 `song_urls` 别名、兼容视图、双写、时间排序或失效接口作为过渡层。仍使用现有 SQLite 与事务机制，不新增数据库、配置项或后台定时器。按[存储格式约定](storage.md#媒体地址存储目标)提升到 v9，在唯一可写打开入口[静默一次性迁移 v8](storage.md#v8-到-v9-的静默迁移)；其他旧版本拒绝，业务只读写 v9。v8 冻结 DDL 和二进制样本保持原样。

开发验证覆盖要求如下，执行结果与限制见开发验证记录：

1. 多歌共享 media、同节点地址覆盖、不同节点隔离；新增或更新任一步写入失败时事务全部回滚，外键继续生效。
2. 歌曲换 media 只更新本次歌曲，旧资源及地址仍可使用；并发结果按实际提交覆盖，不再断言按发起时间拒绝迟到结果。
3. 无时间字段仍可跨重启复用地址；失败、取消及模拟 403/404/5xx、超时或内容异常不删除/标记 URL，重试有界，失败不被当作成功，校验不符的完整文件不被发布。
4. 完整链路共享判定、缺映射/大小/允许节点地址的候选；缺映射歌曲仍按明确 ID 解析，固定资源没有当前歌曲可反查且无可用文件/地址时正常失败；不依赖查询来源歌曲或观察时间。
5. 播放、队列、预览、批量补齐、重取、检测和测速共用新模型；本地立即复用、在途 MD5 固定、歌曲身份和取消责任不退化。
6. 新建与迁移后的 v9 通过同一结构/外键检查，v8 静默一次性迁移并保留用户资料，v2～v7、未知及未来格式拒绝并保留原文件；`media.byte_size` 接受 NULL 和正整数，拒绝落库为 0、负数或非整数，迁移将旧 0 转成 NULL，缺失大小不抹掉已知值；历史测试只保留仍有业务意义的覆盖，移除把 24 小时或失败标记当成上游事实的断言。
7. 按存储契约同步删除 `catalog_state.digest/accepted_at`、`request_events.host/file_bytes/cache_result`、`song_playback`、`traffic_totals`、`catalog_checks` 和 `request_observation` 整表及其专属读写、摘要比对、计数、去重与累计逻辑，清理历史接口的 cache、状态接口的整个 traffic 投影、清单检查持久化投影及首正文覆盖状态 availableFrom/partial；清单版本选择、歌曲需求与优先级、请求历史的身份/结果/交付比例继续使用各自的保留字段，运行期响应头不变。
8. 来源总览按当前保留明细现场汇总，明细清理后统计相应变化；覆盖空明细、失败/取消的已计入贡献、先加字节再计算占比及重启重算，并验证实际数据规模下的查询耗时。首正文统计仍是最近 72 小时的现场分组查询，保留 P50/P95、样本数和空组提示，取消“数据不足 72 小时”覆盖提示；验证不依赖采集状态表、短保留期/不保留明细及重启后的查询。
9. 删除清单检查表后，前台更新失败、自动检测的解析/校验/入库失败仍有当前反馈；已有本地清单时继续展示可用数据，备用成功的静默完成及错误清除遵循[清单检查反馈](#清单检查反馈)。已取消的同版本内容冲突不再作为失败反馈。清单事务失败仍全部回滚，成功及旧版本补缺分支仍完成提交；重启依据已接受版本判断初始化，不恢复上次清单检查错误，不借旧快照重建检查状态。
10. catalog_state 以 `songs_list` 键保存歌曲清单来源和版本，读取、写入及初始化判断一致使用新键；v8 冻结样本仍保留旧键 `songs`。仍跨歌曲清单来源比较新旧，同版本 HTTPS Udon 替换备选、备选不替换已接受 HTTPS Udon；同版本同优先级即使正文变化也保留资料和成员，不报摘要冲突、不因此尝试备用，合法资源补缺仍生效。不重建摘要判定，候选完整校验和归一化仍执行。
11. 内置资源资料只随显式新建库初始化：覆盖桌面新建、空库初始化失败的事务回滚与不误认成功、已有库打开/重启/选择及更换内置包后的原样保护；v8 迁移保留已有资料，不重新注入预置，且不写 media_seed 行或替代导入标志。播放 API 观察和备用清单按现有业务规则仍可更新或补缺。更新内置初始分数时，无本地需求歌曲采用新版默认分数，有有效本地或导入需求的歌曲继续使用本地分数、不改写需求累计。
12. `songs` 全部现有资料字段及约束在 v9 保持，包含当前没有业务读取的上游字段；完整清单解析、写入、空值和数组归一化、重启读取均不因摘要删除而退化。

验证按[现行机制](live-acceptance-process.md)由开发者先完成自动、隔离服务和必要浏览器检查；仅在实现后发现必须依赖 VRC 的剩余风险时合并到实机台账，不因这次设计记录自动新增游戏操作。

## 需求计分与优先级

歌曲统计来源为 SWD 观察到的明确歌曲 ID 播放 GET，以及用户显式执行的 VRCX 历史初始化。直接视频 URL 请求即使能反查到一个或多个歌曲，也不推断歌曲、不增加歌曲次数和热度。HEAD、后台检查、批量下载和预加载不增加热度。这里统计可识别需求观测；VRCX 播放事件不等于 SWD 拦截的 GET，两者都不声称确认完成播放。

同一歌曲跨线路、跨资源的需求，以前一次有效需求为锚点做 30 秒去重。窗口内重复请求不推进计分时间；时间回拨到最后有效需求之前时不增加次数或分数、不回拨时间。

半衰期固定为 60 天。第一次有效需求记次数 1、分数 1；后续有效需求更新为：

```text
新分数 = 旧分数 × 2^(-间隔天数 / 60) + 1
新次数 = 旧次数 + 1
```

查询时将累计分数衰减到查询时刻，不写回数据库，不运行每日全表衰减任务。累计次数保留为个人需求数据；当前产品查询用它判断是否已有实际需求，界面不展示具体次数，次数不参与评分公式。统计更新应原子完成，避免并发重复计数或丢失累计值。

歌曲没有实际需求时使用现有内置初始分数，没有初始分数时为零。有实际需求后，其衰减累计值完全替代初始分数，衰减再低也不重新启用初始分数。初始表不写入本地需求统计；软件更新可带来新的默认分数，仅影响仍无有效本地或导入需求的歌曲，有需求的歌曲继续使用本地累计值。

资源优先级通过 `song_media` 汇总所有当前关联歌曲的有效分数，每个歌曲 ID 只计一次。无关联资源为零分；不另存资源热度累计值，不持久化两套下载分数与淘汰分数。

- 批量补齐优先高分资源；同分沿用歌曲 ID 从大到小的稳定排序。
- 容量淘汰优先低分资源；同分先按关联歌曲最大 ID 从小到大，无关联视为 0，再按资源最近有效歌曲需求时间、文件修改时间和路径稳定排序。资源最近需求由关联歌曲统计派生，无歌曲需求时使用文件修改时间，不依赖纯视频请求统计。
- 活动请求、下载、队列和交接保护仍优先于分数，沿用现有保护机制。

下载与淘汰共用同一个有效分数计算入口及汇总规则，避免两处公式和初始分数处理逐渐分叉。请求明细和流量统计可以继续记录直接视频请求，但这些记录不参与歌曲计分，也不需要保留 MD5 级热度来维持排序。

## 清单同步与增改不删

前台刷新与统一上游检测同时请求 Udon HTTPS、Udon HTTP、Kiva HTTPS、WannaInfo HTTPS。主来源 Udon HTTPS 一旦完整读取并校验成功，立即交给既有入库入口，即使备用已先返回或版本更高；取消其余仍在进行的清单请求，并等待请求清理完成。统一检测保留已完成的备用观测，被取消的备用显示未使用，不生成延迟或观测时间，也不改变选择或入库。主来源失败或内容无效时，等待全部请求结束，从有效备用中选择最新版本；同版本同优先级按上述来源定义顺序稳定选取，不按响应先后决定。每轮只提交选中的清单，已接受的本地较新资料不回退；同版本入库规则仍见下表。

预置资源在新建数据库时初始化，之后可由播放 API 补齐，已有清单同步取得的备用资料仍按原规则补缺。备用清单保留完整资料，Kiva/WannaInfo 仍可提供资源映射；本地存储错误或取消会停止并清理请求，不触发兜底。直连 Monitor 仍只检查 Udon HTTPS；各入口均复用已取得正文、完整解析和 SyncCatalog，不重复请求同一正文。固定协议与执行边界见[上游通道](upstream-channels.md#业务请求的协议策略)。

同意条款后，Console 启动统一上游轻量检测，自动周期与手动入口共用清单请求、播放地址解析、补齐进度及检测结果；`catalogsync` 管理业务选歌和当前清单错误，不再拥有网络或定时循环。直连、SOCKS5、Mihomo 均适用；访问方式、5 分钟周期和首次清单退避统一见[上游检测](upstream-channels.md#上游检测与测速)。网络失败、正文无效或未成功入库都不能结束初始化；完成依据为 `catalog_state` 的完整歌曲清单版本（旧 v8 键为 `songs`，v9 键为 `songs_list`），预置映射、占位歌曲及视频导入不能替代。重启从数据库重新判断，无持久化初始化标志。界面的 `catalogSync` 将统一检测的初始化、运行和下次执行状态与 Store 的业务更新时间组合展示，不借用 Monitor 状态。

业务更新时间由 Store 在清单同步（`SyncCatalog`）、播放 API 观察（`ObserveSongURL`）或歌曲关联（`recordSongMapping`）事务实际改变记录并成功提交后推进，只保留本次 Store 会话内的时间，不新增持久化字段。重复的相同清单或地址不重写相同记录，也不发布曲库变化；旧清单若实际补齐映射，仍发布变化。成功检测的观测时间、地址来源的运行期有效期及当前清单错误继续独立更新，不能用业务更新时间代替。事务失败或回滚不发布变化，曲库页面据此按需重读，读取状态本身不访问数据库。

初始化确认完整清单可用时，若没有有效覆盖率快照，则通过现有扫描生命周期从本地清单和视频目录计算一次覆盖率，不再次联网、不启动视频引擎；已有有效快照保持不变。视频目录不可用不撤销已完成的清单初始化，覆盖率显示实际文件检查错误，可手动重试。后续周期同步不重复扫描覆盖率，普通更新与导入语义保持不变。

| 事件 | 处理 |
| --- | --- |
| 合法较新完整清单 | 同一事务更新歌曲资料、替换 catalog_members 和推进歌曲清单水位；资源另按补缺规则处理 |
| 同版本不同来源 | HTTPS Udon 优先；Udon HTTP、Kiva HTTPS、WannaInfo HTTPS 同级，保留先接受的资料，合法资源仍可补缺 |
| 同来源或同级备选同版本内容不同 | 视为已处理，保留资料与成员，不报内容冲突，仍可补资源缺项 |
| 旧备选清单 | 不更新歌曲资料和成员；合法 MD5 仍可新增 media、占位歌曲和缺失映射 |
| 本次清单缺少某 ID | 歌曲、映射、资源、偏好和统计保留，仅退出当前成员集合 |
| 备选 MD5 与已有映射不同 | 新资源仍可入库，已有映射保持；清单版本不代表每首歌的 MD5 同步程度 |
| 新取得的有效 API URL | 在同一事务保存 URL、资源属性与当前映射，可覆盖已有映射 |
| API 查询顺序 | 合法观察按实际事务提交顺序更新映射及资源地址，不保存查询时间 |
| 纯视频 URL 或下载完成 | 可补资源属性，明确歌曲 ID 的完成记录只填映射空缺，不撤销新 API 观察 |
| 本地视频被淘汰 | 只删文件，保留业务数据 |

来源不复制业务表，不为每条映射增加来源字段。API 观察不改变正在传输的 MD5；本地命中仍立即返回，后台查询只影响后续请求。旧 URL 缓存读取不是新观察。

完整候选校验时间、结构、唯一正数 ID、共同字段类型；备选还须校验每条 MD5。任何无效候选不部分写入。未知资源大小保持 NULL，补 MD5 不抹掉已知大小。

`catalog_state` 只保存完整清单的来源和版本，所有来源共用 `songs_list` 水位。完整校验和归一化仍执行；删除摘要不改变歌曲字段的保留和替换规则。同版本同优先级正文变化视为已处理，不因此报错或触发备用。

观察到备选版本高于 HTTPS Udon 时，后台警告包含双方版本、来源及观察时间，不阻止接受较新清单。只对已经取得的合法候选比较，不把 HTTPS Udon 失败解释为备选较新，也不增加独立探测。观察时间只用于诊断，不取代清单版本。

### 清单版本记录

**当前数据库 v9。** `catalog_state` 只保留 catalog_key 主键及 source、revision 两项信息，业务仅写歌曲清单 `songs_list` 行，不再写 media_seed 行；读取和写入均使用新键，旧 v8 仍使用 `songs`，字段和新建库行为见[存储目标](storage.md#单行状态与清单水位)。各清单入口继续跨来源比较版本：先判断新旧，相同版本时仅 HTTPS Udon 优先于备选。2026-11-07 起 Udon HTTP 与 Kiva/WannaInfo 同级，已有 HTTP Udon 水位也按备用处理，无需数据迁移；不新增每来源历史水位。

删除 digest 及同版本内容差异判定。同版本且来源优先级相同就视为已处理，保留现有歌曲资料与成员，即使正文变化也不报内容冲突、不因此尝试备用；备选的合法资源及缺失映射仍按原规则补齐。HTTPS Udon 同版本替换已接受备选仍可更新资料；较新版本正常接受，较旧版本不回退。本地接受时间 accepted_at 同时删除。摘要不转存、不现场重算，不另建一致性标志；候选仍须通过完整格式、ID、字段类型和资源身份校验。

内置资源资料只在明确新建数据库时初始化一次，与建表及版本标记在同一事务提交；不再向已有库导入软件更新携带的预置资料，也不保存 media_seed 导入版本或任何替代标记。初始化失败不得留下可被误认为成功的新库；失败文件及恢复材料按既有规则保留。预置不建立当前成员或歌曲清单水位，软件更新不通过预置改动已有歌曲—资源映射；之后真实 API 观察和备用清单仍执行各自已确认的更新/补缺规则。内置初始分数仍是查询时的默认值，仅用于没有有效本地需求的歌曲。取消运行期摘要判定不涉及构建产物登记和生成输入的既有校验资料。

### 清单检查反馈

**当前数据库 v9。** 删除 `catalog_checks` 整表及其 checked_at/message/error 接口投影，不将它们搬到其他表或状态文件。页面的最后检查时间来自库存扫描结果，当前错误由操作或同步状态提供。删除检查表不取消清单版本选择、成员集合和初始化判断，这些仍依据业务资料及 `catalog_state`；同版本内容冲突检测则已按[清单版本记录](#清单版本记录)另行取消。

清单获取、解析、校验和入库失败继续记录诊断日志；用户反馈以本轮是否取得可用清单并完成同步为准。任一来源同步成功即静默完成，不提示备用切换或来源成功，也不保留该轮其他来源的错误提示；这类失败已由备用来源处理，用户无需操作。较旧或同版本低优先级的合法备用清单完成补缺、保留当前版本时，同样视为成功。所有来源都失败时仍显示当前错误，并继续使用已有可用清单；本地存储故障继续通过原故障通道报告，不能被其他来源的成功掩盖。

成功轮次清除当前同步错误，取消或未取得任何清单响应的轮次不视为成功。各来源失败的排障细节沿用现有日志，不新增错误历史、成功通知或持久化诊断框架。此规则替代此前要求在备用成功时仍向用户展示同轮失败来源的约定。

清单错误通过当前操作与 `catalogsync` 内存结果反馈，不再调用持久化检查接口；较新、相同及旧版本补缺分支仍完成事务提交或失败回滚。曲库当前同步错误统一读取 `catalogSync.error`，手动更新不再向库存错误复制一份；库存只保留本地扫描和覆盖率读取错误，后台同步恢复不能清掉这些独立故障。CatalogStatus、接口和库存/批量快照不保留检查表的专属字段，重启不恢复全局清单检查错误；既有任务自身的历史结果继续按原任务快照规则保存，但不作为当前检查状态。已接受的清单仍可离线读取，初始化仍从歌曲清单水位判断，不新增持久化标志。

## VRCX 历史初始化

WebUI 同意条款并取得程序状态后，仅检查默认 `%APPDATA%\VRCX\VRCX.sqlite3` 是否为现存文件；不打开源数据库，不读取表结构、记录数量、时间范围或历史内容。默认文件存在、当前 SWD 的 `song_usage` 为空且用户尚未忽略时，曲库显示「检测到 VRCX 历史，可用于安排歌曲下载与保留顺序。仅在本机处理。」及「导入历史 / 忽略」。曲库建议不局限于首次建库进程：重启、重新打开已有空库或新建空库后仍可显示，直到首次写入歌曲需求统计或用户忽略。资格随既有程序状态刷新更新，不额外增加轮询；请求明细的保留与清理不影响判定。

Toast 仅在首次自动建库的本次运行、且当前不在曲库时显示一次「检测到 VRCX 数据库」，说明确认前不读取内容，并提供「前往曲库」链接；链接只导航，进入曲库后撤去 Toast，不重复弹出。重启或打开已有空库不再触发 Toast，曲库建议仍按上述条件保留。Toast 不自动超时，等待用户点击「前往曲库」或关闭通知；同一标签页用 sessionStorage 只记已提示标记，刷新不重复，不保存路径或历史内容，浏览器存储不可用时仍在当前页面内去重。检测及导入共用同一份前端模型，不因切页再次检测。

检测受条款和既有请求门禁约束。忽略属于当前配置实例的界面选择，原子保存为主配置的 `vrcxImportDismissed=true`，不进入可编辑运行设置或触发重启；缺失或 null 默认为 false，普通设置保存保留该字段，切换数据库或视频目录不重置忽略。保存失败保留原选择和建议并允许重试，不创建额外状态文件或数据库表。关闭 Toast 只关闭通知，曲库建议仍保留。缺少默认文件或检测失败时不弹出提示，手动入口始终保留。

只有用户点击「导入历史」后才读取默认源库，复用下述预览聚合和导入事务；有效结果且目标统计仍为空时直接提交，无需额外预览或确认。读取后发现已有统计则转到原预览界面，最终覆盖仍需明确确认；提交时出现新需求则拒绝并要求重新预览。无有效记录不提交，读取失败在提示区域反馈，提交失败或结果未确认时保留原导入机制的核对入口；不自动重试或持续同步，不记录“曾有统计”的重复状态，不改变数据库或配置格式版本。

曲库中的「导入 VRCX 历史」提供只读预览与导入。标题下方以正文说明“读取 VRCX 中的 WannaDance 播放记录，计算歌曲需求分，用于安排视频下载和保留顺序。”空统计的提交按钮为“导入需求记录”；已有统计时，预览及确认弹窗均说明将替换已有歌曲需求统计，不会与原统计累加。导入表单直接显示，不提供启用复选框；打开页面只检测默认文件与当前歌曲统计状态，点击“读取并预览”才读取历史内容。点击只读路径框直接通过 Windows 文件选择器选择数据库，旁边提供“恢复默认”；默认路径以灰色显示，自选路径用正文色，恢复默认释放旧预览。支持手动预览和即时导入；预览展示数据源、目标、数量、时间范围和跳过原因；统计信息在桌面以两列信息组排列，窄屏回到单列。已有非空统计在最终导入时确认整体覆盖。预览和导入只使用当前生效目录，不接受引导草稿中的另一目标。

只读取实际 `gamelog_video_play` 表的 `created_at`、`video_url`，不使用通用 `video_id`、歌名、玩家或房间信息。正常解析 http/https URL，限定 `api.udon.dance`、`/Api/Songs/play`、单一合法正整数 `id` 及默认端口；节点参数不参与歌曲身份。时间按带时区 RFC 3339 解析，拒绝无效、非正纪元和未来时间；按真实时刻排序后，复用实时需求的 30 秒锚点去重和 60 天半衰期计算。最后计分时间保存事件原始 Unix 毫秒，历史贡献只衰减一次；查询时仍由统一评分入口衰减至当前时刻。

源库以 SQLite `mode=ro` / `query_only` 正常锁定读取，一个 SELECT 提供包含已提交 WAL 的一致快照；不使用 `immutable` / `nolock`，不修改日志模式、不 checkpoint、不拷贝单独主库。缺库、缺表/字段、损坏、占用或读取超时返回固定诊断，不输出原始 URL 或数据库错误细节。单次最多读取 200 万条记录、30 秒，字段长度有界；超过限制整次失败，不导入截断结果。

预览只在进程内保留歌曲聚合值，至多一份，15 分钟失效；新预览替换旧预览，取消或离开组件时释放，超时也主动释放。原始事件、URL、用户名、房间及数据源路径不写入 SWD 持久文件或日志。空结果没有提交令牌，不能清空已有统计。

目标是否为空只看 `song_usage` 行数。非空时再次弹窗明确说明需求次数、分数、最后需求时间整表替换，不与原统计累加，未出现在有效历史中的旧统计也删除。预览为空而提交前出现需求时返回冲突，必须重新预览并确认覆盖；不能用此前空预览直接授权覆盖。

预览与提交都访问应用已打开的业务数据库，目标绑定当前数据库文件；视频目录是否可用不影响历史统计导入。缺失或打不开的数据库返回冲突，不将其当成空统计，不读取任务快照推断初始化许可，不在导入中创建数据库。

活动引擎导入复用需求队列同步边界，先排空已接受事件，再在同一数据库事务内检查空表/覆盖权限、删除旧统计、插入新聚合及必要占位歌曲；后来的 GET 在提交后正常累计。没有活动视频引擎时，仍使用应用持有的数据库写入权与同一个替换事务；不启动引擎、下载、缓存清理或淘汰，也不创建视频目录。任一写入失败全部回滚；成功的同一预览令牌再次提交只返回原结果，不二次替换后续统计。

只更新 `song_usage` 并补缺失歌曲 ID，不重建歌曲资料、MD5 映射、视频、设置、请求明细、播放完成统计或条款凭据。沿用原评分字段和数据库版本，不增加来源表、持续同步、自动补偿或独立权重。批量补齐与容量淘汰在之后评分时使用新结果；P0–P3 实时调度和资源保护不变。开发验证见 [#28 记录](validation/issue-28-validation.md)。

## 职责边界与实施影响

原 `current_videos` 由 `song_media` 替代；`video_versions` 由 `media` 替代；原历史 `song_videos` 不再保留。原 `resource_usage` 中的歌曲分数改为显式 `song_usage.song_id`，不再混用 `song:ID` 和 MD5 字符串键。

管理页面、下载、扫描、路由和队列等原有读取方统一查询当前关联。旧资源仍可显示 MD5、文件属性及当前引用；没有当前引用时显示未关联，不能继续声称知道其历史所属歌曲。队列运行期间的临时保护关系仍可保留在内存，不能据此建立历史持久映射。

早期四表重构保留了请求日志保留期、流量累计和文件校验；v9 已另行确认删除旧统计累计并将来源总览改为[保留明细现场汇总](storage.md#请求统计的计算方式)。请求明细及来源统计都不是恢复歌曲热度的必需输入；请求明细被清理后，歌曲累计衰减贡献仍然保留。

向游戏返回重建歌曲列表的故障兜底明确暂缓；桌面程序业务的本地数据库回退已实现。本设计不保留原始清单、分组完整上下文和标签翻译，不能保证从四张核心表无损重建游戏响应。将来实现时另行确认协议转换和可处理 HTTP 的入口；现有 HTTPS 透传不能直接返回本地清单。

## 实现验收要求

以下要求由新格式及现有业务回归验证；实际游戏、实网和部署验收尚未执行：

1. 新歌、资料更新、MD5 更换和清单缺席符合增改不删；没有重复的权威 MD5 或歌曲 JSON。
2. 事务失败不留下半份清单或提前提交的版本水位；并发同步中新版本先提交、旧候选后进入写入阶段时，旧版本仍被拒绝。
3. 一首歌至多一个当前资源，多歌共享资源正常；外键约束生效。
4. 仅 ID 播放计分，直接视频请求即使已有明确反向映射也不计分；HEAD 和预加载不计分。
5. 30 秒边界、60 天衰减、时间回拨、并发计数和重启后累计值均符合定义。
6. 歌曲换 MD5、视频删除、请求日志清理和清单更新均不丢失歌曲热度。
7. 共享资源分数求和、孤儿零分、初始分数替代及下载/淘汰一致性正确，保护机制不退化。
8. 受支持的 v8 在可写打开入口静默一次性迁移到 v9，业务不兼容读取 v8；其他旧格式明确拒绝打开，异常文件保留，不删除或重建。
9. 新 API 观察将 A 更新为 B；备选清单和旧下载完成记录不能覆盖已有映射，已开始的响应仍传输原 MD5。旧 v8 的迟到请求拒绝仅适用于旧实现，新模型按[专门验证要求](#实施边界与验证要求)检查。

## 本地快照与当前成员

全量缺失检查、手动补齐及覆盖率仅使用 `catalog_members`，共用映射锁下的成员、水位及映射快照。缺失检查和补齐在任务期间保护已知资源；覆盖率只读取当时的文件状态，不登记视频引用或启动视频管理。缺映射歌曲仍计入总数，下载时按歌曲 ID 独立解析，不按空 MD5 合并。已知相同 MD5 的成员仍共用一个任务，分数复用全部当前关联歌曲的有效资源分数；无映射歌曲使用自己的分数。离线时使用已接受成员，未取得完整歌曲清单时不以预置映射推断成员或覆盖率。

“更新曲库”通过应用已有 `Store` 同步清单，不创建视频引擎。视频目录不可用时仍更新歌曲资料，覆盖率标为不可用并说明文件检查错误，保留上次成功检查时间和磁盘快照，不把旧百分比或零值当作本次结果。数据库不可用时拒绝同步，不创建替代数据库。引擎已运行时，清单写入继续使用 Store 与淘汰、发布共用的映射锁及保留策略同步边界；引擎自己的正常资源管理不受影响。

覆盖率为“已知映射且本地对应文件存在的成员数 / 全部当前成员数”，只查文件存在，不重新校验正文。缺映射单独计为“资源待识别”，扫描结果不将其计为已知文件缺失；概览通过感叹号提示、批量任务通过独立计数说明，具体呈现见[曲库设计](webui-design.md#曲库)。持久化统计保存计算使用的清单版本，界面据此说明统计范围；最新观察的清单状态独立读取。库存/批量/尝试快照升为 v3，拒绝旧范围的 v1/v2 结果并保留旧文件。

曲库展示全部已知歌曲和资源，包括退出当前清单的歌曲、失去关联或仅由预置提供的资源。单歌曲或指定资源下载沿用完整资料，不受成员限制，不把历史目标重新加入成员。资源目标固定 MD5，已知歌曲目标仍保留预期 MD5 一致性检查；API 查到新版本可更新映射，但不自动把本次固定目标换成新内容。无任何当前歌曲关联的资源仍按原有规则说明无法通过歌曲 API 取得地址，不猜测历史归属。

旧 v8 的[预置 media/song_media](../data/media-seed/README.md) 在应用启动时只补缺失记录和大小，有独立版本，不带 URL；v9只在新建数据库时初始化，不再向已有库导入或保存该版本。有效 API 观察自然更新映射，无需额外维护任务。外部视频导入以 media 身份准入，可离线启动且不依赖歌曲映射；先校验来源目录、目标目录及二者关系，再取得或创建视频引擎，被目录校验拒绝的请求不启动视频管理。大小预算、收藏和淘汰继续沿用资源管理规则。

元数据选歌与入库归曲库业务：从已有歌曲中按自身有效分数选择缺 URL、映射或正资源大小的歌曲，无 MD5 者也参与。共享完整链路判断见[地址使用、刷新与后台补齐](#地址使用刷新与后台补齐)。统一全量检测的清单同步与选歌并行；本地没有歌曲样本时等待本轮清单，之后再选歌。每轮只解析一首歌的 CF 地址；资源轻量检查可并行使用已有地址，没有地址时复用本轮返回的 URL，只读取一个正文 byte，不保存视频。失败项沿用每遍公平重试，全部剩余缺项尝试后再从最高分重试，已补齐者退出；不设 URL 固定期限或整库续期。自动与手动连通性检测共享选歌进度和入库入口；仅全量检测在本地清单可用时推进轮换位置，没有缺项时使用轮换样本。单项播放地址或资源检测不推进轮换，仍优先选择待补齐歌曲；没有缺项时复用 10 分钟内的有效样本，缺少样本则跳过。只检测清单时也保留成功接受的样本，但不调用选歌或推进缺项遍历。直连 Monitor 的有效响应也可复用入库，但不负责初始化、补齐选择或业务调度。

手动下载测速在已有 URL 未达到备料目标时，与连通性检测共用上述缺项选歌及每遍尝试进度，排除本轮已持有或已尝试的歌曲；播放访问和响应入库也复用既有入口，成功解析同步补齐 URL、歌曲资源映射及资源大小。下载失败只影响当前测速结果，不修改地址记录。测速不获取目录；本地候选后备、备料目标和准备期限统一见[上游检测与测速](upstream-channels.md#上游检测与测速)。

## 清单协议与历史依据

三个来源均用 YYYYMMDDhhmmss 民用时间字符串表达版本，按真实日历校验后比较；共同 UTC 轴只用于排序，不声称发布者原时区。非法日期、失败或空清单不推进水位。

Udon 读取顶层 time 与 groups.contents[].songInfos；Kiva/WannaInfo 读取成功状态 code=200、data.time 与 data.groups[].entries。请求尝试与正文校验复用现有 upstreamrequest，入口及逻辑来源身份由 catalogmeta 统一定义；传输规则统一见[业务请求的协议策略](upstream-channels.md#业务请求的协议策略)。

2026-10-29 的保留真实样本验证：同版 Udon/Kiva 各 10,470 首，经共同字段规范化后摘要一致。字段取舍、历史来源限制和旧实现证据见[研究记录](research/catalog-sources-20261029.md)。此前仅接受 MD5 清单、API 只补缺的规则已被本文替代。
