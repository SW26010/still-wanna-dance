# 曲库、资源关联与歌曲需求统计

确认日期：2026-10-06。状态：曲库清单业务仅使用 Kiva／WannaInfo，Udon 清单仅供 monitor。

歌曲 URL 观测和加载流程已实现，当前需求与资源边界见[下载需求与资源管理设计](download-resource-design.md)，演进背景见[早期加载设计](history/song-loading-design.md)。URL 观测写入与已有歌曲—MD5 关联更新分别处理，不增加来源冲突裁决。

本文维护曲库、资源关联与需求统计模型；存储格式及旧版本拒绝规则见[存储契约](storage.md)。

歌曲屏蔽与收藏独立保存，其业务规则以[下载需求与资源管理设计第 8 项](download-resource-design.md#8-歌曲屏蔽与收藏)为准，不改歌曲评分或统计含义。

## 目标与范围

优先永久保存歌曲 ID 到当前 MD5 的映射，同时保留歌曲资料供后续使用。原则是最小必要、职责分离、标准约束和可维护性，沿用 SQLite 与现有驱动，不引入新数据库、通用同步框架或自制版本系统。

“增改不删”定义为：新增记录、更新已有记录，上游清单缺席的记录保留；不要求保留每次修改前的值。歌曲资料、资源记录、当前映射和日常歌曲累计统计均适用。用户明确确认的 [VRCX 历史初始化](#vrcx-历史初始化)可整表替换歌曲统计。本地视频存储和请求日志仍按各自保留策略清理。

本轮不保存历史歌曲—视频关联、不保存完整清单快照、不实现面向游戏响应的歌曲列表故障兜底，也不兼容或迁移旧数据库格式。引擎启动和离线删除应拒绝带有已知旧存储标记的目录并提示使用独立新目录；除目录锁外不删除或改写旧数据。

### 干净重构，不保留过渡架构

直接围绕新模型重构数据库结构、领域类型、读写入口及所有调用方，不为旧结构保留兼容视图、旧表名别名、双写、旧格式读取分支或过渡适配层。不编写数据迁移或历史统计转换逻辑。

旧模型被替代后，删除其建表语句、查询和写入实现、废弃接口及仅用于旧结构的测试；相关测试改为验证新模型和本设计要求。不把新表包装成旧模型继续使用，也不让新旧两套实现长期并存。沿用现有 SQLite、驱动和仍适用的下载、文件校验及并发保护机制，不重复实现已有能力。

旧格式识别用于各资源入口拒绝误用。数据库创建／打开检查所选文件父目录中的 `stepstash.sqlite` 标记；视频引擎及离线删除检查所选视频目录中的旧组合键文件，拒绝后不清理或淘汰其中的数据。旧布局的父目录检查和锁交接、独立工作区的早期块清理分别遵循[存储契约](storage.md#数据库打开约定)与[运行生命周期](runtime-lifecycle.md)，不再以一个混合根推导全部资源。检查不读取旧库内容，也不承诺识别任意历史目录；这是旧数据保护，不是兼容支持，不授权迁移或删除用户已有数据库、视频及恢复文件。

## 数据职责

四张核心表分别保存一类事实：

| 表 | 唯一职责 | 主键 |
| --- | --- | --- |
| `songs` | 歌曲资料 | `song_id` |
| `media` | 视频资源属性 | `md5` |
| `song_media` | 歌曲到当前视频的映射 | `song_id` |
| `song_usage` | 本地歌曲需求统计与衰减累计值 | `song_id` |

另以一张小型 `catalog_state` 表保存同步版本水位。它是同步状态，不存清单正文或歌曲副本。请求明细、流量总计、文件校验继续独立承担原有职责，不属于这四张核心表。

### songs：歌曲资料

明确的标量字段使用原生列，不保存完整歌曲 JSON，也不另存一份重复的标题或元数据副本。内部列名统一使用 snake_case，由来源适配器进行固定字段转换。

| 列 | SQLite 类型 | 上游字段或含义 |
| --- | --- | --- |
| `song_id` | INTEGER | `id`，正整数主键 |
| `name` | TEXT | `name` |
| `artist` | TEXT | `artist` |
| `dancer` | TEXT | `dancer` |
| `player_count` | INTEGER | `playerCount` |
| `volume` | REAL | `volume` |
| `start`、`end` | REAL | 播放起止参数 |
| `flip` | INTEGER | `flip`，布尔含义 |
| `double_width` | INTEGER | `doubleWidth`，布尔含义 |
| `skip_random` | INTEGER | `skipRandom`，布尔含义 |
| `disable_public` | INTEGER | `disablePublic`，布尔含义 |
| `rpe` | INTEGER | `rpe` |
| `genre` | TEXT | `genre` |
| `group_name` | TEXT | 条目的 `group` |
| `composed_title` | TEXT | `composedTitle` |
| `composed_title_spell` | TEXT | `composedTitleSpell` |
| `aya_id` | TEXT | `ayaId`，上游数值的原始 JSON 数值文本；null 或未知保存为 SQL NULL |
| `tags_json` | TEXT | `tag`，JSON 数组 |
| `original_urls_json` | TEXT | `originalUrl`，JSON 数组 |
| `shader_motion_json` | TEXT | `shaderMotion`，JSON 数组 |

数组目前只需整体保存、读取，使用 JSON 数组列并校验 JSON 及数组形状；有独立查询、关联或约束需求时再拆子表。作者等文字不为规范化而额外拆成实体表。不建立分组表，不承诺保存父级分组结构或标签翻译等完整响应上下文。

歌曲可能先由 ID 播放请求发现，因此允许仅有 `song_id` 的占位记录，其余未知资料为 NULL，不能用 0、false 或空字符串冒充已知值。布尔列仅接受 NULL、0、1。已接受的清单条目应完整写入其已定义字段，来源本身的空值与未知值按协议处理。

`checksum` 不进入本表，提取后写入 `media` 和 `song_media`。未知上游字段不自动建立扩展 JSON；未来需要时通过普通数据库结构变更显式支持。已知字段的类型及空值约束在实现时用样本和协议测试核对，不凭字段名称猜测单位或含义。

### media：资源属性

| 列 | 类型与约束 | 用途 |
| --- | --- | --- |
| `md5` | TEXT PRIMARY KEY | 小写 32 位十六进制内容标识 |
| `byte_size` | INTEGER NULL | 已知文件字节数，非负；未知用 NULL |

MD5 同时是资源身份和正式文件名 `videos/{md5}.mp4` 的依据，不再保留相同含义的 `version_key`、`checksum` 两列。v6 删除没有产品读取用途的 `source_path`；实际播放地址证据统一保存在 `song_urls`，不从资源元数据拼造地址。歌曲资料列全部保留，清单摘要仍为 v1。

资源记录不等于文件本地已有。清单提供 MD5 时即可创建记录，是否存在文件仍由文件系统检查决定。多个歌曲可以共用一个资源；播放参数属于歌曲，不能放到共用视频上。

### song_media：当前关联

| 列 | 约束 |
| --- | --- |
| `song_id` | INTEGER PRIMARY KEY，外键关联 `songs.song_id` |
| `md5` | TEXT NOT NULL，外键关联 `media.md5` |

每首歌最多一条当前关联，没有已知关联时不创建该行。为 `md5` 建普通索引，支持反查当前歌曲和汇总资源分数。外键检查必须在数据库连接上实际启用，不使用级联删除。

歌曲从 A 更新为 B 时直接更新这一行。不保存 A 曾经属于该歌曲的关系，也不维护 `is_current` 标志、历史关系表或歌曲表中的 MD5 副本。A 的资源记录和文件可以继续存在；无当前歌曲引用时，其保留分数为零。

### song_usage：歌曲需求统计

| 列 | 类型与约束 | 用途 |
| --- | --- | --- |
| `song_id` | INTEGER PRIMARY KEY，外键关联 `songs` | 统计归属 |
| `demand_count` | INTEGER NOT NULL，非负 | 累计有效需求次数 |
| `demand_score` | REAL NOT NULL，非负 | 上次有效需求时的指数累计值 |
| `last_demand_at` | INTEGER NOT NULL | 对应时刻，Unix 毫秒 |

无需求时可以没有统计行。占位歌曲和第一条统计应保持外键一致。统计独立于清单更新、MD5 更换和文件删除；不将统计写进歌曲资料或关联表。

### song_preferences：本地歌曲偏好

`song_preferences` 只保存用户对歌曲的屏蔽或收藏标记，普通状态无记录；精确 DDL 和版本约定见[歌曲偏好存储](storage.md#歌曲偏好存储)。它独立于上游资料及需求统计，清单同步、MD5 更新、VRCX 初始化和文件清理均不覆盖偏好，也不改变清单摘要。

资源策略根据当前 `song_media` 关联推导，不复制 MD5 偏好或修改需求分数。收藏只影响保留资格，不代表下载需求、已保存状态或实际播放统计；共享、预算及生效规则统一回到 canonical 第 8 项，不在本页维护第二套规则。

## 需求计分与优先级

歌曲统计来源为 SWD 观察到的明确歌曲 ID 播放 GET，以及用户显式执行的 VRCX 历史初始化。直接视频 URL 请求即使能反查到一个或多个歌曲，也不推断歌曲、不增加歌曲次数和热度。HEAD、后台检查、批量下载和预加载不增加热度。这里统计可识别需求观测；VRCX 播放事件不等于 SWD 拦截的 GET，两者都不声称确认完成播放。

同一歌曲跨线路、跨资源的需求，以前一次有效需求为锚点做 30 秒去重。窗口内重复请求不推进计分时间；时间回拨到最后有效需求之前时不增加次数或分数、不回拨时间。

半衰期固定为 60 天。第一次有效需求记次数 1、分数 1；后续有效需求更新为：

```text
新分数 = 旧分数 × 2^(-间隔天数 / 60) + 1
新次数 = 旧次数 + 1
```

查询时将累计分数衰减到查询时刻，不写回数据库，不运行每日全表衰减任务。次数用于展示及判断是否已有实际需求，不参与评分公式。统计更新应原子完成，避免并发重复计数或丢失累计值。

歌曲没有实际需求时使用现有内置初始分数，没有初始分数时为零。有实际需求后，其衰减累计值完全替代初始分数，衰减再低也不重新启用初始分数。初始表不写入本地需求统计。

资源优先级通过 `song_media` 汇总所有当前关联歌曲的有效分数，每个歌曲 ID 只计一次。无关联资源为零分；不另存资源热度累计值，不持久化两套下载分数与淘汰分数。

- 批量补齐优先高分资源；同分沿用歌曲 ID 从大到小的稳定排序。
- 容量淘汰优先低分资源；同分先按关联歌曲最大 ID 从小到大，无关联视为 0，再按资源最近有效歌曲需求时间、文件修改时间和路径稳定排序。资源最近需求由关联歌曲统计派生，无歌曲需求时使用文件修改时间，不依赖纯视频请求统计。
- 活动请求、下载、队列和交接保护仍优先于分数，沿用现有保护机制。

下载与淘汰共用同一个有效分数计算入口及汇总规则，避免两处公式和初始分数处理逐渐分叉。请求明细和流量统计可以继续记录直接视频请求，但这些记录不参与歌曲计分，也不需要保留 MD5 级热度来维持排序。

## 清单同步与增改不删

两个同构的带 MD5 来源共用适配器，写入同一套歌曲、资源和关联表，不按来源复制业务表。一次接受完整候选清单后，在一个事务内完成歌曲资料更新、资源补充、当前映射更新及同步水位提交；失败全部回滚。清单同步不修改 `song_usage`。

| 事件 | 处理 |
| --- | --- |
| 新 ID | 新增歌曲资料、资源和当前关联 |
| 已有 ID 的资料变化 | 更新该歌曲已定义的资料字段 |
| 同 ID 的 MD5 改变 | 更新当前关联，保留旧资源记录，不保留旧关联 |
| 本次清单缺少某 ID | 其歌曲、当前关联和统计保持不变 |
| 有效 API URL 观察发现没有关联（含播放、队列、补齐和后台探测） | 用解析得到的 MD5 在同一事务补齐资源与关联，必要时先建占位歌曲，不等待视频下载或持久化 |
| API URL 与已有映射冲突 | 记录差异，不覆盖任何已有映射，无论它最初来自清单还是补缺 |
| 纯视频 URL 请求 | 可补充资源属性，不建立或推断歌曲关联，不计歌曲热度 |
| 本地视频文件被淘汰 | 只删文件，保留上述业务数据 |

API URL 观察和显式 ID 加载只补缺失关联，任何已有映射仅由已接受的清单更新，不额外引入映射来源字段。例如先观察到 A、随后解析到 B，即使该歌曲始终未进入清单，当前映射也仍为 A，仅记录差异。补缺写入必须采用原子插入且冲突时不更新，避免解析期间清单已写入的映射被覆盖。`ObserveSongURL` 的时序、事务与入口共用规则见[存储约定](storage.md)。

候选清单应验证成功状态、完整结构、ID 唯一性和合法 MD5；无效候选不得部分写入。未知资源属性保持 NULL，清单中没有大小或路径不应抹掉已经知道的资源属性。不引入通用 JSON 合并器或双向数据同步。

`catalog_state` 最小保存逻辑清单键、已接受的上游版本、内容摘要、来源及接受时间。上游版本与本地获取时间分开；两个镜像共享同一版本水位。候选整体更旧时不写入，同版同内容视为重复，同版不同内容记录冲突并保留现状。摘要基于统一适配后的内容和稳定排序计算，避免仅 JSON 排版或对象键顺序差异导致冲突。

读取并比较版本水位与提交更新必须串行化：同一逻辑清单的所有同步入口使用同一同步锁，从事务内读取最新水位、比较候选直到提交或回滚均在锁内完成；也可使用具有等价串行化保证的数据库事务。网络获取和候选解析在锁外进行，不能把锁外预检查作为最终写入依据。并发获取的旧候选即使后完成，也必须基于提交前的最新水位重新判断，不能覆盖已经提交的新版本。

Kiva 两个端点是同一上游表的两个来源，按响应 `data.time` 比较新旧，共用唯一的 `songs` 水位；Udon 清单的 `time` 仅在 monitor 中展示，不参与本地数据版本判断。使用解析后的清单时间比较，不使用本地获取时间或任意字符串排序。获取失败或空响应不能降低水位。

## VRCX 历史初始化

WebUI 同意条款并取得程序状态后，仅检查默认 `%APPDATA%\VRCX\VRCX.sqlite3` 是否为现存文件；不打开源数据库，不读取表结构、记录数量、时间范围或历史内容。默认文件存在、当前 SWD 的 `song_usage` 为空且用户尚未忽略时，曲库显示「检测到 VRCX 历史，可用于安排歌曲下载与保留顺序。仅在本机处理。」及「导入历史 / 忽略」。曲库建议不局限于首次建库进程：重启、重新打开已有空库或新建空库后仍可显示，直到首次写入歌曲需求统计或用户忽略。资格随既有程序状态刷新更新，不额外增加轮询；请求明细的保留与清理不影响判定。

Toast 仅在首次自动建库的本次运行、且当前不在曲库时显示一次「检测到 VRCX 数据库」，说明确认前不读取内容，并提供「前往曲库」链接；链接只导航，进入曲库后撤去 Toast，不重复弹出。重启或打开已有空库不再触发 Toast，曲库建议仍按上述条件保留。Toast 沿用普通通知的 7 秒超时及悬停／窗口失焦暂停，可关闭；同一标签页用 sessionStorage 只记已提示标记，刷新不重复，不保存路径或历史内容，浏览器存储不可用时仍在当前页面内去重。检测及导入共用同一份前端模型，不因切页再次检测。

检测受条款和既有请求门禁约束。忽略属于当前配置实例的界面选择，原子保存为主配置的 `vrcxImportDismissed=true`，不进入可编辑运行设置或触发重启；缺失或 null 默认为 false，普通设置保存保留该字段，切换数据库或视频目录不重置忽略。保存失败保留原选择和建议并允许重试，不创建额外状态文件或数据库表。关闭 Toast 只关闭通知，曲库建议仍保留。缺少默认文件或检测失败时不弹出提示，手动入口始终保留。

只有用户点击「导入历史」后才读取默认源库，复用下述预览聚合和导入事务；有效结果且目标统计仍为空时直接提交，无需额外预览或确认。读取后发现已有统计则转到原预览界面，最终覆盖仍需明确确认；提交时出现新需求则拒绝并要求重新预览。无有效记录不提交，读取失败在提示区域反馈，提交失败或结果未确认时保留原导入机制的核对入口；不自动重试或持续同步，不记录“曾有统计”的重复状态，不改变数据库或配置格式版本。

曲库中的「历史偏好」提供只读预览与导入。先只读检查当前生效目录的 `song_usage` 行数，新目录或空表默认勾选，非空默认不勾选；手动勾选不弹警告。支持文件选择器、路径输入、手动预览和即时导入，预览展示数据源、目标、数量、时间范围和跳过原因。已有非空统计在最终导入时确认整体覆盖。预览和导入只使用当前生效目录，不接受引导草稿中的另一目标。

只读取实际 `gamelog_video_play` 表的 `created_at`、`video_url`，不使用通用 `video_id`、歌名、玩家或房间信息。正常解析 http/https URL，限定 `api.udon.dance`、`/Api/Songs/play`、单一合法正整数 `id` 及默认端口；节点参数不参与歌曲身份。时间按带时区 RFC 3339 解析，拒绝无效、非正纪元和未来时间；按真实时刻排序后，复用实时需求的 30 秒锚点去重和 60 天半衰期计算。最后计分时间保存事件原始 Unix 毫秒，历史贡献只衰减一次；查询时仍由统一评分入口衰减至当前时刻。

源库以 SQLite `mode=ro` / `query_only` 正常锁定读取，一个 SELECT 提供包含已提交 WAL 的一致快照；不使用 `immutable` / `nolock`，不修改日志模式、不 checkpoint、不拷贝单独主库。缺库、缺表/字段、损坏、占用或读取超时返回固定诊断，不输出原始 URL 或数据库错误细节。单次最多读取 200 万条记录、30 秒，字段长度有界；超过限制整次失败，不导入截断结果。

预览只在进程内保留歌曲聚合值，至多一份，15 分钟失效；新预览替换旧预览，取消或离开组件时释放，超时也主动释放。原始事件、URL、用户名、房间及数据源路径不写入 SWD 持久文件或日志。空结果没有提交令牌，不能清空已有统计。

目标是否为空只看 `song_usage` 行数。非空时再次弹窗明确说明需求次数、分数、最后需求时间整表替换，不与原统计累加，未出现在有效历史中的旧统计也删除。预览为空而提交前出现需求时返回冲突，必须重新预览并确认覆盖；不能用此前空预览直接授权覆盖。

预览与提交都访问应用已打开的业务数据库，目标绑定当前数据库文件；视频目录是否可用不影响历史统计导入。缺失或打不开的数据库返回冲突，不将其当成空统计，不读取任务快照推断初始化许可，不在导入中创建数据库。

活动引擎导入复用需求队列同步边界，先排空已接受事件，再在同一数据库事务内检查空表/覆盖权限、删除旧统计、插入新聚合及必要占位歌曲；后来的 GET 在提交后正常累计。没有活动视频引擎时，仍使用应用持有的数据库写入权与同一个替换事务；不启动引擎、下载、缓存清理或淘汰，也不创建视频目录。任一写入失败全部回滚；成功的同一预览令牌再次提交只返回原结果，不二次替换后续统计。

只更新 `song_usage` 并补缺失歌曲 ID，不重建歌曲资料、MD5 映射、视频、设置、请求明细、播放完成统计或条款凭据。沿用原评分字段和数据库版本，不增加来源表、持续同步、自动补偿或独立权重。批量补齐与容量淘汰在之后评分时使用新结果；P0–P3 实时调度和资源保护不变。开发验证见 [#28 记录](validation/issue-28-validation.md)。

## 职责边界与实施影响

原 `current_videos` 由 `song_media` 替代；`video_versions` 由 `media` 替代；原历史 `song_videos` 不再保留。原 `resource_usage` 中的歌曲分数改为显式 `song_usage.song_id`，不再混用 `song:ID` 和 MD5 字符串键。

管理页面、下载、扫描、路由和队列等原有读取方统一查询当前关联。旧资源仍可显示 MD5、文件属性及当前引用；没有当前引用时显示未关联，不能继续声称知道其历史所属歌曲。队列运行期间的临时保护关系仍可保留在内存，不能据此建立历史持久映射。

请求日志保留期、流量累计和文件校验不因本次四表重构被取消；它们不能作为恢复歌曲热度的必需输入。请求明细被清理后，歌曲累计衰减贡献仍然保留。

向游戏返回重建歌曲列表的故障兜底明确暂缓；桌面程序业务的本地数据库回退已实现。本设计不保留原始清单、分组完整上下文和标签翻译，不能保证从四张核心表无损重建游戏响应。将来实现时另行确认协议转换和可处理 HTTP 的入口；现有 HTTPS 透传不能直接返回本地清单。

## 实现验收要求

以下要求由新格式及现有业务回归验证；实际游戏、实网和部署验收尚未执行：

1. 新歌、资料更新、MD5 更换和清单缺席符合增改不删；没有重复的权威 MD5 或歌曲 JSON。
2. 事务失败不留下半份清单或提前提交的版本水位；并发同步中新版本先提交、旧候选后进入写入阶段时，旧版本仍被拒绝。
3. 一首歌至多一个当前资源，多歌共享资源正常；外键约束生效。
4. 仅 ID 播放计分，直接视频请求即使已有明确反向映射也不计分；HEAD 和预加载不计分。
5. 30 秒边界、60 天衰减、时间回拨、并发计数和重启后累计值均符合定义。
6. 歌曲换 MD5、视频删除、请求日志清理和清单更新均不丢失歌曲热度。
7. 共享资源分数求和、孤儿零分、初始分数替代及下载/淘汰一致性正确，保护机制不退化。
8. 旧格式明确拒绝打开，不执行隐式迁移、删除或重建。
9. 播放先补齐 A、随后发现 B 且歌曲未进入清单时保持 A；播放补缺与清单更新并发时不覆盖清单提交的映射。

## 本轮协议边界

2026-10-05 直接核对三个现有 HTTPS 入口：`x.kiva.moe/api/v2/wanna/songs` 的 `data.time` 为 `20261004235822`；`wanna.kiva.moe/api/wannaInfo` 的 `data.time` 为 `20260215004959`；`api.udon.dance/Api/Songs/list` 的顶层 `time` 为 `20261004235822`。三者均为年月日时分秒字符串，响应值精确到秒、不带时区偏移；Kiva 与 Udon 同时间的 10,398 个 ID/歌名逐项一致。

适配器使用标准日期解析器的 `20060102150405` 格式，校验真实日历日期后用 `time.Time.Before/Equal` 判断先后与相等，替换原先仅检查 14 位数字并按字典序排序的实现。首发持久化契约限定输入为 14 位数字，不接受标准解析器额外允许的秒小数或时区后缀。无偏移的值在统一 UTC 轴上表示其民用日期时间，仅用于按用户确认的共同时间基准比较，不声称原值的实际时区是 UTC，也不依赖机器本地时区或 HTTP Date。保存的 `revision` 仍是上游原值；非法日期、失败或空清单不推进水位。

曲库清单来源仅限 Kiva（`x.kiva.moe/api/v2/wanna/songs`）和 WannaInfo（`wanna.kiva.moe/api/wannaInfo`）。二者通过同一完整清单同步接口写入歌曲、资源和映射，使用 `catalog_state` 的单一 `songs` 水位。移除 Udon 名称投影、`SyncCatalogNames`、名称摘要和 `song_names` 水位的读取、比较及写入。已有数据库中遗留的 `song_names` 行不再参与任何计算，也不会阻挡 MD5 更新；本次不删除歌曲、映射或视频，也不回滚过去写入的数据。新接受的 MD5 清单按原规则更新现有记录。

本地 10,398 条样本的 `ayaId` 均为 null；上游站点所链接仓库的[固定版本类型定义](https://github.com/ClownpieceStripedAbyss/aya-dance-web/blob/db10092436a49120ca62232e002a998289eb6eb4/types/video.ts#L20)明确声明 `ayaId: number | null`，同文件的获取函数指向当前 MD5 接口。可空 TEXT 是数据库存储表示，不是字符串输入协议：只接受 JSON 数值或 null，字段缺失时也保存为 NULL；数值按原始 JSON 数值文本存储，不经 float64、整数转换或额外范围限制，保留整数精度、小数和指数写法。字符串（包括带引号的数字）、布尔、对象及数组均拒绝。数组资料仍按 JSON 数组整体保存；未知字段不持久化。

MD5 清单失败时不得请求 Udon 清单作为替代，也不得进入 ID-only 清单的逐首解析流程。批量扫描／补齐与覆盖率只接受经过完整校验的 MD5 清单；无效候选不会部分落库。

为保持本地视频列表最近访问语义，独立 `media_access` 仅长期保存每个 MD5 的最后 GET 时间，与保留期内 HTTP 请求明细取较新值。不保存资源次数或热度，不参与下载和淘汰评分。

## 本地快照与检查状态（2026-10-06）

覆盖率和批量任务先获取 Kiva／WannaInfo 候选并尝试同步，随后只读取本地数据库快照。远端错误不阻止使用已接受的有效本地 MD5 清单；无有效本地清单时明确失败。快照包含保留的旧歌曲映射，不包含没有 MD5 的名称记录。读取水位和映射使用同一映射锁，随后固定所引用的资源，任务结束释放保护；网络获取在锁外。

新增 catalog_checks 保存 songs 的成功检查时间、说明和最近错误。合法重复或旧候选也记录成功检查；更新时与歌曲、映射、水位在同一事务提交。失败不推进成功检查时间，重启后保留状态；旧库没有记录时不推断历史检查时间。catalog_state 的 songs 仍是唯一数据水位，不恢复 Udon 名称水位。

catalog_members 记录最后接受的完整 MD5 清单包含的 ID，更新清单时在同一事务替换，用于共享资源下载时优先选择该清单中的歌曲。旧库在下次同版同内容检查时补齐该集合；它不删除 songs 或 song_media 中保留的旧记录，也不构成第二套水位。
