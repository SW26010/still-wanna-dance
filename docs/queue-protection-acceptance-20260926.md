## 实机发现：播放开始前的保护空档

1346 在 T+0.000s 完成预下载，T+11.000s 独立文件校验通过。用户随后播放该首：

1. T+26.377s 队列同步为 `[1347]`，1346 离队。
2. T+26.381s 容量清理淘汰 1346，52,162,845 字节。
3. T+26.739s 播放 API 请求到达，触发新的 `download_started`。
4. 探测响应为 MISS，播放器随后发起 `bytes=0-`；T+31.677s 重新下载完成并发布。

淘汰发生在已解析资源的首个请求日志之前约 0.36 秒。现有队列保护随离队立即解除，而播放资源引用尚未建立；网络够快使用户没有察觉，但预缓存收益丢失。活动请求已经持有引用的自动化测试不能覆盖此真实先后顺序。后续修复应回归“先离队，后到达播放请求”的时序，同时确保普通删歌、清空和停止仍能合理回收。
