# issue #51：文件位置、播放时间与模型余量

本次只读分析现有本地视频和目录元数据，未修改视频、数据库、产品策略或实验参数。对应[入口判断设想](issue-51-request-admission-proposal.md)中的播放模型，不调整现有下载延续的 30 秒窗口。

## 样本与测量方法

共读取 10,197 个 MP4，合计 473,483,947,835 字节，全部成功解析。其中 10,152 个文件与目录媒体身份、大小及正数结束时间匹配，进入模型比较；其余 45 个只计解析覆盖。按当前实现取同一媒体关联的最小正数 `songs.end`，本批没有同媒体关联时长不一致的情况；5 个文件关联非零歌曲起点，未据此改写现行模型。

用 MP4Box.js 2.5.0 读取音视频样本的文件位置、大小、显示时间、解码时间和同步帧标记，应用容器编辑列表。只读取索引所需范围，合计约 2.34 GB，不遍历解码整个视频。将每个样本覆盖到所有相交的 1 MiB 块，取块内最早的音视频显示时间作为“开始播放用到这个块”的文件依据。跨块的帧也计入，不能只按帧的起始字节归块。整体统计排除第 0 块和不包含有效音视频样本的块，共 445,436 块。

这个时间不是游戏画面实际卡住的时刻：日志同步误差、播放器缓冲和解码依赖仍会影响后者。索引中块内最早显示时间与最早解码时间的差，在本批不超过 0.077 秒，不能解释数秒至数十秒的线性换算偏差。元数据位于前部的文件有 10,074 个，后部的有 123 个；后者提前取得容器索引的需求没有包含在正文块时间中。排除后部元数据文件后，主要误差结论不变。

独立校验使用 PyAV 19.0.2／FFmpeg 解封装：

- 前面实验的 8 个文件，逐包位置、大小、显示／解码时间和关键帧标记全部匹配，最大时间差约 1.14×10⁻¹³ 秒。
- 再选两端偏差最大的各 3 个文件、3 个后部元数据文件及按资源键排序均匀抽取的 24 个文件，去重后 33 个、575,852 包。块时间映射全部在 10 微秒容差内，最大差约 7.30 微秒。这是确定性覆盖抽样，不是随机抽样置信区间。
- **同步帧检查有一项未通过：** 3081 的 16 个块，FFmpeg 标记的后续关键帧早于 MP4 索引标记，最大差 4.1041 秒。此文件的块时间映射仍匹配。保留检查脚本的非零退出与差异，不把索引同步帧统计当作播放器可跳转位置的精确保证。初次 2 微秒容差另报两文件微小时间差，原始结果本地保留；调整为 10 微秒后仍保留上述实质差异。

方法依据：[MP4Box.js 渐进解析接口](https://github.com/gpac/mp4box.js/blob/main/README.md)、[PyAV Packet 字段](https://pyav.org/docs/stable/api/packet.html)。工具只用于隔离的离线分析，没有增加产品依赖。汇总与校验结果见[证据清单](../evidence/issue-51-media-map-20261117/manifest.json)。

## 线性换算的偏差

定义 `误差 = 目录时长 × 块起点 / 文件大小 − 索引中的块最早显示时间`。正值表示模型把使用时间估晚了，负值表示估早了。

| 统计位置 | 误差 |
| --- | ---: |
| 第 1 百分位 | −13.20 秒 |
| 第 5 百分位 | −6.72 秒 |
| 中位数 | +0.67 秒 |
| 第 95 百分位 | +7.63 秒 |
| 第 99 百分位 | +14.01 秒 |
| 最小／最大 | −54.65／+115.68 秒 |

这是按块统计，较大文件权重较高；证据另列每文件等权的过早阈值比例，结论方向一致。只统计前部元数据文件的第 5／95 百分位仍为 −6.75／+7.67 秒。

目录时长相对容器时长的第 1／99 百分位为 −0.98／+0.45 秒，只有 3 个文件相差超过 2 秒。将线性公式中的目录时长换为精确容器时长后，位置误差的第 5／95 百分位仍为 −6.63／+7.80 秒。因此，只把总时长读得更准不能解决主要偏差；文件中不同时段的字节分布才是此处需要校正的部分。

| 歌曲／文件范围 | 线性估计 | 索引最早使用点 | 估计偏差 |
| --- | ---: | ---: | ---: |
| 4598／2–3 MiB | 7.93 秒 | 7.85 秒 | +0.08 秒 |
| 3214／16–17 MiB | 77.94 秒 | 73.33 秒 | +4.61 秒 |
| 1314／16–17 MiB | 108.14 秒 | 87.05 秒 | +21.10 秒 |
| 5396／16–17 MiB | 87.81 秒 | 102.40 秒 | −14.59 秒 |
| 8935／8–9 MiB | 29.75 秒 | 29.12 秒 | +0.63 秒 |

例如，1314 即使余量取零，仍会将此块的使用时间估晚约 21 秒；5396 即使加 5 秒，阈值仍比实际使用早约 9.6 秒。单个统一常量无法同时修正这两个方向。

## 正、零、负余量的代价

这里的余量加在播放模型的使用时间上：负数允许更早拒绝，正数延后允许拒绝。实际仍须有符合范围关系、同块未就绪、有效非 owner 模型等条件的新请求；不会到时自动返回 504。

以下只移动线性模型阈值，不模拟请求到达。**比例是文件块的时间偏差比例，不是误杀率、触发频率或播放失败率。**

| 余量 | 阈值早于索引使用点 | 提前超过 5 秒 | 晚于使用点超过 5 秒 |
| --- | ---: | ---: | ---: |
| −2 秒 | 72.61% | 13.34% | 5.88% |
| 0 秒 | 36.22% | 7.81% | 10.56% |
| +2 秒 | 17.68% | 4.63% | 19.54% |
| +5 秒 | 7.81% | 2.16% | 63.78% |

**偏早的代价：** 重复请求可能仍是正常预读。若在那时返回 504，可能把原本还有缓冲、来源也有机会及时恢复的播放变成错误与重新加载。[跨歌曲预读实验](../acceptance/live-acceptance-20261116-03.md)已观察到当时画面正常、随后黑屏和重新加载；并非只影响早已卡住的画面。较早重新打开视频也未必跳过缺块，新的目标位置仍可能需要它。

**偏晚的代价：** 已经停住的播放可能放过仅有的一次接续请求。当前只在入口判断，之后跨过阈值不会补做拒绝，因此阈值只差两三秒，也可能多等待二十多秒；后段虽可读取，却暂时没有新的跳转请求。较大的正余量还会扩大模型选择 10 秒交接的范围；负余量则会缩小它，可能使后来仍需使用的块只保留 2 秒。仅有文件映射不能计算额外槽位、下载字节或交接净收益。

在目标“故障后尽快恢复，同时减少对正常播放干预”下，已经卡住后的短暂黑屏与跳过进度较容易接受；尚在正常播放时被额外打断，代价更难接受。等待本身也有代价，8935 已说明过大的余量会错过入口机会。实际最佳取值还取决于接续请求何时到达、故障持续时间和重新加载后的目标位置，本批没有给这些事件建立频率分布。

## 重新核对实机样本

保持[本轮实机](../acceptance/live-acceptance-20261117-01.md)记录的同步时间基准，只将缺块位置对应的媒体时间换成索引结果：

| 样本 | 接续请求相对索引使用点 | −2／0／+2／+5 秒线性余量的入口结果 |
| --- | ---: | --- |
| 4598 受阻 | 晚 19.58 秒 | 均拒绝 |
| 2502 受阻 | 晚 28.71 秒 | 均拒绝 |
| 3214 预读 | 早 29.46 秒 | 均放行 |
| 1314 预读 | 早 34.95 秒 | 均放行 |
| 8935 边界 | 晚 3.24 秒 | 前三档拒绝，+5 秒放行 |

“相对索引使用点”用于解释当时进度；最后一列仍是各候选余量对原线性公式的阈值复算，没有替换运行过的程序。5396 本轮受提前自动加载干扰，继续排除。没有反推改变响应后还会发生完全相同的后续请求。

8935 的真实观察是停顿约 28 秒、来源恢复后继续、没有黑屏；这次资料说明 +2 秒已经能改变那次入口判断，不需要负余量。但尚未实测该次提前 504 的恢复耗时及是否跳过缺块，不能将整个等待时长算作可获得的收益。

1 MiB 所覆盖的音视频时间跨度中位数约 3.87 秒，第 95 百分位约 8.98 秒，第 99 百分位约 15.12 秒。“一块约四秒”适合作数量级估计，不能作为全库保证。块后第一个索引同步帧相对块最早使用点的中位距离约 6.28 秒；该辅助值受上述同步帧校验差异、音频依赖及播放器实际跳转选择限制。预读 504 到实际重新加载的间隔随样本变化，直接取 −6 秒仍需验证，重新加载也可能再次请求同一块。

## 初步评估与后续取舍

现有证据不支持统一采用负余量，也不支持将 +5 秒称为足以覆盖全库误差的安全值。若保留线性模型，+2 秒可作为下一轮有针对性的候选：它能改变已观察到的 8935 边界，同时保持本轮另四笔的入口结果；这不是产品默认值的验证。

更直接的后续方向是先评估能否利用已有媒体索引校正“文件位置→播放时间”，再确定小范围余量。索引不可用的冷文件、文件末尾才有索引、日志同步误差、同一余量对入口及交接的两种影响仍要分别核对。本次没有实施索引缓存、修改参数或增加配置，也没有要求追加游戏实验。

上述为初步评估。后续结合误差分布和维护成本，阶段决策已收敛为**保留线性映射、下一阶段采用 0 秒余量，暂不引入预制索引**；+2 秒不再作为优先候选。统计本身未证明索引能够改善多少实际播放，不能仅因存在长尾误差就新增索引机制。当前决策及重新评估条件统一见[方案记录](issue-51-request-admission-proposal.md#阶段决策线性映射0-秒余量)，历史实测值和研究数据不变。
