# 日志队列预缓存

控制台「房间队列预缓存」读取 VRChat 新增日志，按队列顺序准备前 N 个位置（默认 3）中具有有效曲库 ID 的歌曲。通过独立按钮开启或关闭，不依赖本地播放网关；设置中「控制台启动」的「运行控制台时自动启用房间队列预缓存」（`autoStartQueue`）默认启用。字段缺失或为 null 时采用该默认值，已保存的 true/false 保留，不跟随播放网关或废弃的 `queuePrefetchEnabled` 字段。实际游戏读取本地缓存仍需启动播放网关并完成 hosts 接入。VRChat 日志目录默认每次启动按当前 Windows 用户自动读取 `AppData/LocalLow/VRChat/VRChat`，输入框显示灰色且不可编辑。只有勾选「手动指定 VRChat 日志目录」（`manualLogDir`）后才接受并保存 `logDir`；手动模式不能为空。自动模式保存时将 `logDir` 清空，快照也不保存自动路径。旧配置缺少 `manualLogDir` 时恢复自动模式，包括曾固化的路径；原先确需自定义目录的用户需重新勾选并指定。

设置中的「队列预缓存数量」（`queuePrefetchCount`）可设为 1～100，默认 3；旧配置缺少该字段或设为 0 时使用默认值。数量按队列位置计算，非曲库条目也占位置。运行中也可保存，统一在重启应用后生效；并发下载仍最多两首。

## 日志检测与频率

参考 dancing-log 本地检出 `c3fa28fa3b68879cb43513bc2cb53f1cc03fa1cc` 的 [vrc_log_watcher.py](https://github.com/SW26010/dancing-log/blob/c3fa28fa3b68879cb43513bc2cb53f1cc03fa1cc/dancing_log/vrc_log_watcher.py) 与 [vrc_log_parser.py](https://github.com/SW26010/dancing-log/blob/c3fa28fa3b68879cb43513bc2cb53f1cc03fa1cc/dancing_log/vrc_log_parser.py)。调查时 GitHub 返回 404，实际参考源码来自本机已有仓库。独立用 Go 标准库实现，没有引入 Python 运行依赖。

- dancing-log 默认轮询 0.25 秒。Still Wanna Dance 每 **3 秒**检查当前日志并从字节偏移读取增量，每 **15 秒**扫描新日志文件；没有新增内容时不解析、不请求歌曲 API。
- 初次启动从现有最新文件末尾开始，等待新的队列同步。不会重放旧会话；在点歌前开启最稳妥。新会话文件从头读取，按 VRChat 文件名中的会话时间选取，旧文件 mtime 改变不会倒退。
- 保留尚未写完的行，完整换行后再解码，支持 UTF-8 跨次写入。单次最多读取 4 MiB，单行最多 1 MiB。截断、替换、读取失败、异常队列行会清空待处理队列。
- 处理 `OnPreSerialization: queue info serialized:` 和 `OnDeserialization: syncedQueuedInfoJson =` 两类 JSON 数组。忽略当前视频 userData 和预览事件；不读取玩家姓名到业务状态，不持久化完整日志。
- 离房、进入新房间、应用正常退出或文件切换时清空待处理队列；日志 5 分钟无新增时也清空，等待新的同步。
- 当前文件新增日志通常在 0～3 秒内被读取，新日志发现通常在 0～15 秒内。游戏本身的日志缓冲、磁盘和系统调度会增加延迟，这不是严格实时保证。

## 下载调度

同一次读取中的快照先合并为最终队列，再通知后台协调器，最多同时准备两首。每首开始前重新检查最新顺序；解析视频地址后也再检查一次，避免接口慢时把已删歌曲提交下载。

使用设置中的回源线路（默认 Auto：主动下载先查询 node=cf，失败后查询 node=nya；参数不约束返回域名；同校验和与大小才允许在同次传输中替换）、大小/MD5 校验和 `Prefetch` 共享下载机制；详见[统一回源选路](console.md#统一回源选路)。歌曲持续处于设定的预缓存范围时，已经准备成功的歌曲不因重复同步而重新请求；离开设定的预缓存范围后清除完成标记，重新进入时再次解析地址并检查缓存，缺失则补下。完整队列中的已有缓存持续受保护，不受热度影响，也不会因移出设定的预缓存范围而失去保护；预算不足时可暂时超限，普通离队（包括空队列快照）后保留 30 秒交接保护，避免播放请求稍晚到达时预缓存已被淘汰；重复快照和 HEAD/探测请求不会延长或提前结束期限。到期主动触发回收，停止监听、换房、日志失效及退出立即清除交接保护，活动播放请求仍由独立引用保护。仅凭队列快照无法区分删歌与开始播放，因此普通删歌和清空也有此宽限期；这不保证整首播放期间始终留盘。失败最早 60 秒后重试，且歌曲必须仍在前 N 个位置（默认 3）。原始日志存在 `songId=-1` 条目，保留位置但不请求曲库。与全曲库下载补齐互斥，补齐期间临时暂停，结束后仅在用户仍希望开启且应用未退出时恢复，暂停期间关闭则不恢复；只读扫描可同时运行。队列预缓存和下载补齐各支持最多 2 首并发，下载引擎统一限制后台任务最多占用 2 个名额（默认总共 3 个），为播放保留 1 个名额。删歌、切房或歌曲移出设定的预缓存范围时，立即取消该歌曲的地址解析与额度等待，并更新实际资源的下载需求。新队首需要名额时，旧下载按下面的优先级让位；实际 worker 完成取消及临时文件、连接清理后才归还名额，不挤占播放预留名额。失效取消和抢占不计入队列失败或 60 秒重试；仍有需求的被抢占任务等待名额后重新下载。

停止、删歌、切房会撤销对应的下载需求。没有资源竞争时，已经开始的下载可以自然完成；出现更高优先级需求时允许抢占。正在服务的有效视频 GET 独立保有最高优先级，包含等待首字节和后续块的时间，不因队列变化而被取消。退出控制台会关闭缓存引擎并取消全部下载。手动开关是本次运行的用户意图，不改写自动启动配置。下载补齐临时暂停队列；此时关闭队列会取消结束后的恢复。播放网关停止或故障不停止队列。日志目录不可读时显示预缓存错误，不阻止播放网关启动。

失败状态按歌曲 ID 保存并按当前队列顺序显示，其他歌曲成功不会掩盖仍待重试的失败。歌曲删除、队列清空、换房或停止监听时清理对应错误；重试成功只清除该歌曲的错误。已被移出队列的下载即使稍后失败，也不会恢复过期提示。

## 资源需求与优先级

| 等级 | 有效需求 | 调度方式 |
| --- | --- | --- |
| P0 | 正在服务的视频 GET | 请求等待和传输期间保护；结束或断开即释放 |
| P1 | 预缓存窗口第 1 个位置的有效歌曲 | 优先于后续队列和后台补齐 |
| P2 | 窗口内第 2～N 个位置的有效歌曲 | 按最新队列位置先后 |
| P3 | 全曲库补齐等主动预取 | 不抢占更高等级 |
| 无需求 | 已离开窗口且没有 GET 或主动预取 | 有竞争时优先取消 |

需求按 MD5 合并。同内容的多个歌曲或多个 GET 任一仍有效，就按其中最高等级处理。队列重排即时更新等级；协调器仍只保留两个准备调用，必要时取消较后的等待者，让新队首进入。无效歌曲占用原队列位置，不向后扩展窗口。

只在名额受限且存在更高等级（或 P2 中更靠前位置）的等待任务时抢占，先选择无需求任务；同级同序不相互抢占。每次先等待已选 worker 真正退出，再决定是否还需让位。新 GET 遇到同 MD5 的旧 worker 正在取消时，会等待其清理并重新取得资源，不并行启动重复下载。所有名额均被不可抢占的 GET 占用时，新的不同资源请求仍可返回 503。

HEAD、探测、历史 GET 和热度不保有 P0；不解析视频开始/结束事件，也不推断游戏画面是否播放。30 秒交接保护只保留缓存文件，不强制继续下载。现阶段没有落盘断点续传、连续权重或全局带宽限速；被抢占的未完成内容重试时重新下载。该调度不改变单个视频内部的 Range 读取与校验规则。

日志用 `cache_task_preempted` 记录被抢占等级、等待等级与原因，worker 清理后记录 `cache_task_canceled`；`cache_task_finished` 的取消结果与正常完成、失败分开。
