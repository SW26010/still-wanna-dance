# 日志队列预加载

> [歌曲偏好](download-resource-design.md#8-歌曲屏蔽与收藏)只在来源准备阶段过滤屏蔽歌曲，完整队列仍交给既有计时机制参与时长及 `need-by` 估算，屏蔽成员不会提前让出队首身份。收藏标记不产生预加载需求。已开始的准备按原生命周期结束，后续新准备读取最新偏好；屏蔽跳过不进入失败重试。

桌面程序的「房间队列预加载」读取 VRChat 新增日志，根据队列顺序，为即将播放的有效曲库歌曲登记下载需求；实际下载时机由预计播放时间和全局块调度决定。设置「预加载与下载」中的「随视频网关启用队列预加载」（`queueWithGateway`）默认开启，保存后重启生效。开启时随网关启动；网关停止、故障或加速回滚时等待队列停止并撤销需求。关闭时网关不启动队列。后台队列由网关生命周期管理，不提供独立 HTTP 启停入口，WebUI 入口按[目标设计](webui-design.md)统一收口；仅启动程序或刷新网页不单独开队列。读取失败单独报告，不改变整体加速的 hosts／网关成功判定。VRChat 日志目录默认每次启动按当前 Windows 用户自动读取 `AppData/LocalLow/VRChat/VRChat`，输入框显示灰色且不可编辑。只有勾选「手动指定 VRChat 日志目录」（`manualLogDir`）后才接受并保存 `logDir`；手动模式不能为空。自动模式保存时将 `logDir` 清空，快照也不保存自动路径。旧配置缺少 `manualLogDir` 时恢复自动模式，包括曾固化的路径；原先确需自定义目录的用户需重新勾选并指定。

提前准备的时机由播放期限和准备时间 M 共同决定，M 可在设置中调整，详见[启动窗口与运行规则](download-concurrency.md)。队列登记范围与下载提前窗口的区别见下方[队列范围与提前准备](#队列范围与提前准备)。

## 日志检测与频率

参考 dancing-log 本地检出 `c3fa28fa3b68879cb43513bc2cb53f1cc03fa1cc` 的 [vrc_log_watcher.py](https://github.com/SW26010/dancing-log/blob/c3fa28fa3b68879cb43513bc2cb53f1cc03fa1cc/dancing_log/vrc_log_watcher.py) 与 [vrc_log_parser.py](https://github.com/SW26010/dancing-log/blob/c3fa28fa3b68879cb43513bc2cb53f1cc03fa1cc/dancing_log/vrc_log_parser.py)。调查时 GitHub 返回 404，实际参考源码来自本机已有仓库。独立用 Go 标准库实现，没有引入 Python 运行依赖。

- dancing-log 默认轮询 0.25 秒。Still Wanna Dance 每 **3 秒**检查当前日志并从字节偏移读取增量，每 **15 秒**扫描新日志文件；没有新增内容且未触发日志失效清空时，不解析日志，也不唤醒队列协调器。
- 初次启动从现有最新文件末尾开始，等待新的队列同步。不会重放旧会话；在点歌前开启最稳妥。新会话文件从头读取，按 VRChat 文件名中的会话时间选取，旧文件 mtime 改变不会倒退。
- 保留尚未写完的行，完整换行后再解码，支持 UTF-8 跨次写入。单次最多读取 4 MiB，单行最多 1 MiB。截断、替换、读取失败、异常队列行会清空待处理队列。
- 处理 `OnPreSerialization: queue info serialized:` 和 `OnDeserialization: syncedQueuedInfoJson =` 两类 JSON 数组，仅提取 songId 顺序（包括未知占位）；不提取日志中的标题、时长和玩家姓名。忽略当前视频 userData 和预览事件，不持久化完整日志。WebUI 的歌曲名称来自本地清单，未知时显示 ID；调度时长和大小也只使用自己的媒体数据。
- 离房、进入新房间、应用正常退出或文件切换时清空待处理队列；日志 5 分钟无新增时也清空，等待新的同步。
- 当前文件新增日志通常在 0～3 秒内被读取，新日志发现通常在 0～15 秒内。游戏本身的日志缓冲、磁盘和系统调度会增加延迟，这不是严格实时保证。

## 下载调度

同一次读取中的快照先合并为最终队列，再通知后台协调器。来源按最新顺序逐项解析，成功登记块使用需求后即可处理下一项；校验和发布结果独立反馈，不等待前面的整首视频完成。容量不足时只保留一个已解析待接入项，等待需求释放通知；解析后的旧来源不能因晚到结果复活。

队列更新、歌曲偏好提交和重新取得准备资格直接通知协调器，失败重试由最近到期的一次性 timer 驱动，均不依赖下一次日志读取；通知与重试规则见[容量接入、准备回补与保留取舍](download-resource-design.md#5-容量接入准备回补与保留取舍)。

固定使用 CF 播放入口（不回退 HKG；参数不约束返回域名；同校验和与大小才允许在同次传输中替换）、大小/MD5 校验和 `Prefetch` 共享下载机制；详见[统一回源选路](console.md#统一回源选路)。歌曲持续处于队列中时，已经准备成功的歌曲不因重复同步而重新请求；离队后清除完成标记，重新进入时再次解析地址并检查本地资源，缺失则补下。已接入的块使用需求进入本地保护提前窗口后保护数据，最后一份块需求结束后按配置时长延续（默认 300 秒，0 表示不延续）；队首退出的 2 秒使用交接先按窗口保护，再从交接结束起延续配置时长。普通离队不生成使用交接，但已有保护仍按最后需求结束起延续。远期队列需求不会仅凭队列身份保护整文件；任一块受保护或存在必要文件引用时，完整视频仍不能回收。重复快照、HEAD、停止监听及换房不刷新或清除已有延续期；引擎关闭结束运行期保护。普通失败最早 60 秒后重试，且歌曲必须仍在队列中；因下载截止失败的同一成员须等队列预计开始时刻或媒体时间估算改变后才可再次准备，重复快照或定时重试不能续命。原始日志存在 `songId=-1` 条目，保留位置但不请求曲库。手动下载和全曲库补齐不暂停或恢复队列，各来源通过统一需求管理共享下载；只读扫描也可同时运行。队列预加载和下载补齐不再设独立歌曲并行门槛；唯一块使用需求最多 4096，非 GET 新增唯一块后的总量不超过 2867。网络执行由全局块调度管理。删歌或切房会取消对应的地址解析及调用，再按下文生成有限交接租约。停止的任务清理后，仍有有效需求的缺块重新建立任务，复用仍可读的完整块；顺序下载重新开始。

停止、删歌、切房撤销对应来源，有限交接期内可继续共享下载。其他 GET 的实际读取需求独立存在。退出程序关闭引擎并排空全部执行；下载补齐、队列随动配置和自动启动意图按各自生命周期管理。

失败状态按歌曲 ID 保存并按当前队列顺序显示，其他歌曲成功不会掩盖仍待重试的失败。歌曲删除、队列清空、换房或停止监听时清理对应错误；重试成功只清除该歌曲的错误。已被移出队列的下载即使稍后失败，也不会恢复过期提示。

## 资源需求与优先级

这一层负责把队列与读取事实转换为独立块需求；整体动机、分层及算例见[全局块调度设计](block-scheduler-design.md)，参数与协议细节见[运行规则](download-concurrency.md)。

期限使用自己的媒体数据：队首开始时刻为当前有效 GET 最早预计播完的时刻，后续逐首累加本地歌曲清单 end；各块按 media.byte_size 和时长的比例推导 ReadyBy。GET 时间基准固定为请求到达时刻，Range 起点近似对应播放点，下载速度或读取推进不重置它。没有有效 GET 时保留尚在未来的估算，已落后的起点由来源层按 10 秒节奏推进到当前时间；滚动阶段按块距队首的相对时间分别判断下载和保护窗口，避免刷新间隙反复入窗、回收和重取。队列未离队不能仅因经过预计时间而视为已经消费。最后一个 GET 传输退出不等于播放结束。规则见 [canonical 队列预计使用时间](download-resource-design.md#队列预计使用时间)，元数据缺失和版本匹配见[并发说明](download-concurrency.md)。重复快照本身不重置基准，重排及本地元数据更新重算受影响项；日志只用于歌曲 ID 顺序。

2026-10-15 起使用[全局块调度](download-concurrency.md)。队列控制器按完整队列顺序和块需求容量有序接入，日志只提供顺序。资源层按当前顺序产生有限 ReadyBy，调度器按实际 Blocking、期限和独立租约分配执行能力；不再使用视频 P0～P4 或后台视频席位抢占。Blocking 绕过启动窗口、缓增与普通额度，但计入总在途数；普通有限期限块先进入 ReadyBy − M 窗口，再在总在途数低于开放额度时按 ReadyBy 启动。有可启动积压且额度满才逐路增开；可启动积压包括已入窗任务和允许提前执行的独立补齐需求，不再反推目标并发；期限、来源或 Blocking 变化不暂停仍有有效需求的在途下载。

队首消失会在来源管理内原子转移尚未结束的完整使用范围，包含已下载块，交接到真实退出 + 2 秒固定结束，ReadyBy 在原期限上一次延后 2 秒；普通队列删除直接撤销。队首与普通队列互换只更新原来源的属性，不创建交接。队列删除后重加或重置会换用新标识，旧的地址解析结果不能重新登记为新队列来源。

新 GET 注册自身的读取需求并共享完整可读块及仍有合法执行资格的在途请求。同块有有效 GET 时，旧交接不参与调度属性竞争；独立队列需求仍按自己的期限竞争，交接也仍按固定租约到期。GET 取消/关闭后的交接最多 2 秒，ReadyBy 同样只在原期限上延后 2 秒；读取正常推进/Seek、完成和引擎关闭不生成交接。交接不保留原始来源，转换日志记录来源与原因，运行时只保存剩余范围、冻结的时钟及固定到期；下载协调器从中筛出缺块，不再生成交接。无有效需求或交接后不继续补齐；未来再次需要时可复用本引擎仍保留的完整块。

文件保留层不再维护队列专属保护；完整文件回收与手动删除均检查统一的块保护。关闭引擎立即取消所有执行和租约，等待正文/写盘清理；不提供跨重启断点续传。旧等级日志按原版本解释，新调度可通过 block_schedule 事件检查块身份、Blocking、ReadyBy、放行/结束原因、active/open、block_time_ms/prepare_ahead_ms，以及 started 的 overdue（start_urgent 已移除）；不再输出 target/supply。通过 block_demand 与 block_demand_handoff 检查来源汇总和交接转换；常规任务日志继续区分完成、失败与取消。

本地保护提前量由独立的引擎配置 LocalProtectAhead 控制，程序接受 0～24 小时，0 跟随有效下载 PrepareAhead（默认 500 秒）。正常配置与验收约定有效保护提前量不小于下载提前量，运行时不校验两者大小关系，也不自动抬高较短的值；暂不新增 WebUI 设置。完整使用范围、配置延续、块文件存储与回收均已接入，现行规则和验证边界见[下载需求与资源管理设计](download-resource-design.md)。

开发验证见[块调度记录](validation/block-scheduler-validation.md)。旧实机报告继续保留；新规则待 LA-040，关联 LA-037/038/039。

## 队列范围与提前准备

完整队列按顺序参与需求登记，不再按位置或歌曲数量截断。来源逐项解析，直到全部登记或块需求容量不足；容量释放后继续回补。重排只更新仍在队列中的已登记来源，不因位置变化清除准备结果或取消其调用；尚未准入的待办仍按最新顺序放行。

提前准备时间 M 控制已登记块何时允许下载，不限制需求登记范围，也不保证整首立即下载完成。非曲库条目不请求资源，但保留顺序，并按每项 210 秒估算后续歌曲的使用时间。现行容量、下载与保护规则统一见[下载需求与资源管理设计](download-resource-design.md)；历史验收记录中的数量限制只适用于其对应构建。

## 离线回放与验证

独立命令只读日志并输出统计，没有本地视频读写或网络调用：

```powershell
go run ./cmd/still-wanna-dance-replay -show-terms
# 阅读并同意后运行；此工具只读本地日志，不访问内容服务。
go run ./cmd/still-wanna-dance-replay -accept-terms=2026-10-11.1 -logs '<log-collector-directory>\logs\source-vrc-logs'
```

2026-09-25 回放结果：68 份文件、805,405 行；5,843 次队列快照，其中 376 次为空，1,893 次与上一个队列 ID 序列相同；最大队列 20 项，覆盖 1,043 个有效歌曲 ID；出现 223 个非曲库条目（按快照累计），解析失败 0。原始日志未复制进仓库。

`go test ./...` 和 `go vet ./...` 通过。自动化覆盖两种队列来源、无效数据、半行 UTF-8、EOF 起读、截断、新文件发现、旧文件 mtime 变化、入队/删歌/换房的快照合并、解析地址期间删歌、去重、失败退避、批量任务并行和退出回收。旧版浏览器的队列／补齐互斥验收仅适用于旧实现；当前并行行为见 WebUI 验证记录。
