# 统一存储

StepStash 使用一个存储根目录。控制台设置 `storageDir`，命令行使用 `-storage-dir`，默认 `stepstash-data`。本格式不兼容旧数据库和旧文件名，不提供迁移。

```text
stepstash-data/
  videos/<资源指纹>.mp4
  tmp/download-*.part
  stepstash.sqlite
  .lock
```

曲目 ID 标识目录中的曲目，视频 URL 中的编号属于视频资源，两者不要求相同。例如曲目 138、140 可以同时引用同一视频。资源指纹是 URL 文件名中的资源编号、版本、MD5、长度组成的 SHA256，不包含请求曲目 ID、Host 和 URL 目录，因此同一资源可以跨曲目和 CF/HKG 复用。这是资源身份指纹，不对不同资源地址中内容相同的文件进一步去重。

每个资源只有一份正式视频和一项版本记录。共享下载按资源指纹合并；每个曲目的预取调用在完整校验成功后分别保存引用，即使共用同一个下载任务也不会丢失曲目映射。批量及队列预取传入实际曲目 ID；只有视频 URL 的直接播放或预取不猜测曲目，不创建虚构的歌曲记录。

首次成功校验建立该曲目的初始引用。同曲出现不同资源时，再以该曲目的 ID 向歌曲 API 查询当前资源（最多等待 5 秒）；匹配候选才更新引用。返回的视频编号可以与曲目不同。API 不可用或返回其他资源时保留原引用，新下载失败也不动原资源。不根据哈希、请求到达或下载完成顺序判断新旧。

替换引用后，只有不再被任何已知曲目当前引用的历史资源才会被清理；正在播放、校验、预取或下载的资源延后至最后一个使用者结束。另一首曲目仍引用旧资源时继续保留。迟到的旧 URL 不能回滚引用；重启会重试清理。纯视频请求无法建立曲目关系，未关联曲目的资源通过容量策略管理，不根据文件名推断新旧。未同步过的曲目引用无法被本地知晓。

| 表 | 内容 |
| --- | --- |
| `songs` | 曲目 ID、标题、附加资料 `metadata_json` |
| `video_versions` | 资源指纹、MD5、大小、来源路径；无所属曲目字段 |
| `song_videos` | 曲目与已校验资源的历史关联 |
| `current_videos` | 每首曲目当前引用的资源指纹，允许多曲目引用同一资源 |
| `resource_usage` | 按资源指纹统计的需求次数和时间 |
| `request_events` | 资源请求结果、耗时与字节数；不推断播放曲目 |

直接播放的请求仅携带资源信息，所以热度按资源统计，跨 CDN 共用，同一资源 30 秒内去重。扫描只读校验文件，不写映射或统计；界面检查结果按曲目计数，本地文件数量和容量按唯一资源计数。

下载先写 `tmp`，校验大小和 MD5 后发布至 `videos`，再记录资源及曲目引用。Windows 发布时临时复制一次，播放结束后删除下载临时文件。文件发布和数据库提交不是跨资源原子操作：崩溃可能留下已校验文件但缺少记录，下次命中补齐，无需重新下载。淘汰只删除文件，保留曲目、资源、关联和统计；版本记录存在不代表文件仍在磁盘，每次读取检查实际文件和完整性。

`.lock` 独占存储目录。重启清理 `tmp/download-*.part` 和已确认无当前曲目引用的历史资源。容量上限仅计算正式视频，数据库和临时文件另需空间；容量淘汰可以删除仍被曲目引用但未被活动请求占用的资源，需要时重新下载。备份请在停服后保存整个根目录。
