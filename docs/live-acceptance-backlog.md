2026-10-16 按必要性整理：原 46 项收敛为下列 **5 组游戏场景**，沿用原编号。合并与迁出不是通过；原步骤、补充、自动结果及批次链接完整保存在[分流前快照](live-acceptance-backlog-20261016-archive.md)，非游戏工作见[开发验证分流](validation-followups.md)。本次仅整理规则与文档，没有执行新一轮验收。

## LA-025：播放接入与恢复

- **依据与必要性**：[API 接入边界](resource-domains.md#仅接管-api-的假设与待验证边界)、`internal/cacheproxy/{playback,server,redirect}.go`。请求脚本能验证协议和选路，但不能证明 VRC 是否重新访问本地 API、复用旧资源地址或接受返回视频的方式。
- **最少操作**：在已准备好的隔离环境冷播一首，再热播/切线路恢复进度；如仍需覆盖中途接入，让一首先播放再启用接入，观察后续新的游戏动作，结束时恢复直连并触发一次新播放。所需接入操作由 agent 在本轮授权内执行。代理模式只有涉及游戏 HTTPS 透传的剩余风险时补一个代表场景，不按节点/协议做全组合。
- **预期与证据**：实际音画及进度符合操作，能区分本地 API 请求与旧解析资源读取；恢复后新动作可正常直连。共用游戏/服务相对时间线及简短音画反馈；仅本轮触及 hosts 时附前后差异和恢复回执。
- **已有覆盖**：[LIVE-20261015-01](live-acceptance-20261015-01.md) 的 CF 冷热、完整缓存及直连恢复反馈正常；这部分无需因本次文档整理重测。旧构建结论不外推至受影响的新实现。升级、导入、缓存文件校验及代理候选穷举转开发验证，不再分别追加“游戏 HIT”。

## 全局块调度与有限需求租约

### LA-040：慢网拖动、多播放器与后台竞争

- **依据与必要性**：`internal/blocksched/`、`internal/cacheproxy/{scheduled_download,scheduled_range,block_demands,stream}.go`；[开发验证](block-scheduler-validation.md)、[调度规则](download-concurrency.md)。真实播放器的探测/重连、并发读者及用户观察到的卡顿不能仅由受控 HTTP 断言代表。
- **最少操作**：优先复测历史失败条件下的冷播放和前后拖动，再在同一会话加入同歌预览/正式双播放器及后台预取，取消一个读者或切歌，观察另一个是否继续。单连接限速与总带宽限速分清，不为每个修复分支另开游戏操作。agent 先分析历史证据、准备可控复现和所需采集；不能把未定位的问题反复交给用户重试。
- **预期与证据**：取消一个读者不打断仍有需求的播放；可用带宽恢复后不永久等待，进度与音画恢复；记录起播/Seek 等待及卡顿。低于媒体所需带宽不承诺无卡顿，保留实际瓶颈和恢复结果。共用请求/读者时序、针对问题的调度日志及音画反馈；判断游戏卡顿时由 agent 同步采集必要 CPU/帧时间，完成下载时核对文件哈希。
- **失败与已有覆盖**：[LIVE-20261014-02](live-acceptance-20261014-02.md) 的 1 Mbps 交互未恢复、[LIVE-20261015-01](live-acceptance-20261015-01.md) 的聚合慢网冷播卡顿/双播放器 Seek 长等待继续跟进；[LIVE-20261015-02](live-acceptance-20261015-02.md) 日常播放及 38 文件校验正常，没有复测上述失败。本项汇总原 LA-008/020/037/038/039 的相关游戏行为，不因 A1–A8 或调度重构的自动检查通过就关闭失败。
- **已分流**：16 路额度、250 ms 增路、T/M 边界、租约精确时间、容量 4,094 块、候选耗尽、错误 Range、MD5、竞态和文件清理由开发测试/隔离进程验证，不再要求游戏逐条证明。原 6/4 路、每视频固定 worker、1 秒宽限等旧策略不再适用；历史依据保留。

## LA-041：队列交接与真实游戏事件

- **依据与必要性**：`internal/vrclog/`、`internal/console/queue.go`、`internal/cacheproxy/{queue_timing,demand,block_demands}.go`；[队列机制](queue-prefetch.md)。真实游戏的队首消失、日志落地、播放器 GET 与开播间隔不能由人工构造快照证明。
- **最少操作**：复用 LA-040 的慢速下载，让队首自然切入正式播放；利用同轮热缓存场景作对照。对尚缺的来源退出覆盖，在游戏中重排/删歌或离房，核对没有旧队列复活；同一动作覆盖相关需求、续传与交接，不按旧编号重复。
- **预期与证据**：歌曲与 GET/开播关联正确，交接没有导致错误撤销/重复下载或永久等待；退出来源后不复活旧队列。agent 关联队列快照、应用发现时刻、正式 GET 与游戏开播/音画反馈，区分预览，注明轮询和日志缓冲误差；记录交接是否在接手前到期及其实际影响，不预设必须小于 20 秒，不把未开播样本填成零。
- **已有覆盖**：[LIVE-20261015-01](live-acceptance-20261015-01.md) 有三笔交接观测；[LIVE-20261015-02](live-acceptance-20261015-02.md) 的 37 个正常网络样本中，消失→正式开播为 9–11 秒，消失→候选 GET 为 0.962–2.371 秒。保留这些结论，只补慢网/租约及未覆盖事件；不重新收集同类 37 个样本。LA-043 的设置与窗口计算转开发验证，实际提前准备效果在本场景观察。

## LA-011：多人中途加入

- **依据与必要性**：[历史未覆盖项](live-acceptance-20261007.md)。多人同步、非 owner 的进度追赶与房间实际播放状态无法由单人或 HTTP 请求替代。
- **最少操作**：在合适实例中以非 owner 中途加入正在播放的歌曲，确认追上实际进度并持续播放；可复用本轮 LA-025 的接入环境，无需额外切全套线路。
- **预期与证据**：同步进度正确、音画持续，记录实际角色、同步/播放事件、服务请求及用户反馈。实例暂不可用时仅保留此场景，不阻塞其他开发；不在材料中保留玩家/房间身份。
- **状态**：待验收；早期其他版本的通过记录不自动证明当前相关实现。

## 零容量缓存与独立不限选项

### LA-047：零预算下的实际播放保护

- **依据与必要性**：`internal/cacheproxy/{retention,cache}.go`；[开发验证](cache-capacity-validation.md)。引用/保护逻辑可自动验证，剩余风险是实际播放器断开/重连和真实队列事件之间的空窗是否触发过早回收。
- **最少操作**：agent 提前在隔离配置应用零预算并验证生效；复用 LA-040 的冷播、拖动和 LA-041 的预取→正式播放，在保护有效时重播，随后退出相关需求并等待回收。
- **预期与证据**：实际播放/交接不因误删而中断，保护有效期间复用已有内容，最后保护释放后可回收；共用音画、请求/命中、引用释放与文件变化记录。无需在游戏里重复设置输入、CLI、重启、正数/不限矩阵或异常进程清理。
- **状态**：待验收。零预算完整响应、共享/交接保护、计时回收及 UI 输入已有[自动与浏览器结果](cache-capacity-validation.md#自动检查)，本次不重复执行或外推为游戏通过。
