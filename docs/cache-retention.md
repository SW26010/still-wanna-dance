# 视频缓存优先级与上限

控制台「视频缓存上限（GiB）」支持两位小数，0（默认）表示不限；停止 CDN、队列和批量任务后保存，下次启动 CDN 或下载任务时生效。命令行使用 `-max-cache-bytes`，单位为字节，负数拒绝启动。旧配置缺少此字段时保持不限。

上限按歌曲库 `<正整数ID>/video.mp4` 和缓存目录 `<64位版本键>.mp4` 的文件长度合计；两份副本分别计数。包含已有歌曲库视频，启用有限上限即允许其参与淘汰。元数据、下载说明、统计数据库、其他文件和符号链接不删除。此值是保留视频容量，非整个磁盘的硬配额；数据库、元数据和下载临时文件不计入。

## 排序规则

直接复用 SQLite 的 `song_usage.demand_count` 和 `last_demand_at`：

`优先级 = ln(1 + 去重需求次数) / (1 + 距离上次需求的天数 / 7)`

- GET 按既有 30 秒窗口跨 Host/版本去重；统计代表观察到的请求需求，并非确认完成播放。HEAD、预缓存不增加热度。
- 七天衰减尺度抑制长期未使用的历史热门视频；对数频次避免累计次数长期支配排序。
- 无需求记录的视频得分为 0，优先淘汰。
- 同分时先淘汰较早的需求；无需求时用文件修改时间。时间仍相同时先淘汰版本缓存副本，再按路径稳定排序。
- 版本缓存由已有 `request_events.version_key/song_id` 关联歌曲，在首次超限时加载历史映射，新请求补充内存映射；无法关联的旧版本按无需求处理。不同版本沿用歌曲级热度。

## 执行与并发

启动缓存引擎时，以及同一歌曲最后一个请求、预缓存或后台下载引用释放时，检查容量；worker 与 handler 的重复释放合并为引用归零时的一次检查。先扫描视频容量，未超限（含恰好等于上限）直接返回，不等待统计落盘、不读取数据库、不排序。超限时先排空已接受的统计事件，再按低到高顺序清理到上限。正在响应、校验或下载的歌曲使用引用计数保护；低优先级文件仍被占用时延后删除，不会因此改删更高优先级的视频。最后一个使用者结束后重新清理。

单个视频大于上限仍可播放，但使用结束后不能长期保留。低优先级预缓存可能下载成功后立即被淘汰；预缓存成功表示完成校验和发布，并不保证一直保留。临时文件及受保护的视频可能令实际占用暂时超过上限。

删除失败记录 `cache_eviction_failed`，下次清理重试；实际删除记录 `cache_evicted`，暂不能满足上限记录 `cache_limit_deferred`。数据库无法打开时使用文件时间作为降级排序；已打开数据库查询失败时本轮不删除，保留错误日志。保留需求统计，不因删除视频丢失历史热度。

不支持另一程序同时写入相同歌曲库；仅配置不同 cache-dir 不提供跨进程歌曲库保护。默认不限时不扫描或淘汰。

## 验证

自动化测试覆盖衰减/频次排序、无需求预缓存淘汰、双副本计量、启动清理、元数据及未知文件保留、引用计数保护、低优先级占用不挤出热门视频、活动 HTTP 响应保护、超大视频完整播放后清理，以及控制台配置持久化和负数拒绝。
