# Issue #21：实际预取与有界历史复验

本协议在首次运行前登记，作为 CONTINUATION 的下一阶段；不修改既有校准窗。研究对象是指定 Wi-Fi 下、Direct 模式、CF 播放节点的完整预取。使用现行 Console 播放地址解析、Monitor、候选池、缓存引擎的分块、回退、完整 MD5 校验与发布。没有播放器/VRC，也不声称覆盖自动 CF/HKG 路由或运行多日后的 Monitor 历史。

## 三个策略

- `ordinary`：新建独立 DNS/客户端，没有测量推荐，按当前产品冷启动回退直接预取。
- `monitor`：新建相同 DNS/客户端和 CF 范围的现行 Monitor，默认策略执行一次 `CheckThroughput`，随后调用实际 `operationSelections`。保留真实 TTL 资格及全部推荐顺序；没有推荐时使用普通客户端，不强迫固定已失效地址。只做一次检查，不通过连续人工触发改变迟滞状态。
- `history-two`：仅复验凌晨已冻结的完整训练 DNS 赢家 `2606:4700:20::681a:41c` 与额外来源赢家 `104.16.0.1`。对歌曲 1343 各做一次冷连接 8 MiB、15 秒上限的 HTTPS/证书/206/内容校验，选完整成功中耗时较小者；均失败则普通直连。两者来自 `calibration-01/selection.json`，SHA256 为 `fb8a2221d52ae2e0f5318d15075dd94663d12da097e24f5303983fad8d3cb640`，绝不按晨间排名改历史。选中地址仅有五分钟实验资格，保留普通直连作为引擎回退；不写产品 DNS。探测池关闭，业务池重新建立，这个冷连接差异需在结果中说明。

Monitor 的成本包含实际 API/资源检查；历史复验包含训练资源 API 准备和两次探测。业务任务直接调用 `Console.prefetchSong`，包括 API、资源传输与本地发布，不再另做业务视频预热或完整内容参考。各会话使用新的存储目录、DNS 和连接池，存储设为 unlimited 以保留并核验文件，不接触用户存储。相同会话内连续三个不同资源保留连接，避免重置成三次独立首用。

## 次序与预算

- 每个窗口三轮：第一轮 `ordinary, monitor, history-two`；第二轮 `monitor, history-two, ordinary`；第三轮 `history-two, ordinary, monitor`。
- 每个会话顺序预取 1344、10552、10553；每轮轮转资源起点，使三个资源各占一次首任务位置。
- 历史两地址探测顺序随轮次交替。每个会话最多六分钟，初始化测量最多三分钟；每个业务任务 90 秒，窗口最多 30 分钟和 3 GiB 已读应用正文（不等于网卡流量，DNS/协议开销另在连接日志中）。固定资源合计超过 200 MiB 则停止。
- 准备失败保留为该会话失败及未执行任务，不换歌补齐；一个任务失败仍可继续下一项，除非绑定、内容身份、429/503 或总预算触发停止。所有未执行项必须列出。
- 先执行一次晨间窗口；午间 12:00–13:30 使用冻结构建再执行一次。方法错误先用离线夹具修正并另记版本，不能把实网失败归为无效数据后静默重跑。
- 每窗开始前检查竞争测速进程，测量时不编译、运行另一个测速或下载研究附件。

## 判读

分别报告初始化耗时/正文、每任务 API+下载+发布耗时、实际远端/推荐变化、累计首一/二/三任务的全成本及成功率。`monitor` 初始化加首任务是“用户主动要求先检查再下载”的实测场景；产品正常冷启动不会强制等待后台测速，不能把该时间宣称为产品固有首用延迟。另列已准备推荐后的任务成本。

记录每次请求的阶段、目标主机（不导出签名 URL）、范围、长度、状态、证书验证、实际远端、缓存状态、连接复用、实际读字节和错误。完整任务以产品成功返回、MISS、真实发布文件的长度/MD5 为准；重试/失败不能在成功后消失。实际请求未触发回退时只能证明接线已保留回退，不能声称已实网验证故障恢复。

每轮同歌曲/同序号对照；首先列原始会话和配对，不把 1 MiB 块当独立网络样本，也不把同地址的差异解释为候选收益。只有两个独立窗口，仍不能证明跨日、跨运营商或晚高峰稳定性。累计三任务不摊平为无限任务收益；不得用假设无限复用掩盖前置成本。

## 晨间后、午间前的记录器修订

晨间 v1 完成 27 个真实任务后，检查发现普通直连的一个成功媒体响应把嵌套 DoH 连接 `1.12.12.12` 记为媒体远端。此前只清理“HTTP 失败时的 DNS 远端”还不够：DNS trace 可以晚于媒体 GotConn。保留 v1 原始文件、二进制 `ef4e35a8ba37e47b1ab90ffc069e89f7917458ecdbf99e67c72733a9858fb29f` 和源文件快照；任务时间、实际 TLS 响应及完整文件校验仍有效，普通直连的所有未过滤远端仅当线索，不能作确定路径归因。

v2 仅修订观测：GotConn 必须具有验证过的 TLS 状态且 ServerName 等于当前请求主机，才记录为当前连接；用锁防止未结束 DNS callback 与记录读取竞争。增加“媒体成功后到达 DNS GotConn”的夹具。策略、候选、资源、顺序与预算不变。午间改用经验证并重新冻结的 v2，明确区别构建，不覆盖 v1。

正式午间窗之前允许一个单独的 `TestCFProductTraceSmoke`：只执行第一轮 ordinary 的三个任务，确认真实目标连接能被正确区分；不增加策略性能配对，也不作为独立时段收益证据。此诊断的缺少其余 24 项是预先限定范围，不记为正式窗口失败。累计会话墙钟含研究记录保存和独立文件复核；同时报告初始化与业务任务秒表之和，避免把夹具开销当成下载成本。
