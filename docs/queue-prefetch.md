# 日志队列预缓存

控制台「房间队列预缓存」读取 VRChat 新增日志，根据队列顺序，为即将播放的有效曲库歌曲登记下载需求；实际下载时机由预计播放时间和全局块调度决定。通过独立按钮开启或关闭，不依赖本地播放网关；设置中「控制台启动」的「运行控制台时自动启用房间队列预缓存」（`autoStartQueue`）默认启用。字段缺失或为 null 时采用该默认值，已保存的 true/false 保留，不跟随播放网关或废弃的 `queuePrefetchEnabled` 字段。实际游戏读取本地缓存仍需启动播放网关并完成 hosts 接入。VRChat 日志目录默认每次启动按当前 Windows 用户自动读取 `AppData/LocalLow/VRChat/VRChat`，输入框显示灰色且不可编辑。只有勾选「手动指定 VRChat 日志目录」（`manualLogDir`）后才接受并保存 `logDir`；手动模式不能为空。自动模式保存时将 `logDir` 清空，快照也不保存自动路径。旧配置缺少 `manualLogDir` 时恢复自动模式，包括曾固化的路径；原先确需自定义目录的用户需重新勾选并指定。

提前准备的时机由播放期限和准备时间 M 共同决定，M 可在设置中调整，详见[启动窗口与运行规则](download-concurrency.md)。当前准备范围的配置边界集中记录在下方[现有设置说明](#现有设置说明)。

## 日志检测与频率

参考 dancing-log 本地检出 `c3fa28fa3b68879cb43513bc2cb53f1cc03fa1cc` 的 [vrc_log_watcher.py](https://github.com/SW26010/dancing-log/blob/c3fa28fa3b68879cb43513bc2cb53f1cc03fa1cc/dancing_log/vrc_log_watcher.py) 与 [vrc_log_parser.py](https://github.com/SW26010/dancing-log/blob/c3fa28fa3b68879cb43513bc2cb53f1cc03fa1cc/dancing_log/vrc_log_parser.py)。调查时 GitHub 返回 404，实际参考源码来自本机已有仓库。独立用 Go 标准库实现，没有引入 Python 运行依赖。

- dancing-log 默认轮询 0.25 秒。Still Wanna Dance 每 **3 秒**检查当前日志并从字节偏移读取增量，每 **15 秒**扫描新日志文件；没有新增内容时不解析、不请求歌曲 API。
- 初次启动从现有最新文件末尾开始，等待新的队列同步。不会重放旧会话；在点歌前开启最稳妥。新会话文件从头读取，按 VRChat 文件名中的会话时间选取，旧文件 mtime 改变不会倒退。
- 保留尚未写完的行，完整换行后再解码，支持 UTF-8 跨次写入。单次最多读取 4 MiB，单行最多 1 MiB。截断、替换、读取失败、异常队列行会清空待处理队列。
- 处理 `OnPreSerialization: queue info serialized:` 和 `OnDeserialization: syncedQueuedInfoJson =` 两类 JSON 数组，仅提取 songId 顺序（包括未知占位）；不提取日志中的标题、时长和玩家姓名。忽略当前视频 userData 和预览事件，不持久化完整日志。控制台歌曲名称来自本地清单，未知时显示 ID；调度时长和大小也只使用自己的媒体数据。
- 离房、进入新房间、应用正常退出或文件切换时清空待处理队列；日志 5 分钟无新增时也清空，等待新的同步。
- 当前文件新增日志通常在 0～3 秒内被读取，新日志发现通常在 0～15 秒内。游戏本身的日志缓冲、磁盘和系统调度会增加延迟，这不是严格实时保证。

## 下载调度

同一次读取中的快照先合并为最终队列，再通知后台协调器。来源按最新顺序逐项解析，成功登记块使用需求后即可处理下一项；校验和发布结果独立反馈，不等待前面的整首视频完成。容量不足时只保留一个已解析待接入项，等待需求释放通知；解析后的旧来源不能因晚到结果复活。

使用设置中的回源线路（默认 Auto：主动下载先查询 node=cf，失败后查询 node=nya；参数不约束返回域名；同校验和与大小才允许在同次传输中替换）、大小/MD5 校验和 `Prefetch` 共享下载机制；详见[统一回源选路](console.md#统一回源选路)。歌曲持续处于当前准备范围时，已经准备成功的歌曲不因重复同步而重新请求；离开当前准备范围后清除完成标记，重新进入时再次解析地址并检查缓存，缺失则补下。已接入的块使用需求进入本地保护提前窗口后保护数据，最后一份块需求结束后固定延续 60 秒；队首退出的 20 秒使用交接先按窗口保护，再从交接结束起延续 60 秒。普通离队不生成使用交接，但已有保护仍按最后需求结束起延续。远期需求和准备范围外的队列项目不会仅凭队列身份保护整文件；任一块受保护或存在必要文件引用时，完整视频仍不能回收。重复快照、HEAD、停止监听及换房不刷新或清除已有固定延续期；引擎关闭结束运行期保护。失败最早 60 秒后重试，且歌曲必须仍在当前准备范围内。原始日志存在 `songId=-1` 条目，保留位置但不请求曲库。与全曲库下载补齐互斥，补齐期间临时暂停，结束后仅在用户仍希望开启且应用未退出时恢复，暂停期间关闭则不恢复；只读扫描可同时运行。队列预缓存和下载补齐不再设独立歌曲并行门槛；唯一块使用需求最多 4096，非 GET 新增唯一块后的总量不超过 2867。网络执行由全局块调度管理。删歌、切房或移出窗口会取消对应的地址解析及调用，再按下文生成有限交接租约。仍有有效需求的暂停块在资源允许时续取，顺序下载重新开始。

停止、删歌、切房撤销对应来源，有限交接期内可继续共享下载。其他 GET 的实际读取需求独立存在。退出控制台关闭引擎并排空全部执行；下载补齐、队列开关和自动启动意图仍按原生命周期管理。

失败状态按歌曲 ID 保存并按当前队列顺序显示，其他歌曲成功不会掩盖仍待重试的失败。歌曲删除、队列清空、换房或停止监听时清理对应错误；重试成功只清除该歌曲的错误。已被移出队列的下载即使稍后失败，也不会恢复过期提示。

## 资源需求与优先级

这一层负责把队列与读取事实转换为独立块需求；整体动机、分层及算例见[全局块调度设计](block-scheduler-design.md)，参数与协议细节见[运行规则](download-concurrency.md)。

期限使用自己的媒体数据：队首开始时刻为当前有效 GET 最早预计播完的时刻，后续逐首累加本地歌曲清单 end；各块按 media.byte_size 和时长的比例推导 ReadyBy。GET 时间基准固定为请求到达时刻，Range 起点近似对应播放点，下载速度或读取推进不重置它。没有 GET 时从首次队列快照开始；最后一个 GET 传输退出后保留已算出的队列起点，避免把传完误认为播完。元数据缺失和版本匹配规则见[并发说明](download-concurrency.md)。重复快照不滑动期限，重排及本地元数据更新重算受影响项；日志只用于歌曲 ID 顺序。

2026-10-15 起使用[全局块调度](download-concurrency.md)。队列控制器在当前准备范围内按块需求容量有序接入，日志只提供顺序。资源层按当前顺序产生有限 ReadyBy，调度器按实际 Blocking、期限和独立租约分配执行能力；不再使用视频 P0～P4 或后台视频席位抢占。Blocking 绕过启动窗口、缓增与普通额度，但计入总在途数；普通有限期限块先进入 ReadyBy − M 窗口，再在总在途数低于开放额度时按 ReadyBy 启动。有可启动积压且额度满才逐路增开；可启动积压包括已入窗任务和允许提前执行的独立补齐需求，不再反推目标并发；期限、来源或 Blocking 变化不暂停仍有有效需求的在途下载。

队首消失会在来源管理内原子转移尚未结束的完整使用范围，包含已下载块，交接到真实退出 + 20 秒固定结束，ReadyBy 在原期限上一次延后 5 秒；普通队列删除直接撤销。队首与普通队列互换只更新原来源的属性，不创建交接。队列删除后重加或重置会换用新标识，旧的地址解析结果不能重新登记为新队列来源。

新 GET 注册自身的读取需求并共享已完成块、部分前缀和在途请求。同块有有效 GET 时，旧交接不参与调度属性竞争；独立队列需求仍按自己的期限竞争，交接也仍按固定租约到期。GET 取消/关闭后的交接最多 2 秒，ReadyBy 同样只在原期限上延后 2 秒；读取正常推进/Seek、完成和引擎关闭不生成交接。交接不保留原始来源，转换日志记录来源与原因，运行时只保存剩余范围、冻结的时钟及固定到期；下载协调器从中筛出缺块，不再生成交接。无有效需求或交接后不继续补齐；未来再次需要时可复用本引擎保留的进度。

文件保留层不再维护队列专属保护；完整文件回收与手动删除均检查统一的块保护。关闭引擎立即取消所有执行和租约，等待正文/写盘清理；不提供跨重启断点续传。旧等级日志按原版本解释，新调度可通过 block_schedule 事件检查块身份、Blocking、ReadyBy、放行/暂停原因、active/open、block_time_ms/prepare_ahead_ms，以及 started 的 overdue（start_urgent 已移除）；不再输出 target/supply。通过 block_demand 与 block_demand_handoff 检查来源汇总和交接转换；常规任务日志继续区分完成、失败与取消。

本地保护提前量由独立的引擎配置 LocalProtectAhead 控制，0 跟随下载 PrepareAhead（默认 500 秒），允许 0～24 小时；暂不新增控制台设置。完整使用范围及 60 秒延续已接入，块文件存储与回收迁移继续见[下载需求与资源管理设计](download-resource-design.md)。

开发验证见[块调度记录](block-scheduler-validation.md)。旧实机报告继续保留；新规则待 LA-040，关联 LA-037/038/039。

## 现有设置说明

「队列预缓存数量」（`queuePrefetchCount`）是现有上层准备范围的设置，未来可能调整或弃用。它限制哪些队列位置会被登记为准备任务；具体下载时机和网络并发仍由块调度器决定。维护文档和后续设计时，以队列需求及预计播放时间为主线，数量设置只作为当前实现的边界说明。

该设置目前仍生效：可设为 1～100，默认 3；旧配置缺失或为 0 时使用默认值，非曲库条目也占队列位置。修改并保存后，在重启应用时生效。这些位置内的歌曲仍须等待各自的启动窗口，不保证立即下载或已完整缓存。

```powershell

# 阅读并同意后运行；此工具只读本地日志，不访问内容服务。
go run ./cmd/still-wanna-dance-replay -accept-terms=2026-10-11.1 -logs '<log-collector-directory>\logs\source-vrc-logs'
```
