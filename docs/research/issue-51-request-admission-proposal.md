# Issue #51：接续请求入口判断与播放模型

本页保留实验设计和当时的判定条件。后续已确定的规则以[正式播放需求与 GET 入口](../download-resource-design.md#正式播放需求与-get-入口)为准。

历史桌面 canary 接入记录见[验证报告](../validation/issue-51-canary.md)。以下实验阶段的策略和默认值仅适用于相应批次。

当时的状态：已完成可选日志模型、历史回放、隔离引擎检查及[首轮模型实机观察](../acceptance/live-acceptance-20261117-01.md)。当时 main 已统一为 2 秒交接，下载延续仍为 30 秒；正式产品未启用模型入口拒绝或 10 秒覆盖。实验采用默认 2 秒、模型命中部分 10 秒；模型默认关闭，主动 504 仅针对确认的非 owner。现行规则以[下载设计](../download-resource-design.md)为准，实验代码与复现入口见[播放模型实验](../../experiments/playback-model/README.md)。

## 目标与实施边界

网络无法连续供数时，希望播放器在短暂中断后尽快重新播放，允许跳过部分进度；同时避免因为正常预读而打断播放。先用历史资料检查判定，再用临时机制观察游戏，取得收益和成本证据后才决定产品接入。此前只靠 HTTP 请求组合建立模型的讨论保留在下文作为历史特征复核，本阶段不实施该识别器，也不在缺少日志时启用它作为替代。

模型共用日志中的本机角色与正式播放器同步目标，以及匹配媒体版本的歌曲时长和文件大小。模型不改写获准 GET 的调度时钟，三种时间分别服务于不同目的：

| 参数 | 实验值与作用 |
| --- | --- |
| 模型余量 | 下一阶段采用 0 秒，保留线性映射；历史回放覆盖 0、2、5、10 秒，首轮实机使用 5 秒，不将其结果改记为 0 秒验证 |
| 退出后的交接 | 原本可交接的剩余范围默认 2 秒，模型预计仍会用到的部分为 10 秒；从实际退出时刻计算 |
| 下载延续 | 保持当前调度器的 need-by + 30 秒；模型不延长该截止 |

## 数据来源与有效性

复用现有 `internal/vrclog.Tail`，可选解析已观察到的 WannaDance 正式播放器日志。普通队列读取仍走原解析器；只有显式开启 Playback 才提取角色、起播、同步目标、暂停、结束、错误与重新加载事件。事件中不保留玩家名字、世界标识、完整 URL 或原始行。

采用 `Syncing video to` 后的目标秒数，不采用同一行中可能已停住的 `current time`。时间依据为日志事件时间，日志精度为秒；当前读取轮询为 3 秒。实验最多接受延迟 4 秒的事件，过旧、未来时间、日志读取错误、日志轮换／截断或离房会使模型失效。重复的同歌同秒起播不覆盖已有同步；暂停会撤掉时间线，Seek 后以新同步目标更新。错误和重新加载期间暂停主动拒绝，仍可供旧请求退出时判断交接范围。

模型不把本地画面停住解释为房间进度也停住。只有收到新起播和同步依据才建立有效时间线；启动时从现有日志末尾读取，缺失角色或进度时入口放行。此版本仅支持已记录的世界日志格式、同一正式播放器；多播放器关联及世界格式变化没有产品级覆盖。

### 时长能否实际读到

2026-11-16 对日常配置指向的数据库作只读核对：歌曲与媒体关联查询取得 10,576 条记录，全部有正数 `songs.end` 和 `media.byte_size`。八首回放歌曲也有对应元数据，例如 4598 为 133 秒、2502 为 206 秒、6776 为 522 秒；[脱敏核对结果](../evidence/issue-51-playback-model-20261116/log-model-replay.json)只保留数量、歌曲编号、秒数和大小。

现有 `Store.mediaTiming` 已按媒体 MD5 与歌曲关联读取 `songs.end`；本字段是目录的结束时间，当前实现将其用于文件位置到时间的换算，不能称作逐文件探测得到的精确容器时长。早前实验夹具没有插入此字段，实际走了默认 2 Mbps 换算，不能用那份实验数据库代表日常库。新夹具明确写入对应时长，模型要求调用方提供同版本的明确元数据；缺失、无效或无法匹配时放行，不用默认码率触发主动 504。变码率和目录时间误差仍由模型余量容忍。

### 文件位置到播放时间的复核

11 月 17 日新增[全库索引研究](issue-51-media-time-map-20261117.md)：10,197 个文件成功解析，10,152 个匹配目录；线性位置换算相对块最早音视频使用点的第 5／95 百分位误差为 −6.72／+7.63 秒。改用容器精确总时长仍不能消除主要偏差。因此，上文“由余量容忍”只是原设计意图，不是固定 5 秒已覆盖误差的保证。

离线比较包含负余量；统一 −2 秒会使 72.61% 被统计块的拒绝阈值早于索引使用点，但这个比例不是实际拒绝频率。8935 的边界接续用 0 秒或 +2 秒均会改变判定，尚未实测该反事实的恢复收益。

### 阶段决策：线性映射、0 秒余量

全库块误差分布复核后，下一阶段保留现有线性映射，采用 0 秒余量；不增加预制媒体索引、索引生成／发布机制或运行时解析依赖。已有误差统计保留为近似模型的边界，不能用均值接近零推导每个块都准确。当前没有证据证明额外增加 2 秒等待的净收益，也没有证据证明预制索引对实际恢复的收益足以抵偿维护成本。

0 秒表示符合其他入口条件的请求在 `当前时间 > N(x)` 时可被拒绝，不表示播放器已经确定卡住。沿用同一个模型余量时，交接范围判断也相应以 `N(x)` 为界；默认 2 秒、模型命中部分 10 秒的寿命和下载延续 30 秒不变。此前 5 秒实机结果及程序快照保持原样，本次只记录阶段取舍，未改变运行程序或启用正式产品策略。只有后续出现可归因于位置映射偏差的实际误拒绝或恢复损失，再评估索引的必要性。

## 入口判断：在新需求建立前返回一次 504

1. 确认本机为非 owner、模型有效且不处于已拒绝／错误恢复阶段。角色未知或 owner 均放行。
2. 关联同歌曲、同媒体版本的前后请求。原范围为半开区间 `[a,b)`，截至新请求到达实际连续交付到 `d`；后一次恰好请求 `[d,b)` 或 `[max(a,d−8192),b)`，并且仍索取同一个未就绪块。错误正文不计入视频交付；前次请求仍活动时读取当时快照，不能使用未来最终字节数。
3. 以最近有效同步时刻 T、同步目标 P、对应媒体时间 D 和大小 S，计算缺口 x 的预计使用时间：`N(x) = T + D × x / S − P`。接续 HTTP 请求不重新建立这份时间依据。
4. 只有 `当前时间 > N(x) + 余量` 才在新需求及视频响应头产生前返回 504。否则原样交给 SWD。范围改变、块已就绪、缺少明确元数据或无法关联均放行。
5. 同一已识别播放最多拒绝一次；同歌自动重新加载不会清掉拒绝标记。结束／停止／重置或切歌后才允许下一次，宁可漏掉未能明确识别的同歌重播，也不制造连续 504 循环。

模型按预计时间判断“过时”，播放器仍可能需要这个块；首轮实机中两首受阻歌曲在模型 504 后越过仍不可读块并恢复。实验就绪检查使用受控缺块的放行状态；桌面观察构建另有只记录、不改变响应或交接的接入，未作为本轮被测程序。正式构建未启用主动判定。

## 交接：对原本可交接的范围选择 2 秒或 10 秒

对 GET 撤销后按现有规则仍可交接的未交付范围逐块判断：模型有效且退出时刻不晚于该块 `N + 余量` 的部分保留 10 秒，其余 2 秒。相邻同寿命块合并成范围，再复用现有交接建立机制；取消原因与原请求调度时钟保留。不根据“是否预计重新加载”分类，也不因重复通知续期。

正常完成、无剩余范围和本来不产生交接的退出不新增交接。现有下载截止退出先剔除已经不符合原请求时间依据的范围，这个筛选保持；模型只能为剩余范围选择寿命，不能重新纳入被剔除的块、开放新的普通下载启动资格或越过调度截止。

新入口 504 没有建立需求，因此不创建、延长、补建或升级交接。重新加载期间只能使用旧 GET 退出时已有的交接及其他仍有效来源。10 秒只是一项实验参数，早前约 6 秒请求空档提供了选取依据；预读错误后数十秒才再次读取的样本不在它的覆盖保证内。

## 本阶段已验证的范围

[历史日志回放](../evidence/issue-51-playback-model-20261116/log-model-replay.json)覆盖第二、三批共 12 笔记录，扫描四种模型余量与 0、2、3 秒日志轮询附加延迟。为避免秒级日志把同秒稍后发生的错误提前暴露给判定，事件到该秒结束后才视为可用，再增加模拟延迟。回放只采用新请求到达前已经结束的视频响应；重叠旧请求的中间进度不从最终字节数倒推。

在 5 秒余量的三个延迟设置下：

- 四笔已知预读提前 504 样本（5396、3214、1314、6776）均放行；原未注入的 3136 也放行。
- 4598 基线、提前 504、缺块后移及连续三块四笔的第 3 个请求被判断为过时接续。
- 2502 和两笔手动刷新没有匹配到该拒绝条件，不当作误判或恢复收益样本。
- 关闭模型时所有回放请求均放行。上述只是固定历史请求到达时的判断，不是假设改变响应后播放器仍会保持同一后续请求序列。

[隔离真实引擎检查](../evidence/issue-51-playback-model-20261116/model-engine-check.json)使用合成的本机非 owner 日志和受控 HTTP 请求：首次 206 交付 2 MiB 后取消；关闭模型，重试仍为 206，交接全为 2 秒；开启模型，重试为 504，SWD `request_started` 数量不增加，再次重试为 206。实际交接调用将块范围 `[2,5)` 保留 2 秒、`[5,34)` 保留 10 秒。这里证明入口位置、一次拒绝限制和范围寿命接入，本轮的检查对象为请求准入逻辑。

解析器及模型全部单元测试、race 检查通过。现有 Console 队列相关回归在沙箱内遇到仓库已知的 `renameat: The handle is invalid`；按开发约定在普通用户环境重跑通过，未修改产品文件操作。上述是 11 月 16 日的非游戏开发检查；11 月 17 日新增实机结果如下，策略仍仅在实验引擎生效。

## 首轮实机结果与剩余验证

11 月 17 日的[六笔记录](../acceptance/live-acceptance-20261117-01.md)包含五笔可解释样本与一笔受干扰样本：4598、2502 各一次模型 504 后越过仍不可读块并恢复；3214、1314 的正常预读接续均按模型放行，未报告异常并观察到结束。5396 的故障计时被提前自动加载消耗，不作为干净边界样本。

8935 暴露了入口单次判断的边界：接续到达时已晚于预计使用点约 2.609 秒，但距 5 秒余量截止尚有 2.391 秒，因此放行；此后跨过截止本身不会重新判断，直到约 25.4 秒后来源恢复。人工观察卡顿约 28 秒、无黑屏、自然结束。调小余量在同一记录上会改变判定，但提前拒绝的实际净收益未测，尚不据此修改参数或增加请求内中断。

实际 2／10 秒交接分段已记录；由于后段数据大多已经由来源交付且使用无限缓存，没有证明 10 秒比 2 秒挽救了未完成下载。来源供数字节及执行驻留统计保留在证据中，没有对应控制组，不计算交接净收益。先用受控调度检查复用与额外额度成本，只有留下游戏特有问题时再安排实机。

模型启动晚于播放、角色未知、暂停／Seek／同歌重载等开发边界已有自动检查；真实世界日志到达顺序是否满足模型输入仍需随上述场景核对。当前 5 秒余量不是最佳值，10 秒交接也没有与 2 秒做实机成本对照。临时方案验证后再决定是否接入产品，不将本项作为现有产品发布阻塞。

## 追加 owner A/B：角色独立模型的负面样本

[LIVE-20261117-02](../acceptance/live-acceptance-20261117-02.md)在当前 main 正式逻辑基线下比较 A 与 0 秒、取消角色门槛的 B。开头缺块时 A 未重新加载，B 一次提前 504 后回零，整首起播到结束由 133 秒增至 170 秒；后半段 A、B 都在正式等待正文超时后回零，均为 288 秒，B 没有入口主动拒绝。后半段 B 的预读接续因没有有效同步时间线而放行，不计作模型正确识别预读；日志中同步与 start 的顺序作为开发边界保留。

结果证明不加角色门槛的模型可能给 owner 增加负面影响，但不能估计频率，也没有证明 504 是回零的必要条件。本次是实验扩展，不改写前述默认非 owner 门槛或正式产品策略；尚未测试其他返回码。

后半段终端日志明确标记 `download need-by window expired`，上述等待超时指等待正文期间下载时间窗口到期，不据约 30 秒的间隔另推独立读取超时。后续在隔离夹具中实现并观察了“有效媒体请求先发送合法 200／206，再按原截止中止响应”；结果见下节。无限 HTTP 等待未测试，正式产品策略未变更。

## 正常响应头与手动刷新：事实、推断与后续计划

### 观察到的事实

[LIVE-20261117-03](../acceptance/live-acceptance-20261117-03.md) 记录 owner 在全部响应为 200／206 时仍自行报错、重新加载、同步归零并再次撞上同一永久缺块。因此 504 不是回零的必要条件，本轮在正常响应头后到期断流时也观察到回零。无正文请求连续失败至报错约 183 秒，但 SWD 每约 30 秒断流，尚不能区分总等待时钟和失败次数，播放器的固定等待阈值仍未知。

同批 owner 手动刷新则在缺块仍不可读时跳到后段、保留原时间线，约 3 秒恢复并自然结束。[LIVE-20261117-04](../acceptance/live-acceptance-20261117-04.md)另有两首各一次重复，卡住 12 秒后刷新、约 2 秒恢复。三笔均有新请求越过坏块和游戏同步位置支持；未证明任意刷新时点、多块阻塞或所有播放器版本都有相同结果。刷新后的旧缺块请求可能继续与新请求重叠，不能把画面恢复当作需求已经完全交接。

另一笔在来源恢复后自行继续的样本，先收到原缺块数据再请求后段，不属于跳过仍不可读块。短歌结束后才恢复供数的样本没有画面恢复，不混入成功组。

非 owner 的三组对照已取得恢复观察：3136 的 504 自动组总卡顿约 24 秒；504 策略下卡住 8 秒后刷新，总卡顿约 12 秒、点击后约 4 秒恢复；206 策略下同样等 8 秒刷新，总卡顿约 10 秒、点击后约 2 秒恢复。两笔成功手动刷新均未实际收到 504，新请求起点同为 3,162,112 字节，超过 2–3 MiB 缺块末尾 16 KiB。

另两笔在卡住 1 秒、3 秒后刷新，首次目标同为 2,260,992 字节，仍在坏块内；等待 30 秒后由原截止返回 504，随后自动重载恢复，点击至恢复均约 40 秒。收到 504 后才点击的补充样本没有显示明显加速。缓存绕过、好友操作干扰、实际等待与计划不同的样本均保留在报告中；不能将这些样本改记为成功或合并为一种刷新时机。

### 推断与工程取舍

**非 owner 保留有条件 504 是当前证据支持的默认方向。** 它有无人操作时自动跳过的收益，也没有显示损害成功手动刷新的能力；206 未显示相应优势。单次 2 秒差异不足以确定策略速度差异。此处的判断针对已过时接续请求及原等待截止，不支持对正常预读无条件返回 504。

手动刷新能否迅速恢复，取决于后续请求是否真正越过坏块；本歌的 8 秒成功不能直接变为通用刷新阈值。owner 正常响应配合手动刷新仍是候选方向，不能承诺自动等待永不回零。这些取舍未自动转为正式产品实施。

### 未来计划

后续优先从已有日志复查恢复后仍存活的旧请求、需求和下载任务，量化过时占槽及交接复用，再决定是否微调内部生命周期。当前资料未证明 10 秒交接的净收益，也没有给出统一缩短交接的依据。若另行开展产品接入，再验证 owner 分支、模型不可用的处理及真正受影响的边界；不为当前非 owner 默认取舍重复追加相同实机。详细未决项以[本轮未来计划](../acceptance/live-acceptance-20261117-04.md#未来计划)为准。

## 历史备选：仅靠 HTTP 建模的特征复核

本节为离线复核，没有新增游戏实验，也没有实现识别器。选取三批 issue #51 的 26 笔记录，加上 2026-11-13 的正式重试、owner 回零、非 owner 追赶及正常刷新四笔，共 30 组 HTTP 序列；另核对一笔独立冷 Seek。解析／播放器标签沿用源证据的客户端分类，不把 User-Agent 当作唯一用户标识。前歌请求从目标序列中剔除；旧同步、缓存干扰样本保留原限制，不算干净首次播放。数据、复算脚本及来源哈希见[特征证据](../evidence/issue-51-playback-model-20261116/request-features.json)、[清单](../evidence/issue-51-playback-model-20261116/manifest.json)。

### 可以利用的特征及其边界

| 候选特征 | 已有事实 | 对模型的含义 |
| --- | --- | --- |
| 无 Range 的解析 GET 后出现播放器 GET | 30 组中按相邻请求开始事件提取到 57 对；28 对出现在该组首个播放器 GET 之后 | 是请求关联线索，不能单独判为新播放；播放器 GET 不一定带 Range |
| 解析结束到播放器请求的间隔 | 46 对有完整相对时间，间隔为 0.331–0.473 秒；其余时间未知，未补造 | 可优先从解析结束计关联窗口；这是样本分布，不是已确定的超时阈值 |
| 从解析开始计短窗口 | 11-13 正式重试样本有约 20.388 秒间隔，但解析结束到播放器请求仅约 0.387 秒；owner 样本初次间隔约 13.798 秒 | 固定很短的“开始到开始”窗口会漏掉解析耗时长的有效组合 |
| 首次播放器请求一定是 `bytes=0-` | 11-16 首批 N20、N10R、H2 的首个播放器请求没有 Range；H2 后续才请求非零范围 | 无 Range 的请求也可能读取视频正文；应结合客户端类型和实际服务范围识别从头完整请求 |
| 无 Range → 从零 Range 表示新播放 | 11-13 正常手动刷新样本，刷新后再次出现该组合；随后跳到 8,814,592 字节 | 组合也表示重新打开已有播放，不能无条件重置原时间线 |
| 新请求与旧请求不重叠 | 手动刷新 8935 时，新从零 GET 到达后旧 GET 仍存在约 9.795 秒；11-13 正常刷新样本的对应新从零 GET 则在旧播放器 GET 结束约 0.070 秒后到达 | 重叠和不重叠都可能发生于刷新；时间上不重叠不是新播放的充分条件 |
| 下次恰好接着已交付剩余范围，或回退 8 KiB | 三笔预读 504 重试均满足这种范围关系；画面当时仍正常 | 可识别接续读取，但无法单独判断卡顿；需模型与块就绪状态共同参与 |
| 重载一定从零请求 | 11-13 owner 回零样本重载后请求仍从 16 MiB 开始，而游戏日志确认同步到零；11-16 预读重载后也从原缺口前 8 KiB 续读 | HTTP 字节起点不能直接当作实际播放位置；owner 回零需结合游戏进度和请求共同判断 |
| 首个观测请求代表本次播放开头 | 手动刷新 4598 样本首个 HTTP 请求从 4,329,165 字节开始，人工此前已报告起播；该样本保留缓存干扰限制 | 缺少开头证据时不能强建从零模型；采集开始前可能已有同一播放的请求 |
| 非零 Range 前跳代表新播放／重载 | 独立冷 Seek 直接请求 `40681472–52379699`；正式非 owner 恢复也出现前跳 | 前跳可能是 Seek、同步或恢复，只能证明读取范围改变，不能唯一识别用户动作 |

上述相邻请求组合按每组事件计算，日常频率另需按时间采样。30 组中有 5 组观察到播放器请求时间重叠；其他并发组合仍可能发生。11-13/06 中前一媒体的请求 1–4 已从统计排除，防止跨歌曲误关联。冷 Seek 为预览操作，用于说明 HTTP 特征的不唯一性，不作为正式播放策略已验证的证据。

### 可继续验证的最小识别顺序

1. **先确定关联对象。** 同一媒体版本、实际服务范围和播放器请求类别是必要输入；解析请求只提供关联线索。现有资料没有证明 HTTP 字段能够可靠区分同机多个相同播放器，无法唯一关联时不强行合并模型。
2. **先尝试解释为已有模型的接续，再考虑建立新模型。** 用成功交付位置、剩余终点和未就绪块关联，区分错误响应正文与真正视频字节。不能将 504 的 16 字节错误正文算成视频消费推进；也不能等旧 GET 结束后才看新请求，因为已有重叠样本。
3. **没有可解释的旧模型时，从头播放器 GET 可建立候选时间线。** 解析结束后紧随播放器 GET 可增强关联；使用播放器 GET 时间作为候选基准比解析 GET 开始更接近数据读取，但仍早于实际起播。播放器 GET 无 Range 也可表示完整范围；不硬编码“必须有两次请求”。
4. **已有模型时，解析／从零组合只表示发生了新的加载过程。** 不自动重置；继续观察是否接回原缺口、短读前缀后跳向后段，或出现与原时间线冲突的读取。现有记录不足以可靠区分同歌真正重播、Seek、缓存恢复和 owner 回零；冲突时暂停入口拒绝、回到默认交接，比将预测当作真实进度更保守。此为候选处理，未实现。
5. **新模型与旧模型的有效期、调整余量分别确定。** 解析关联窗口解决两次请求能否配对；模型有效期解决是否仍属同次播放；时间余量解决预计使用点误差，三者不能混成一个时间常量。不能仅因暂时没有活动 GET 就销毁模型：视频数据可能早已传完，画面仍继续播放。

可直接从现有 HTTP 路径获取的输入包括媒体身份／大小、请求范围及实际响应范围、到达时间、成功视频交付位置、结束时间和退出原因；歌曲时长与块就绪状态应读取已有数据，检查本身不启动下载。跨请求保留记录的范围、容量和失效方式尚未设计。当前 `CurrentGETs` 的活动快照在请求结束后移除记录，不能独自承担跨空档的模型历史，也不应以用户可见的观测接口承担模型状态。

**阶段结论：** “解析结束后约半秒到达播放器请求”是已有样本支持的关联特征；“从头完整请求”可以提供候选时间基准。二者都不是新播放的唯一标志，“无重叠”也不能补足这一点。现有证据足以排除仅按一次请求组合就重置模型的规则；尚不足以确认一个可靠区分全部播放生命周期的 HTTP 识别器。后续先用这些已知反例离线检查候选规则，不能将匹配到组合本身算作识别成功。


这部分描述改用日志模型之前的备选识别顺序。本阶段保留证据和反例，不实施 HTTP 独立生命周期识别器。
