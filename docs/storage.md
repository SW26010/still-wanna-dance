# 统一存储

StepStash 只使用一个存储根目录。控制台设置 `storageDir`，命令行使用 `-storage-dir`，默认 `stepstash-data`。不读取或迁移旧歌曲库、旧缓存和旧统计数据库。

```text
stepstash-data/
  videos/<歌曲ID>-<版本键>.mp4
  tmp/download-*.part
  stepstash.sqlite
  .lock
```

每个视频版本只有一份正式文件。版本键为歌曲 ID、URL 文件名版本、MD5、长度组成的 SHA256；Host 和 URL 目录不参与键，因此同一版本可跨 CF/HKG 复用。每首歌长期只保留一个版本；更新和播放期间允许短暂共存，不会改动正在读取的旧版本。

首次完成校验的视频作为初始保留版本。同曲出现不同版本时，在候选视频校验成功后向歌曲 API 查询当前地址（最多等待 5 秒），只有匹配的候选才能替换保留版本；不根据哈希、请求到达或下载完成顺序判断新旧。API 不可用、返回其他歌曲或其他版本时保留原版本，候选仍可完成本次播放，使用结束后删除。新下载失败也不动原视频。不主动轮询所有歌曲更新。

替换成功后删除旧文件；仍有播放、校验或下载引用时延后至该版本最后一个使用者结束。迟到的旧 URL 即使重新下载，也不会反向覆盖当前版本；它只用于本次请求。即使容量不限也会清理旧版本，重启会重试遗留清理。歌曲、历史版本描述和请求统计继续保留在数据库中。

数据库是歌曲资料、版本信息和请求统计的唯一存储：

| 表 | 内容 |
| --- | --- |
| `songs` | 歌曲 ID、标题和附加歌曲资料 `metadata_json` |
| `video_versions` | 版本键、歌曲 ID、MD5、大小及来源路径（含文件名版本） |
| `current_videos` | 每首歌当前保留的视频版本键 |
| `song_usage` | 歌曲需求次数与时间汇总 |
| `request_events` | 每次请求的结果、耗时与字节数 |

批量下载从歌曲目录接口保存标题；直接播放只有视频请求信息时创建无标题歌曲记录。不会生成每首歌的 `metadata.json`。淘汰视频只删除文件，歌曲资料、版本记录和需求历史继续保留；版本记录存在不代表视频仍在磁盘，读取时始终检查文件及其完整性。

下载先写入 `tmp`，校验大小和 MD5 后发布到 `videos`，再以数据库事务写入歌曲及版本信息。为支持 Windows 上仍在播放的下载句柄，发布时会临时复制一次；播放结束后删除下载临时文件，不保留第二份正式视频。文件发布和数据库事务不是跨资源原子操作：崩溃可能留下已校验视频但缺少版本记录，下次请求命中后补齐记录，无需重下；容量淘汰从文件名识别歌曲 ID 并使用歌曲级热度。数据库打不开则启动失败，不以无数据库模式运行。

存储根目录由 `.lock` 独占，重启清理 `tmp/download-*.part` 和数据库已确认被取代的视频。不要在运行中修改文件或数据库；备份应在停服后保存整个根目录。视频上限只计算 `videos` 下的正式视频，临时文件和数据库另需空间。
